브랜치를 받아 `origin/main`(9e77a95) 기준으로 전수 대조하고 테스트를 돌렸습니다. 수치는 전부 맞고 CI도 깨끗합니다. 다만 **§2.3(값이 바뀌면 그것을 가리키던 곳을 전수로 찾는다)에서 네 곳이 남았고, 그중 하나는 이 PR이 고친 행이 직접 링크하는 문서**입니다. 그리고 `memory.high` 서술은 이 저장소의 기존 기록과 어긋납니다.

## 확인된 것

수치는 전부 맞습니다.

```
85,899,345,920 == 80 GiB   True
68,719,476,736 == 64 GiB   True   (이전 값)
62,277,025,792 == 58 GiB   True   (이전 high)
80 / 119.7 = 0.6683 → 0.67        기존 표의 반올림 방식과 같습니다 (64/119.7=0.5347→0.53, 58/119.7=0.4845→0.48)
0.9 × 80 = 72.0
64 − 58 = 6
```

- **코드·config에 64 GiB로 사이징한 곳이 없습니다.** `config/`·`src/`·`tests/`·`scripts/`·`tools/`에 `64 GiB`·`68719476736`·`62277025792` 히트 0건입니다. util 기본값은 `tools/probe/run_probe.sh:32`의 `0.6` 하나인데 그 분모는 물리 119.7 GiB라 다른 축입니다. 이 PR이 config를 안 건드린 것이 맞습니다.
- **브랜치가 최신입니다.** `merge-base`가 `origin/main` HEAD와 같고, 세 파일을 건드린 커밋이 main 쪽에 없습니다. 리베이스 불필요합니다.
- `pytest -q` → **930 passed, 3 skipped**, `ruff check .` → clean. `tests/test_docs_format.py` → **248 passed**로 PR 본문의 수치가 그대로 재현됩니다. 표 열 수·내부 링크 테스트도 통과합니다 — 링크가 박힌 표 행 셋을 고쳤는데 구조는 멀쩡합니다.

## 결함

### 1. (HIGH) `memory.high` 58 → `max`는 8/31에 일어난 일이 아닙니다 — 저장소가 이미 8/26에 기록했습니다

세 파일이 모두 스로틀 해제를 80 GiB 확장과 **동시 사건**으로 묶고 있습니다.

- `docs/experiments/README.md:211` — "**동시에** `memory.high`가 58 → `max`로 바뀌어 소프트 스로틀이 사라졌다 … (전에는 58~64의 6 GiB 스로틀 구간이 사실상 예고 역할)"
- `docs/Multi-Agent Vulnerability Harness.md:95`, `docs/portability.md:162` — "`memory.high`는 58→`max`로 바뀌어 소프트 스로틀이 사라짐"

그런데 이 저장소에 그 전 실측이 두 건 있습니다.

`docs/experiments/harness/2026-08-26-pipeline-zlib542-remeasure-atom.md:59`

> `memory.max` **68,719,476,736** (64 GiB) · `memory.high` **`max`** ← **8/25의 62,277,025,792(58 GiB)에서 풀렸다**

`docs/experiments/harness/2026-08-28-pipeline-track-a-pwn003-atom.md:122-125` — on-box 원문

```
$ cat /sys/fs/cgroup/user.slice/user-1004.slice/{memory.current,memory.high,memory.max}
13790609408        # memory.current = 12.84 GiB
max                # memory.high  = 제한 없음
68719476736        # memory.max   = 64 GiB
```

즉 스로틀 해제는 **8/25~8/26 사이의 별개 사건**이고 64→80 확장과 무관합니다. 8/31 실측이 확인한 것은 "여전히 `max`다"이지 "58에서 바뀌었다"가 아닙니다.

따라 나오는 것이 하나 더 있습니다 — **"전에는 58~64의 6 GiB 스로틀 구간이 사실상 예고 역할"이라는 과거형 서술도 틀립니다.** 8/26·8/28 run은 이미 소프트 스로틀 없이 돌았습니다. 8/28 보고서 자신이 그것을 "8/26 재측정이 '58 GiB에서 풀렸다'고 적은 것의 두 번째 확인"이라고 적어 뒀습니다.

PR 본문의 `memory.high = max (이전 58 GiB)`도 같은 자리입니다. 8/20 스냅샷과 비교하신 것으로 보이는데, 그 사이에 더 새로운 기록이 둘 있습니다.

**제안**: 세 문장을 "8/26·8/28에 이어 세 번째 확인으로 여전히 `max`"로 바꾸고, 확장(64→80)과 스로틀 해제(8/25~26)를 두 사건으로 분리하면 됩니다. 운용 결론(방어선을 직접 잡는다)은 그대로 섭니다.

### 5. (MEDIUM) "공식 할당 80 GiB"는 제시된 근거보다 셉니다 (§2.2)

`portability.md:162`와 `Multi-Agent Vulnerability Harness.md:95`가 **"공식 할당 80 GiB"**, README 241행이 "공식 80 GiB"라고 씁니다. 그런데 근거로 적힌 것은 "김진겸이 확장을 **안내**했고 손수민이 실측했다"입니다. cgroup 읽기가 증명하는 것은 **강제되는 하드 한도**이지 공식 할당이 아닙니다.

64일 때는 이 저장소가 그 구별을 명시적으로 지켰습니다 — `README.md:218-219`:

> **PL이 메모리 할당을 34 → 64 GiB로 상향했고, 2026-08-25 팀 회의에서 이를 공식 확인했다.**(cgroup `memory.max`는 2026-08-19에 이미 64로 반영됐고 …, 오늘 **회의에서** 그 상향분이 **공식화**됐다.)

cgroup 반영과 공식화를 두 사건으로 나눠 적었습니다. 80에는 회의·공식 확인이 인용돼 있지 않습니다. 회의 확인이 실제로 있었다면 그것을 적으면 되고, 없었다면 "실측 하드 한도 80 GiB"가 지금 근거에 맞는 표현입니다.
