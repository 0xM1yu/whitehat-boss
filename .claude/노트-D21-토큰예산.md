## 1. 한 줄 문제

캡슐이 토큰을 세는 공식 `estimate_tokens = len(text) // 4`([src/tokens.py:21](../src/tokens.py))가 **실서빙 실측보다 ~1.8배 적게 센다.** 그래서 캡슐이 "예산 안"이라 판단해도 실제 프롬프트는 `--max-model-len 32768`을 넘어 잘린다.

```
공식 가정:  4.0 chars/token   (len // 4)
실측:       2.224 chars/token (run_20260821_0007 scout 2콜, input_tokens 2,975 / sent_chars 6,617)
결과:       auditor 예산 24,000 → 실제 ≈ 43,200 real tokens → 32,768 초과 (이미 서버가 잘라내는 중)
```

## 2. 왜 1.8배나 — 한국어 프롬프트

- 토크나이저(BPE)는 **한글을 글자당 더 많은 토큰**으로 쪼갠다. ASCII 코드는 ~4글자/토큰, 한글은 ~2.2.
- `prompts/scout/v1/prefix.md`가 **한국어 1,061자** → 작은 대상에선 프롬프트가 한국어로 꽉 차 배율이 2.2까지 떨어짐.
- **반전:** 대상 코드가 커지면 ASCII 비중↑ → 배율이 4로 수렴. 그래서 실대상 투사는 하한(×4)·상한(×2.224)을 함께 적는다.
  - zlib `unzip.c`(67,662 B): 하한 33,831 ~ 상한 60,847 토큰. **둘 다 ×2는 D17.**
- **핵심 갈림:** 작은 대상 → 한국어(D21)가 주범 / 큰 대상 → 한국어 옅어지고 **D17의 ×2**가 주범. (하한 33,831도 이미 초과인데 그 초과는 한국어가 아니라 D17)

## 3. 왜 실 토크나이저를 안 쓰나 — "백엔드 독립" 불변식

**백엔드** = 갈아끼우는 뒷단(FakeRetriever↔Hybrid, FakeModel↔vLLM, FakeTool↔docker; 프로필로 선택).

**백엔드 독립** = 캡슐이 `(후보, 레벨, index.json)`만의 함수 → 뒷단을 뭘 끼우든 입력 같으면 캡슐 글자까지 동일. 이게 사주는 것:
1. Fake↔Hybrid retriever 교체해도 같은 캡슐 → **Fake가 실전의 충실한 대역**(테스트가 실전을 검증).
2. Fake도구↔real도구 교체해도 프롬프트 불변 → 결과 차이를 **"도구 때문"이라 귀속** 가능(교란변수 제거). ← 평가 방법론 핵심.
3. 재현성 검사(D14 trace 바이트 동일)가 Fake 경로에서 성립.

`estimate_tokens`가 **하나뿐인 싼 상수**라야 이게 보장됨. [src/tokens.py](../src/tokens.py) 모듈이 존재하는 이유가 정확히 "정의가 하나여야 두 retriever가 같은 캡슐을 낸다".

**실 토크나이저(b)를 쓰면:** 모델마다 토큰 세는 법이 달라 → 캡슐이 "어느 모델이냐"에 종속 → **백엔드 독립이 깨진다.**
- 단 정밀히 보면: 깨지는 건 **"모델 간 캡슐 동일성"**뿐이고, "같은 모델·도구만 바꾼 비교"(핵심)는 안 깬다. 그래도 "모델 종속 캡슐"을 허용할지는 팀 결정 사안.
- → **결론: 실 토크나이저는 보류. (a)/(c)로 간다.** (둘 다 싼 상수 유지 → 백엔드 독립 보존)

## 4. 대안 (a) / (c) — 둘 다 백엔드 독립 유지

`estimate_tokens`를 **토큰 재는 자(ruler)**로 비유.

### (a) 자를 다시 보정 — 상수를 내림
```python
CHARS_PER_TOKEN = 2.4     # 4 → 실측 여유값. estimate_tokens가 더 큰 값 리턴 → 캡슐 덜 담음
```
- 장점: 리턴 숫자 ≈ 진짜 토큰. 예산 숫자가 정직해짐(모든 소비처 이득).
- 단점: 진짜 배율은 **구성 의존**(한국어 2.2 ↔ ASCII 4). 한 점으로 박으면 큰 ASCII 대상은 과다(낭비). 정직히 고르려면 실대상 run 먼저.

### (c) 자는 그대로, 여유분 남김 — 안전계수
```python
# estimate_tokens는 len//4 그대로. 안전은 예산 정책에:
#   방법1(코드 0줄): config/budgets.yaml 값 축소  scout 4000→2400, auditor 24000→14000
#   방법2: fit 검사에 SAFETY=1.7 마진
```
- 장점: 자를 안 건드림("추정은 대충"이라는 정직함 유지). 방법1은 설정만.
- 단점: estimate 절대값은 여전히 틀림(넘침만 막음). 마진도 추측·일률적.

**둘은 숫자상 거의 같은 동작**(2.4로 나눔 ≈ 4로 나눈 뒤 ×1.7). 차이는 "정확한 값이라 주장(a) vs 대충 인정하고 슬랙(c)".
→ **배율이 진짜로 움직이니 (c)가 더 정직.** 특히 **(c) 방법1(budgets.yaml만 축소)**이 tokens.py 불변식 모듈을 안 건드려 제일 깔끔.

## 5. "예산만 줄이면 되지 않나?" — 맞지만 구멍 하나

- 애초에 예산 24,000은 **32K 모델이 담을 수 없는 값** → 축소는 손실이 아니라 **교정**.
- **그러나 구멍:** 제일 큰 덩어리 `{{SOURCE}}`(대상 함수 원문)가 **예산을 통째로 우회**한다.
  > D13: `target_function`도 `min()`으로 깎이지만 프롬프트엔 `read_source()`가 낸 **원문 전체**가 실린다. 캡슐 예산 검증이 아무것도 못 막는다.
- 예산이 지배: callers·callees·related·types (그래프/검색 섹션) / 우회: `{{SOURCE}}` + D17로 사실블록에 한 번 더(×2).
- → **예산 축소만으론 32K 보장 안 됨.** source를 실제로 bound해야 함.

## 6. 프롬프트 실제 크기를 줄이는 레버 (예산 숫자와 다른 층)

**층1 — 진짜 토큰 수 줄이기**
- ① **한국어 프롬프트 → 영어**: 템플릿 토큰 대략 절반 + 배율 4로 밀어 D21 완화. 선례: 전처리 `prompt.md`는 이미 영어(예준님 번역). 출력은 한국어 유지 가능(지시언어≠출력언어). 한계: 템플릿만 줄임(큰 코드 대상엔 절감 비율↓). **모델이 영어 지시 잘 따르는지 실측 필요.**
- ② **D17 중복 제거**: source·그래프가 사실블록+산문에 두 번 → 한 번. 중복분 절반.
- ③ **#25 심볼 단위(머지됨)**: 대상 파일 전체 → 함수 하나. `{{SOURCE}}` 축소. D13이 "심볼 단위 오면 target_function이 예산 다 먹는 문제 사라진다"고 적음.
- ④ 프리픽스 다이어트(few-shot 축소). ※ prefix-caching은 재계산만 아낌 — 컨텍스트 창은 그대로 먹음(맞춰넣기엔 무의미).
- ⑤ 검색 코드 슬라이싱(related를 통짜 청크→슬라이스) ← 별도 CPG 슬라이싱 트랙.

**층2 — 예산 숫자**
- ⑥ budgets.yaml 축소(코드 0줄, source 우회 주의).
- ⑦ source를 예산 안으로 강제(read_source를 자름).

**층3 — 천장 올리기**
- ⑧ max-model-len 상향(YaRN 131K; 품질·KV메모리 비용).
- ⑨ **auditor를 262K 모델(qwen3-coder-30b)로**: 실제 설계상 auditor가 30B → 43K도 여유. **지금 32K 초과는 "32K 실험 모델에 auditor 올렸을 때" 얘기**일 수 있음(큰 맥락).

## 9-2. 팀 결정 (2026-08-25 민규 회의)

> **(c) 예산 floor를 먼저 적용하고, 그 후에 실 토크나이저를 도입한다.**

- **(c) = stopgap**, **토크나이저 = 정본.** len//4는 (c) 단계까지만 살고, 토크나이저가 들어오면 계상이 실측으로 바뀐다.
- 이 결정으로 앞의 (a)/(c) 저울질과 "backend-독립이 토크나이저를 막는다"는 홀드가 **풀렸다** — 팀이 모델 종속 캡슐을 수용.
- **D17은 이 경로와 별개다**: 토크나이저는 *계상 정확도*를 고치고, D17은 *산문↔JSON 중복(×2 프롬프트 크기)*을 고친다. c→토크나이저가 D17을 대체하지 않는다(원하면 병행 트랙).

**갱신 (2026-08-25, PR #28 리뷰 후) — 값 유지, 주장 낮춤 (민규 f121b65).** 나는 성급하게 (a) 철회로 닫았으나(오판), 민규가 **값(18,000)은 두되 주장을 "천장 → 부분 완화"로 낮춰** 리뷰 5건을 닫고 PR #28을 재오픈했다:

- 그래서 18,000은 `--max-model-len` **보장이 아니라** `related` 자리를 계상 6,000 줄이는 **부분 완화**다.

→ **계상 축 정본은 (b) 토크나이저**(민규 착수). **원문을 실제로 묶는 건 프롬프트 조립부 별개 PR**(크기 축, `on_truncate` 규약 필요). `len//4`는 토크나이저 전까지 그대로.

## 9. 언제 반영하나 — "실험 끝나고"가 아니라 "비교 경계에서"

D17·D21은 버그 수정이 아니라 **측정 조건 변경**이다(캡슐/프롬프트 구성이 바뀜 → `prompt_template_version` ↑ → evaluation.md §2.3 규칙4: 이전 run과 비교 불가). 그래서 **비교 도중에 바꾸면 그 비교가 무효**다(W1·D17을 같은 PR에 안 얹은 이유).

- **지금 불난 것 없음:** auditor 43K>32K는 "auditor를 ≤32K 모델에 실서빙할 때"의 투사. 현재 ATOM run은 auditor가 Fake(`single_gpu_12g`는 scout만 실서빙), scout는 4,000→실제 ~7,190로 여유.
- **진짜 마감(deadline) 트리거:** ① auditor를 ≤32K 모델에 실서빙 직전, 또는 ② zlib급 실대상을 하네스로 통째 돌리기 직전. ↔ auditor를 **qwen3-coder-30b(262K)**로 돌리면 43K도 여유 → 덜 급함.
- **배치 반영:** 셋(D21·D17·D22)이 다 version을 올리니 **한 경계에서 묶어** 단절을 한 번만 지불. (단 "dedup이 정확도를 바꾸나"를 따로 측정하려면 D17만 분리.)

## 10. 전처리 실험 격리 — 확인됨 (외부 변수 안 들어감)

**전처리 실험(윤경님 run.py)은 저장소 프롬프트가 아니라 ATOM 로컬 포크를 쓴다.** → 저장소에서 D17/D21을 고쳐도 실험에 안 들어간다.
- `run.py load_prompt(prompt_dir)`가 `~/experiments/preprocessing/prefix.md·body.md`(로컬)를 읽음. 저장소 `prompts/` 참조 안 함.
- 혈통은 같음: prefix = `# Role: Single-Pass Auditor`(저장소 `single/v2` 계열, #21), body에 `{{TARGET}}`·`{{CAPSULE_SECTIONS}}`·FACTS 토큰 검사까지 → **D17 구조가 전처리 프롬프트에도 있음.** run.py:71이 표를 수동 동기화 중.
- **위험 경로는 하나뿐:** 실험 도중 저장소→ATOM 프롬프트 **재복사**. 그때만 외부 변수 유입.
- **그래도 형식 비교는 안전:** D17 이중렌더는 전처리 안에서 모든 형식·모델에 똑같은 **상수**라 ast↔cfg 비교를 교란 안 함. 문제는 "도중에 바뀔 때"뿐.
- **실천 규칙:** 전처리 실험 끝날 때까지 ATOM `prefix.md·body.md·run.py 하드코딩 표` **동결.** 저장소 D17/D21은 무관하게 진행 가능.
- **미확인(선택):** run.py `prompt_dir` 기본값이 로컬 고정인지, 전처리 body.md에 `{{SOURCE}}` 중복이 실제로 있는지 — 필요하면 못 박기.
