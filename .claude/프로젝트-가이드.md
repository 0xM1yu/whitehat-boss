## 1. 프로젝트 개요 (기초)

**한 줄:** 소스·펌웨어에서 취약점을 찾는 **멀티 에이전트 하네스**. 도구가 증거를 모으고, 크기가
커지는 LLM들이 후보를 단계별로 걸러낸다.

**핵심 질문(연구 목표):**

> 작은 오픈 모델을 여러 개 묶으면 Frontier 모델(GPT-4 급)의 취약점 탐지 성능에 **어디까지
> 근접**하며, 그 대가로 **비용·프라이버시**에서 얼마나 이득인가?

→ 목표는 최고 성능이 아니라 **정확도와 비용을 함께 본 최적 구조.** 그래서 모든 비교는
**계산량(토큰·GPU-second 예산)을 고정한 상태**에서 한다.

**설계 철학 5가지:**

1. **Tool-first, Model-second** — diff·정적분석·sanitizer·fuzz는 도구가. LLM은 신호 해석만.
2. **비싼 단계일수록 뒤에** — 후보는 단계마다 줄고, 모델은 뒤로 갈수록 크다.
3. **역할 = 서비스가 아니라 실행 계약** — `역할+모델+도구정책+예산+출력스키마` 조합.
4. **에이전트 간엔 대화가 아니라 구조체(Pydantic)만** 전달.
5. **처음부터 분산 안 만든다** — 단일 Python + SQLite + 로컬 디렉터리 + Docker.

**명시적 비범위(MVP 제외):** 패치 자동 생성, Kubernetes·외부 vector DB, LLM 기반 리포트/dedupe.

## 2. 무엇을 측정하나 — 조건과 지표

### 조건 (⚠️ 같은 라벨을 두 축으로 씀 — open-question D1)

**축 A — 2×2 (PRD §2.1):** 역할 분담 × 모델 앙상블

```
               단일 모델    여러 회사 모델(앙상블)
역할 통합         B1            B3
역할 분담         B1'           B3'
역할 분담 효과 = B1→B1' / 모델 혼합 효과 = B1'→B3'
```

> 앙상블 = **제작사가 다른** 모델(같은 계열 다른 크기 아님). Critic을 Devstral(Mistral 계열)로
> 두는 근거가 이것.

**축 B — 파이프라인 (PRD §5.2):**

```
B1   단일 LLM/단순 retrieval 소스 분석      (source-only 한계)
B1'  바이너리·펌웨어 포함                    (입력 범위 확장 효과)
B3   Multi-Agent (Scout·Auditor·Critic)     (역할 분리 효과)
B3'  B3 + Evidence Gate + Tool Validation    (오탐 감소·근거 품질)
```

→ 실행 시 `RunRecord.condition`에 `B1@2x2` / `B1@pipeline`로 **어느 축인지** 명시.

### 비교 규칙 (중요)

1. 모든 조건 **동일 예산**(토큰·GPU-second 상한).
2. 조건 차이는 **프로필·단계 활성화만.** retrieval·프롬프트·데이터셋은 고정.
3. 같은 조건 **seed 바꿔 최소 3회**, 분산 함께 보고.
4. **런타임(docker/podman) 다른 run은 같은 비교 셀에 안 넣음.**
5. **장비(atom/seraph) 다른 run도 같은 셀에 안 넣음.**

### 지표 (`docs/evaluation.md` §5)

```
성능:  단계별 후보 제거율 (Scout/Gate/Critic/ToolValidation 각 통과율)
       precision·recall (finding)
비용:  input/output/cached 토큰 (분리 기록)
       ★ validated finding당 GPU-hour = 핵심 비용 지표
         (분자에 컨테이너 도구 시간 제외 — semgrep·clang은 GPU 안 씀 → Budget.tool_seconds가 따로)
       검색(embedding·reranker) 토큰·GPU-second = model_call과 분리 집계
재현성: 동일 조건 재실행 diff
```

## 3. 아키텍처 — 파이프라인 10단계 (`src/orchestrator/nodes/`)

```
# 단계          입력              처리                          출력           통과 조건
0 preprocess   repo/펌웨어/크래시  binwalk·file, artifact hash    Artifact[]     파일 타입 분류
1 index        Artifact[]         소스→Joern(AST/CFG/PDG/CPG)     Code Index,     대상 심볼 해석
                                  바이너리/펌웨어→Ghidra(미구현)   Graph
                                  ·call graph                    Graph
2 signals      Artifact,Index     semgrep·clang-tidy·sanitizer   Evidence[]     실패해도 진행
                                  ·diff 파싱                                    (신호 부재로 기록)
3 retrieval    후보 seed          광역 수집→embedding→reranker    ContextCapsule 캡슐 토큰 상한 내
4 scout        Capsule(light)     후보 우선순위·CWE 추정          Candidate[]    score>=scout_threshold
5 auditor      Capsule(expanded)  source→sink, lifetime, guard   Finding(draft) Evidence Gate
                +Candidate         분석, RCA 초안                  +MissingEvidence
6 gate         Finding+Evidence   결정론적 근거 판정 (E0~E4)      승격/보류/폐기  근거 등급 (§4)
7 critic       상위 Finding만      다른 계열 모델로 반박           Decision       반박 기각 시
8 sandbox      Finding+재현명세    build·sanitizer·fuzz·PoC(도커)  Evidence(로그) 재현 성공→proven
9 report       Finding[]          규칙 기반 dedupe → 템플릿        리포트         —
```

**Queue 규칙:** 4·6단계 탈락 후보는 **버리지 않고 `queued`.** 새 Evidence 오면 그 후보만 재평가.

> **1단계는 입력 종류로 갈린다.** 소스 코드 → **Joern**(AST/CFG/PDG/CPG, 전처리 실험 §13이
> 실제 쓰는 것). 바이너리/펌웨어 → **Ghidra**(역컴파일) — **아직 미구현**, 지금 입력이 전부
> C 소스라 안 켜짐(펌웨어는 킥오프 대상이나 순서 미정, open-question D9). 저장소 스캐폴드엔
> tree-sitter 인덱서(`tools/harness-tools/indexer.py`)도 있으나 그래프 표현은 Joern 기반.

### 쉽게 풀면 — "취약점 후보가 관문을 통과하는 과정"

수많은 코드에서 진짜 취약점만 남기는 **깔때기**다. 뒤로 갈수록 후보는 줄고, 검증은 엄격해진다.

```
0 preprocess  재료 손질.       입력을 풀고 "이건 소스, 저건 바이너리" 분류 + 지문 붙임
1 index       코드 지도 그리기. 함수·변수가 어디 있고 누가 누구를 부르는지(call graph) 뽑음
2 signals     금속탐지기 훑기.  semgrep·clang 같은 도구로 "여기 수상함" 삑삑 표시
3 retrieval   서류철 준비.      판단에 필요한 코드 조각만 골라 캡슐로 묶음 (전부 안 줌)
4 scout       1차 서류심사.     작은 모델이 빠르게 훑어 "볼 만함 / 아님"만 분류 (판정 X)
5 auditor     본 조사.          큰 모델이 깊이 판다 — 입력이 어디서 와(source) 위험 연산(sink)까지
                               어떻게 가나 재구성
6 gate        증거 심사.        규칙으로 근거 충분한지 판정. "모델 주장만"이면 대기(E0),
                               도구·그래프가 뒷받침하면 통과(E2~)
7 critic      반대편 변호사.    다른 회사 모델이 "이거 틀렸다"고 반박 시도. 못 깨면 살아남음
8 sandbox     실험으로 증명.    실제로 빌드·실행해 진짜 터지는지 확인(크래시·PoC) → proven
9 report      판결문 작성.      중복 정리하고 리포트 생성
```

**핵심 두 가지:** ① 작은 모델(scout)로 많이 거르고 **비싼 모델(auditor·critic)은 살아남은 것만** —
비용 절약. ② **모델이 "취약하다"고 말한다고 끝이 아니라, 도구·재현(6·8단계)으로 뒷받침돼야** 승격.

## 4. 근거 등급 E0~E4 + Finding 상태 머신

### 근거 등급 (Evidence Gate 판정 — `enums.EvidenceGrade`)

| 등급   | 조건                                                            | 승격 결과                  |
| ------ | --------------------------------------------------------------- | -------------------------- |
| **E0** | 모델 주장만 존재                                                | `queued` (폐기 아님, 대기) |
| **E1** | 정적분석 신호 또는 코드 경로가 후보와 일치                      | `hypothesized` 유지        |
| **E2** | source→sink 경로가 call graph로 확인 + guard 부재가 코드로 확인 | **Critic으로 승격**        |
| **E3** | Critic이 반박 실패 + 재현 명세 존재                             | `validated`                |
| **E4** | sanitizer/crash/PoC 재현 로그 존재                              | `proven`                   |

**핵심:** 모델이 "취약하다"고만 하면 E0 → 대기. **도구·그래프로 뒷받침돼야** 위로 간다.

### Finding 상태 머신 (`src/orchestrator/state_machine.py`)

```
candidate ─scout pass→ triaged ─auditor→ hypothesized
                                             │ evidence gate
                        ┌──insufficient──────┤
                        ▼                    ▼ sufficient(E2)
                     queued  ←rebutted─  critic review
                        │                    │ upheld+재현명세(E3)
                        │                    ▼
                        │                 validated
                        │                    │ tool 재현 성공(E4)
                        │                    ▼
                        │                  proven → reported (2인 검증 후)
                        └──new evidence──→ candidate/hypothesized (재평가)
```

- `queued`에서 새 Evidence 오면 **처음부터** 게이트를 다시 통과(건너뛰기 금지). 상한 `requeue_max`.

## 5. 역할과 모델 — 누가 어떤 모델을 쓰나

### 역할 5개 (`Role`) + 그 성격

```
scout      트리아지. 많은 후보를 저비용으로 거른다. Light 캡슐(4K), 판정 안 함(likely/unlikely)
auditor    본 분석. source→sink·lifetime. Expanded 캡슐(24K), 토큰 예산 큼
critic     반박. 다른 계열 모델(오류 상관 낮아야 교차검증 의미). 상위 후보만
embedding  검색 top_k (판정·스키마 없음 → Role 아닌 하위 protocol)
reranker   검색 top_n 재선별 (상동)
```

## 11. 재현성 · 관찰가능성

**RunRecord 필수 기록 (하나라도 빠지면 비교표 제외):**

```
repo commit + source hash / model·tokenizer·quant checksum / prompt·spec version /
tool image digest + 런타임 / budget + threshold / seed + sampling / KB 스냅샷 / device
```

## 13. 전처리 실험 (윤경님 주도) — ⚠️ 하네스와 별개의 통제 실험

**목적:** "코드를 어떤 형식으로 전처리해 모델에 주면 취약점을 제일 잘 잡나"를 비교. **하네스
전체 파이프라인이 아니라, 단일 모델에 형식만 바꿔 넣는 통제 실험**이다(그래서 레빈님이
"하네스 설계와 다르다"고 지적).

**비교하는 7가지 표현 형식:**
```
raw · ast · cfg · pdg · cpg · ast+pdg · ast+cfg
```

| 형식 | 정식 이름 | 무엇을 담나 | 취약점 분석에 | 부피 |
| --- | --- | --- | --- | --- |
| **raw** | 원본 소스 | C 코드 그대로 | LLM이 제일 잘 읽음. 단 함수 넘는 흐름은 스스로 추론 | 가장 작음 |
| **ast** | Abstract Syntax Tree | 코드의 **문법 구조**를 트리로(함수·문·식·연산자 계층). "무엇이 쓰였나" | 구조 명확, 흐름·의존 정보 없음 | 중 |
| **cfg** | Control Flow Graph | **실행이 어디로 흐르나** — basic block들이 if·loop·goto로 이어짐 | 도달성(reachability) 판단에 유용 | 중 |
| **pdg** | Program Dependence Graph | **무엇이 무엇에 의존하나** — 데이터 의존(DDG: 값 정의→사용) + 제어 의존(CDG: 문↔분기) | ★ **source→sink taint·backward slice의 기반** | 중~대 |
| **cpg** | Code Property Graph | **AST+CFG+PDG를 하나로 합친** 슈퍼그래프(Joern 대표 표현) | 정보 제일 풍부 but **제일 큼**(2MB) → 큰 샘플 제외 원인 | 가장 큼 |
| **ast+pdg** | — | 구문 구조 + 의존 관계 | 구조와 taint를 함께 | 대 |
| **ast+cfg** | — | 구문 구조 + 제어 흐름 | 구조와 실행 경로를 함께 | 대 |

> **한 줄 직관:** raw=코드 그대로 / AST=문법 뼈대 / CFG=실행 경로 / PDG=의존 관계(taint) /
> CPG=셋 다 합침. 취약점(source→sink)엔 **PDG가 핵심**이고, CPG는 다 담지만 너무 커서 slicing이 필요.

전부 **"통째" 표현**이라 부피가 큼 — CPG는 10KB 소스가 2MB로 폭발. 그래서 압축한다.

**압축 (≠ slicing):** 그래프 전체를 유지하되 부피만 줄임 — 노드 ID 짧게, HTML 디코드, `<operator>`→`op.`,
DOT 문법·부모코드 중복·Joern 내부 연산자 그래프 제거, PDG 엣지 라벨 묶기. **손실 있음**(연결 일부 깨짐).

**1차 실험 대상 = 6개** (모든 형식이 압축 후 32K에 드는 것만): PWN-002·003·004·005·009·010.
**PWN-001·006·007·008은 압축 후에도 초과라 제외** (cpg가 56K~128K 토큰).

**모델·서빙:** `qwen3-8b`(기본) / `foundation-sec`(Foundation-Sec-1.1-8B-Instruct, 64K지만 변수
통제 위해 32K 고정) / `qwen3-4b`. bf16, util 0.25, `--max-model-len 32768`, seed 42, prefix-caching.

**프롬프트 (예준님, Single-Pass Auditor):** sink-first backward trace(Rule 1), 자기반박, source·sink
경로 세우기, E-밴드식 confidence(0.1–0.3 막힘 / 0.4–0.6 모름 / 0.7–1.0 트리거). **입력이 raw든
slice든 받게 설계됨** — slice에 없는 링크는 `missing_evidence`로 요청.

**실행:** `python run.py <샘플> <형식> --model <모델>` (프롬프트 자동 주입, vLLM 모델과 일치해야 함).
결과 → `~/experiments/preprocessing/results/<모델>/*.json`. 도구: Joern(jdk21), `~/experiments/preprocessing/`.

**평가 4요소:** ① 취약 함수 적중(path.symbol에 정답 함수) ② 경로 완성도(source·sink 둘 다) ③ CWE 일치 ④ verdict 적절성(취약 샘플이라 `vulnerable`이 정답, `need_evidence`는 부분점).

### slicing이 들어갈 자리 (레빈님 지적의 실체)

**압축은 "통째 그래프의 부피"만 줄인다 — slicing은 "관련 부분만 선택"이라 다른 축.** sink에서
backward slice하면 제외된 큰 샘플(PWN-006·008)도 32K에 들어온다. **"sliced-pdg"를 8번째 형식으로
추가**하는 게 자연스러운 다음 수:
```
seed = 정답 위치(누출!) 말고 → dangerous-func 호출부 전부(semgrep) 에서 각각 slice
slice = sink backward + control edge(guard 포함, 안 그러면 오탐) + chop(source→sink)
표현 = CPG 덤프 말고 "슬라이스된 소스"를 줌 (LLM은 그래프보다 코드를 잘 읽음)
```
방향이 같은 사람들: 민규님(slicing) · 서영채님(CPG 슬라이싱) · 레빈님(seed만 주기/auditor 모델).
