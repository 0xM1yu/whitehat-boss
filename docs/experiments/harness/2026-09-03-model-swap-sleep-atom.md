# 모델 교대 — 잠재우기가 51 GiB를 반환한다. 그리고 `nvidia-smi`가 값을 준다

> **갱신 (2026-09-09) — 본문은 그대로 두고 §7-5가 든 근거가 바뀐 것만 덧붙인다.**
> 후속 과제 5번이 배선이 없는 근거로 *"`execution.mode`·`swap` 키가 스키마에 없고
> `extra="forbid"`라 프로필이 로드 단계에서 거부된다"*를 든다. **그 근거는 없어졌다** —
> 2026-09-09에 `ProfileEntry.execution`(`ExecutionPolicy`·`SwapPolicy`)이 들어와 두 키를
> 적으면 로드는 통과한다([ADR 0009](../../decisions/0009-stage-unit-execution-and-model-swap.md)
> 결과 1 · `src/config.py`).
>
> **관측도 5번의 결론도 그대로다.** 이 실험이 답한 것은 *"장비가 되는가"*이고 *"하네스가 할 수
> 있는가"*는 여전히 아니오다 — 러너가 아직 단계 단위가 아니고 sleep/wake를 부르는 코드도 없다
> (같은 ADR 결과 2·3, 각각 별도 PR). **바뀐 것은 결론이 아니라 그 결론이 서 있는 이유다**
> (CLAUDE.md §2.3). 지금 상태를 현재형으로 적는 자리는 [build-plan.md](../../build-plan.md)
> §1 정정 6과 §7이다.

[build-plan.md](../../build-plan.md) §8 실행 순서 **6번**(모델 교대 확인)이고, §9 미확인 항목의
「통합메모리에서 잠재우기가 실제로 메모리를 반환하는가」다. ⚠ 1·2·6번이 끝나기 전에는
7번(코드 작성)에 들어가지 않는다는 그 표의 마지막 미완 행이었다.

**교대는 된다. 잠재우기가 51 GiB를 호스트 풀에 반환하고, 왕복이 2~6초다** — 콜드 스타트
238초의 약 1/50이다.

**그리고 §7의 전제가 하나 반증됐다.** build-plan이 *"가중치를 CPU로 내리는 방식은 장부상
아무것도 반환하지 않는다"*고 적었는데, **level 1이 level 2와 구별되지 않는다** — 세 계측기가
전부 같은 값을 낸다.

**부수로 더 큰 것이 나왔다: `nvidia-smi --query-compute-apps`가 이 장비에서 작동한다.**
`[N/A]`를 내는 것은 `--query-gpu` 쪽이다. `mem_gb_ctx8k`가 registry 전체에서 0인 근거가
그 문장이었다.

## 2. 계측기를 먼저 정한 이유와 그 검증

기존 두 후보가 다 막혀 있었다. cgroup은 *"CUDA 통합메모리는 cgroup에 계상되지 않는다"*가
2026-08-28에 확정됐고([README.md](../README.md) 미확정 #1의 답), `nvidia-smi`는 저장소가
`[N/A]`라고 적어 뒀다. 그래서 **vLLM이 기동 로그에 `Free memory on device`를 찍는 근거**인
`torch.cuda.mem_get_info()`를 직접 부르기로 했다.

**그 계측기를 세 갈래로 검증했다** (서버 1부, `--gpu-memory-utilization 0.45`):

| 출처 | 값 |
| --- | --: |
| `cuda.mem_get_info` 차분 (`F0 60.69` → `F1 5.97`) | 54.72 GiB |
| `nvidia-smi --query-compute-apps` | 52.79 GiB (54,060 MiB) |
| vLLM 요청 (`0.45 × 119.7`) | 53.86 GiB |

**3.6% 안에 셋이 모인다.** 이 일치가 아래 모든 수치의 근거다.

### 2.1 기준선이 한 번 반증 조건을 밟았고, 그것이 페이지 캐시였다

아무것도 안 떠 있는 상태의 `F0`이 **60.69 GiB free**였다. 같은 장비에서 22분 전 탐침
기동 로그가 `Free memory on device (112.06/119.7 GiB)`를 냈으므로 **51 GiB가 설명되지
않았고**, 측정 전에 박아 둔 조건("111~119 밖이면 멈춘다")에 걸려 한 번 멈췄다.

`free -g`가 답을 줬다 — **`버퍼/캐시` 49~52 GiB.** 그날 모델 파일을 반복해 읽어(checksum
산출 2회 + `sha256sum -c` 2회 + 모델 로드) 페이지 캐시가 차 있었고, `cuda.mem_get_info()`의
free가 호스트 available을 따라간다. **상수였고**(`F2 63.36` → `F3 63.37`, 60초에 0.01 GiB)
**차분에서 상쇄된다.** 그래서 절대값이 아니라 상태 간 차이만 쓴다.

**실험을 끝내고 정리한 뒤 이 설명이 한 번 더 확인됐다.** 모든 프로세스를 내린 최종
상태에서 `버퍼/캐시`가 **49 → 26 GiB로 줄었고 free가 60.69 → 89.03으로 올랐다**
(감소 약 23, 증가 28.34). 같은 시점 `사용` 6 · `공유` 0 · `가용` 113이다. **free가
페이지 캐시와 반대로 움직인다는 것이 이 절의 주장이었고, 그 방향이 관측됐다.**
`공유`가 23 → 0인 것은 vLLM의 shm까지 반환됐다는 뜻이다.

## 3. 실험

### 3.1 1부 — 프로세스 종료가 반환하는가 (sleep 플래그 없음)

| 상태 | `cuda free` | `nvidia-smi` |
| --- | --: | --: |
| F0 (아무것도 없음) | 60.69 | — |
| F1 (가동) | 5.97 | 54,060 MiB |
| F2 (종료 후) | **63.36** | — |
| F3 (F2 + 60초) | 63.37 | — |

**`F2 ≥ F0`이고 드리프트가 없다 → 프로세스 종료는 온전히 반환한다.** `F2`가 `F0`보다
2.67 GiB 큰 것은 종료가 페이지 캐시 일부까지 놓아준 것으로 읽히지만 **확정하지 않았다** —
페이지 캐시 변동폭이 그 정도이므로 이 차이로는 못 가른다.

### 3.2 2부 — 잠재우기 (`--enable-sleep-mode` + `VLLM_SERVER_DEV_MODE=1`)

엔드포인트 실재를 먼저 확인했다 — `openapi.json`에 `/sleep` · `/wake_up` · `/is_sleeping`.

**소요 시간** (`is_sleeping` 폴링으로 상태 전이를 확인한 시각차):

| 전이 | 시각 | 소요 |
| --- | --- | --: |
| 콜드 스타트 | 14:18:48 → 14:22:46 | **238초** |
| L1 sleep | 14:31:03 → 14:31:09 | 6초 |
| L1 wake | 14:31:14 → 14:31:17 | **3초** |
| L2 sleep | 14:31:20 → 14:31:21 | 1초 |
| L2 wake | 14:31:25 → 14:31:27 | **2초** |

L2 wake 직후 `/v1/models`가 응답했다. **왕복 2~3초 대 콜드 238초다.**

### 3.3 세 계측기로 다시 — level 1과 level 2가 구별되지 않는다

1판에서 `L1 52.61` 대 `L2 58.33`으로 **5.72 GiB 차이**가 보였고, 가중치가 약 18.63 GiB
(09-02 로그의 `consumed memory`)인데 차이가 그보다 작아 **설명이 안 됐다.** 그래서 세
계측기를 같은 시점에 찍는 2판을 돌렸다.

| 상태 | `free -g` 사용 | 가용 | 버퍼/캐시 | 공유 | `nvidia-smi` | `cuda free` |
| --- | --: | --: | --: | --: | --: | --: |
| AWAKE (14:33:58) | 87 | 32 | 49 | 23 | 54,260 MiB | 7.27 |
| **L1 SLEEP** (14:34:01) | **36** | **83** | 49 | 23 | **2,382 MiB** | **58.72** |
| **L2 SLEEP** (14:34:11) | **36** | **83** | 49 | 23 | **2,382 MiB** | **58.89** |

**① 잠재우기는 풀 안에서 옮기는 것이 아니라 반환이다.** 호스트 `사용`이 87 → 36으로
**51 GiB 줄었다.** 통합메모리에서 GPU→CPU 오프로드라면 물리 풀은 그대로여야 하는데
그렇지 않다. `버퍼/캐시`(49)와 `공유`(23)는 세 상태에서 안 움직인다 — 줄어든 것이
페이지 캐시가 아니라는 뜻이다.

**② level 1과 level 2가 세 계측기 전부에서 같다.** `cuda free` 58.72 대 58.89(0.17 GiB)만
차이 나고 나머지 둘은 완전히 같다. **1판의 5.72 GiB는 실재하지 않았다** — L1 sleep 직후
(6초 전이 중 `is_sleeping`이 참으로 바뀐 직후)를 찍어 비동기 해제가 덜 끝난 시점이었다.

**⚠ 기전은 모른다.** 측정은 "같다"고 말하지만 **왜** level 1이 level 2만큼 반환하는지는
설명하지 못했다. 통합메모리에서 vLLM이 오프로드를 해제로 접는 것일 수 있고, 아닐 수도
있다. 그 문장은 §5에 미측정으로 남긴다.

### 3.4 `nvidia-smi`는 쿼리에 따라 갈린다

```
[compute-apps]  150314, 54716 MiB
[gpu memory]    [N/A], [N/A], [N/A]
```

`config/models.yaml`의 `qwen3-coder-30b-a3b` 주석과 [8/25 보고서](2026-08-25-serving-nvfp4-atom.md)
가 **`mem_gb_ctx8k`가 0인 근거**로 *"`nvidia-smi`가 이 장비에서 `[N/A]`를 낸다(GB10은
통합메모리라 별도 VRAM 카운터가 없다)"*를 든다. **그 문장이 참인 것은 `--query-gpu`에
대해서이고, `--query-compute-apps`는 프로세스별 정확한 값을 준다.**

이 실험 안에서 그 값이 `cuda.mem_get_info` 차분과 3.6% 안에서 일치했으므로 **쓸 수 있는
계측기다.** 다만 이것이 `mem_gb_ctx8k`의 정의(context 8K에서의 점유)를 바로 채우지는
않는다 — 그 값은 context를 8K로 고정한 측정이 따로 필요하다. **여는 것은 경로이지 값이
아니다.**

## 4. 막힌 것과 해결

| 벽 | 원인 | 해결 |
| --- | --- | --- |
| 첫 탐침이 `Free memory on device`를 못 찾았다 | 임베딩 모델(0.6B) 로그에는 그 문구가 그대로 안 나온다. 서버 자체는 정상 기동했다 | 탐침 방식을 버리고 `torch.cuda.mem_get_info()`를 직접 부른다 — 서버 기동 자체가 불필요해진다 |
| SSH 재접속 후 `torch`·`vllm`이 전부 `ModuleNotFoundError` | 새 세션에서 venv가 풀렸다. **09-02 §4의 `which vllm` 사고와 같은 계열** | 모든 명령 블록을 `source …/venv-probe/bin/activate`로 시작한다 |
| 백그라운드 `vllm serve`가 종료코드 127 | 위와 같은 원인(PATH에 `vllm` 없음) | 위와 같음 |
| `pgrep -af "vllm serve"`가 clean인데 메모리가 잡혀 있었다 | `VLLM::EngineCore`는 cmdline이 `vllm serve`가 아니라 그 패턴에 안 걸린다 | 정리·확인에 `EngineCore`를 함께 매칭한다 |
| sleep 엔드포인트가 `--help`에 안 보였다 | `vllm serve --help`를 `sleep`으로 걸러 0건이었다 | `EngineArgs.__dataclass_fields__`에 `enable_sleep_mode`가 실재한다. **`--help` 출력만 보고 단정하면 안 된다** |

## 6. 반증 조건

- **「잠재우기가 반환한다」가 반증되려면**: L1·L2 sleep 상태에서 `free -g`의 `사용`이
  AWAKE와 같으면 된다. **87 → 36으로 51 GiB 줄었다.**
- **「level 1과 level 2가 같다」가 반증되려면**: 세 계측기 중 하나라도 두 상태를
  유의하게 가르면 된다. `free -g`와 `nvidia-smi`는 **완전히 동일**했고 `cuda free`는
  0.17 GiB 차였다. **1판의 5.72 GiB 차이는 전이 중 측정이었다.**
- **「프로세스 종료가 반환한다」가 반증되려면**: `F2 < F0`이면 된다. `63.36 > 60.69`다.
- **「계측기가 vLLM 할당을 따라간다」가 반증되려면**: `cuda free` 차분이 vLLM의
  `--gpu-memory-utilization` 요청과 어긋나면 된다. 54.72 대 53.86으로 1.6% 차다.
- **측정 전에 박아 둔 조건이 한 번 걸렸고 그대로 멈췄다** — `F0`가 111~119 밖(60.69)이라
  진단부터 했다. 그 조건이 없었으면 페이지 캐시 오프셋을 모른 채 결론을 냈을 것이다.

## 7. 후속 과제

1. **build-plan §7의 「CPU로 내리면 아무것도 반환하지 않는다」를 고친다** — 이 PR에서 한다.
   §8 row 6과 §9의 해당 행도 같이 움직인다.
2. **`config/models.yaml`과 8/25 보고서의 `nvidia-smi` 서술을 고친다** — **이 PR에서 하지
   않는다.** `qwen3-coder-30b-a3b` 주석 블록을 열려 있는 재측정 PR이 이미 크게 고치고
   있어 같은 자리를 건드리면 충돌한다(CLAUDE.md §4.1). 그 PR이 머지된 뒤 별도로 간다.
3. **`mem_gb_ctx8k` 측정 절차를 세운다.** 경로는 열렸다(`--query-compute-apps`). 값은
   context 8K 고정 측정이 따로 필요하고, registry의 0이 여러 모델에 걸려 있다.
4. **재현 판을 돌린다.** §5의 첫 행이 이 보고서의 가장 큰 결손이다 — 상태별 한 점씩이다.
5. **교대를 하네스에 배선하는 것은 별개다.** `execution.mode`·`swap` 키가 스키마에 없고
   `extra="forbid"`라 프로필이 로드 단계에서 거부된다(build-plan §1 정정 6). 이 실험은
   "장비가 되는가"만 답했지 "하네스가 할 수 있는가"는 안 답했다.
