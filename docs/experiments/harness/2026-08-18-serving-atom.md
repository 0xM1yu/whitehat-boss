| 모델 벤치마크 (registry) | **성공** — 첫 실측값 기입, 측정 장비 귀속 포함 |

### 2.1 하드웨어 및 OS

| 항목 | 값 |
| --- | --- |
| 장비 | GIGABYTE AI TOP ATOM (NVIDIA DGX Spark 계열) |
| GPU | NVIDIA GB10 Grace Blackwell, compute capability **12.1 (sm_121)** |
| CPU | 20코어 Arm (Cortex-X925 ×10 + A725 ×10) |
| 메모리 | 128 GB 통합 LPDDR5x (구조상 별도 VRAM 없음) |
| 저장장치 | 4 TB NVMe (전용 파티션 1 TiB, PCIe Gen5) |
| OS | NVIDIA DGX OS 7.4.0 (Ubuntu 24.04, **ARM64**), 커널 6.11.0-1016-nvidia |
| 드라이버 | libcuda 580.95.05 |

**할당받은 자원 — 2026-08-19 cgroup 실측으로 정정.** 원 보고서는 "메모리 34 GiB, CPU 6코어
상당"으로 적었으나, 이는 멘토 안내값이고 시스템이 강제하는 값과 다릅니다.

`/sys/fs/cgroup/user.slice/user-1004.slice/` — **부모 slice에 걸려 있습니다. 말단 session
scope는 `max`라 그것만 보면 "제한 없음"으로 오판합니다.**

| 기준 | 값 | 성격 |
| --- | --- | --- |
| 팀 약속 (멘토 안내) | **34 GiB** | 시스템은 허용한다. 넘으면 약속 위반 |
| `memory.high` | 58 GiB (62,277,025,792) | 소프트. 넘으면 회수 압박(throttle) |
| `memory.max` | 64 GiB (68,719,476,736) | 하드. 넘으면 **OOM kill** |
| `cpu.max` | `max 100000` | **제한 없음.** nproc 20이 실제로 다 쓰인다 — "6코어 상당"은 강제되지 않는다 |

**제한 단위가 세션이 아니라 사용자(`user-1004`)입니다. 계정 공유라 팀 전체가 하나의
64 GiB를 나눠 씁니다.** 이 실험에서는 8001 하나만 띄웠으므로 다른 서버의 영향이 없었습니다.

### 2.2 소프트웨어

| 항목 | 값 |
| --- | --- |
| vLLM | **0.27.1** (venv: `/srv/tenants/user/venv-probe`, Python 3.12) |
| Docker | **29.2.1** / aarch64 / runc |
| 비교 대상 | Slurm 클러스터 (A2000, sm_86, x86_64), vLLM 0.19.1 |

### 2.3 실험 착수 전 정리한 사항 두 가지

**(a) Triton 빌드에 필요한 파이썬 개발 헤더**

vLLM 내부의 Triton이 CUDA 연동 모듈을 실행 시점에 컴파일하는데, 이때 파이썬 개발 헤더(`Python.h`)를 참조합니다. 최소 재현으로 확인했습니다.

```
$ gcc /tmp/t.c -I/usr/include/python3.12 -o /tmp/t
/tmp/t.c:1:10: fatal error: Python.h: 그런 파일이나 디렉터리가 없습니다
```

권한이 필요한 작업을 요청드리지 않고, 헤더 패키지를 사용자 영역에 전개한 뒤 `CPATH`로 지정하는 방식으로 처리했습니다. 현재 정상 동작하고 있습니다.

다만 이 방식은 셸 환경변수에 의존하므로 새 세션에서는 매번 설정이 필요하고 실행 기록에도 남지 않습니다. 재현성 확보 측면에서 `python3.12-dev` 패키지가 설치되어 있으면 더 깔끔하겠으나, **급한 사안은 아니며 현재 방식으로도 실험 진행에 지장이 없습니다.**

**(b) 네트워크 인터페이스 선택 (기존 확인 사항, 해소 검증 완료)**

vLLM은 단일 GPU 실행에서도 torch.distributed의 TCPStore를 생성하는데, 다중 인터페이스 환경에서 자기 주소를 선택하는 과정이 있습니다. 이전에 확인된 사항이며, 실행 스크립트가 loopback을 명시하도록 저희 쪽에서 수정해 둔 것이 이번에 처음 실전 검증되었고 정상 동작을 확인했습니다.

## 3. 실험 1 — vLLM `/metrics` 프로브

### 3.1 목적

Slurm 클러스터와 ATOM 두 장비에서 **동일한 절차**로 vLLM 메트릭 원문을 수집하여, 두 장비의 차이가 순수하게 vLLM 버전 차이로 분리되는지 확인합니다. 성능 측정이 아니라 **"이 서버가 저희가 읽는 이름으로 저희가 읽는 값을 내주는가"**를 판정하는 실험입니다.

### 3.2 조건

- 모델: Qwen3-0.6B (양 장비 통일)
- 요청 6회, prefix 240토큰 목표
- `--enable-prefix-caching`, `--gpu-memory-utilization 0.2`

### 3.3 결과

| 항목 | 결과 |
| --- | --- |
| 요청 성공 | **6/6** |
| 부재 메트릭 | **`vllm:prompt_tokens_recomputed_total` 1건** |
| prefix cache | `enable_prefix_caching=True`, 해시 알고리즘 sha256 |
| 카운터 구간 | queries 1,314 / hits 960 / **적중률 73.06%** |
| 캐시 토큰 | `prompt_tokens_cached_delta` = 960 |
| 응답 캐시 장부 | `prompt_tokens_details` = **None** |
| KV cache 크기 | `kv_cache_memory_bytes` = **None** |
| KV cache 블록 | `num_gpu_blocks` 12,519 × `block_size` 16 = **200,304 토큰** |

### 3.4 해석

**(a) 메트릭 이름이 vLLM 버전 간 달라졌습니다.** 부재 항목 1건은 이 프로브가 확인하려던 신호에 해당합니다. 확보한 원문을 테스트 fixture로 반영하면 CI가 해당 이름의 부재를 검출하게 되며, 그 시점에 **버전별 이름 매핑**을 도입할 근거가 확보됩니다. Slurm 클러스터는 드라이버 사정으로 vLLM 0.19.1이 상한이고 ATOM은 0.27.1이므로, 버전 간극을 고려하면 예상 범위의 결과입니다.

**(b) prefix cache 카운터 값이 두 장비에서 다릅니다.** Slurm 클러스터 원문은 queries 1,458(= 243 × 6)이었으나 ATOM은 1,314입니다. 같은 모델·같은 요청 수임에도 블록 회계 방식이 다르므로, 두 원문을 직접 대조할 때 이 차이를 먼저 설명해야 합니다.

**(c) 캐시 적중이 응답이 아닌 메트릭 쪽에 있습니다.** 응답의 `prompt_tokens_details`는 `None`이지만 `/metrics`는 캐시된 토큰 960을 보고합니다. 즉 기존에 "서버가 캐시 장부를 주지 않는다"로 정리했던 항목은 **"응답 대신 메트릭에서 읽으면 된다"**로 성격이 바뀝니다. 이 현상은 이후 4B 실서빙 모델에서도 동일하게 재현되어, 모델 크기와 무관함이 확인되었습니다.

### 3.5 산출물

```
vllm_0271_atom_sm121.txt                    (메트릭 원문 — fixture)
vllm_0271_atom_sm121_chat_completion.json   (응답 원문 — fixture)
vllm_0271_atom_sm121.probe.json             (판정 요약)
```

## 4. 실험 2 — Docker 도구 이미지 빌드 및 검증

### 4.1 목적

파이프라인 2단계(정적 신호 수집)와 8단계(도구 검증)가 사용하는 컨테이너 이미지를 ATOM에서 **네이티브 빌드**하고, 실제로 취약/정상 표본을 분류하는지 확인합니다. 기존 이미지는 x86 빌드라 aarch64에서 사용할 수 없어 재빌드가 필요했습니다.

### 4.2 결과

| 항목 | 결과 |
| --- | --- |
| 빌드 (1차) | 중단 — GitHub HTTP 500 (외부 룰셋 저장소 일시 오류) |
| 빌드 (재시도) | **성공** — aarch64 네이티브 |
| 이미지 digest | manifest list `sha256:b5d7048b…` / config `sha256:b64ecf81…` |
| semgrep 룰셋 커밋 | `40b8c63f75dc7c22c8a77482d73bfb864b146f7e` |
| 빌드 시점 검사 | clang ASAN/UBSAN 컴파일·실행, clang-tidy, semgrep 룰셋 로드 **전부 통과** |
| 인덱서 검사 | tree-sitter가 심볼 2개·호출 1개를 실제로 추출 **통과** |
| 컨테이너 테스트 | `tests/test_container_tools.py` **39건 통과** (실컨테이너 분류 테스트 포함) |
| 파이프라인 실행 | `dev_docker` 프로필 **완주** (후보 2건 / Finding 2건) |

1차 중단은 GitHub 측 일시 오류였고 재시도로 해소되었습니다.

### 4.3 해석

**(a) aarch64 패키지 가용성이 검증되었습니다.** 이미지 빌드 시점 검사가 tree-sitter 파서와 semgrep의 arm64 실행 가능 여부를 함께 확인하므로, 빌드 성공 자체가 검증에 해당합니다.

**(b) 도구 이미지 기록이 처음으로 채워졌습니다.** 이 실행은 `tool_images` 필드가 비어 있다는 경고가 사라진 첫 run이며, 해당 항목은 모델 비교표 편입 조건 중 하나입니다.

**(c) 이미지 digest의 종류가 이전 기록과 다릅니다.** Docker 29.x는 레지스트리 push 없이도 `RepoDigests`를 채우며 그 값이 manifest list digest입니다. 기존 기록(2026-08-13)은 config digest 계열이므로 `tool_images` 필드에 성격이 다른 두 종류의 sha256이 혼재하게 됩니다. 저희 문서의 관련 서술을 정정하겠습니다.

## 5. 실험 3 — fp8 실서빙 모델 기동

### 5.1 대상

`Qwen/Qwen3-4B-Instruct-2507-FP8` (revision `8591804019c8b22094c3b5b4454e0edc05dffc98`)

thinking 계열이 아닌 Instruct 계열을 선택했습니다. 해당 역할(scout)은 JSON 스키마 준수가 강제되는 자리인데, 추론 토큰을 생성하는 계열은 응답 형식 강제와 충돌할 수 있고 그 실패가 모델 성능 지표로 오집계될 여지가 있기 때문입니다.

### 5.2 결과 — vLLM 기본 연산 백엔드에서의 동작

기본 설정에서는 가중치 로딩 후처리 단계에서 다음과 같이 중단되었습니다.

```
RuntimeError: Assertion error
  (/workspace/.deps/deepgemm-src/csrc/apis/layout.hpp:60): Unknown SF transformation
```

호출 경로:

```
vllm/model_executor/layers/quantization/fp8.py:434
  → kernels/linear/scaled_mm/deep_gemm.py:96
  → quantization/utils/fp8_utils.py:1137
  → utils/deep_gemm.py:494
```

vLLM이 fp8 연산 백엔드로 **DeepGEMM**을 선택하는데, 해당 라이브러리가 이 모델의 scale-factor 레이아웃을 sm_121에서 변환하지 못하는 구간입니다. GPU 연산이 시작되기 전, 가중치 준비 단계에서 발생합니다.

### 5.3 해결

`VLLM_USE_DEEP_GEMM=0`으로 cutlass/scaled_mm 경로를 사용하도록 설정하여 정상 기동을 확인했습니다.

```
Capturing CUDA graphs (FULL): 100%|██████████| 35/35
Graph capturing finished in 5 secs, took 0.79 GiB
init engine (profile, create kv cache, warmup model) took 29.27 s (compilation: 19.60 s)
INFO: Application startup complete.
```

**이 로그는 `--enforce-eager` 없이 나온 것입니다.** torch.compile이 19.60초 수행되고 CUDA
graph 35개가 잡혔으므로, eager 강제는 이 장비의 기동 조건이 아닙니다
([README.md](../README.md) 확정 #3).

### 5.4 해석 — 검증 범위와의 관계

장비 커널 호환성(R1)은 **bf16 Qwen3-0.6B 기동**으로 통과 판정된 항목이며, 계획 단계에서 **양자화 커널은 별도 검증 대상으로 범위를 분리**해 두었습니다. 이번 결과가 그 별도 항목의 첫 구체 사례에 해당합니다. 장비나 드라이버 사양의 문제가 아니라, vLLM이 새 아키텍처에서 어느 연산 라이브러리를 선택하는지에 관한 사안입니다.

저희 이식성 문서는 fp8을 "Ada(sm_89) 미만 세대에서 불가"로 기술하고 있는데, 이번 건은 **세대 요건은 충족하나 선택된 라이브러리가 레이아웃을 처리하지 못하는** 다른 방향의 조건이므로 별도 항목으로 반영했습니다.

**운영상 유의점**: 이후 측정한 처리량 수치는 모두 이 설정을 적용한 상태의 값입니다. 설정 없이 재측정하면 수치가 달라지는 것이 아니라 서버가 기동하지 않으므로, 모델 자체의 문제로 오진하기 쉽습니다. 해당 사실을 registry의 값 바로 옆에 주석으로 기록해 두었습니다.

## 6. 실험 4 — `gpu_memory_utilization` 기준 확정 및 설정값 산출

### 6.1 배경

통합메모리 구조에서는 별도 VRAM이 없어, 이 비율의 기준이 물리 메모리 전체인지 프로세스가 사용할 범위인지 확인이 필요했습니다. 팀 약속인 34 GiB 안에서 운용하려면 이 값을 먼저 확정해야 했습니다.

### 6.2 결과

vLLM이 기동 로그에 직접 출력했습니다.

```
Free memory on device (109.37/119.7 GiB) on startup.
Desired GPU memory utilization is (0.2, 23.94 GiB).
```

0.2 × 119.7 = 23.94이므로 **기준은 물리 통합메모리 전체(119.7 GiB)**입니다. 프로브 단계에서 `num_gpu_blocks`로 역산한 값과 일치했습니다.

**vLLM은 cgroup을 모릅니다 — 물리 메모리를 봅니다.** 그래서 이 분모와 §2.1의 cgroup 상한이
서로 다른 축이고, 설정값은 두 축을 함께 봐야 정해집니다.

| 설정값 | 요구 메모리 | 팀 약속 34 GiB | `memory.high` 58 GiB | `memory.max` 64 GiB |
| --- | --- | --- | --- | --- |
| **0.2 (채택)** | 23.94 GiB | 범위 내 (약 70%) | 여유 | 여유 |
| 0.3 | 35.9 GiB | **초과** | 여유 | 여유 |
| 0.6 (스크립트 초기 기본값) | 71.8 GiB | **초과** | **초과 — throttle** | **초과 — 즉시 OOM kill** |

**운용 목표는 첫 열입니다(34 GiB / util ≤ 0.25).** 커널이 64 GiB까지 허용해도 34가 약속입니다.
원 보고서가 0.3을 "범위 초과"로만 적은 것은 맞으나, 그것이 시스템 제약이라는 뜻은 아니었습니다 —
시스템은 0.48까지 허용하고 0.53에서 죽입니다.

스크립트의 초기 기본값 0.6은 Slurm 클러스터 기준으로 정해 둔 값이라, ATOM에서는 **0.2로 조정**하여 사용했습니다. **이 값은 즉시 OOM kill 구간입니다** — Slurm 클러스터 기준값을 그대로 가져오면 서버가 뜨지 않습니다.

### 6.3 메모리 사용 내역

```
weights + non-torch : 6.39 GiB
peak activation     : 0.73 GiB
CUDAGraph           : 0.79 GiB
KV cache            : 16.82 GiB
```

비-KV 점유는 **7.91 GiB**입니다.

### 6.4 해석 및 후속 계획

**(a) 두 장비의 설정값이 달라졌습니다.** 실험 절차상 양 장비가 같은 비율을 사용하도록 설계했으나, 통합메모리 구조 차이로 ATOM은 다른 값을 쓰게 됩니다. Slurm 클러스터 원문과 대조할 때 이 차이를 vLLM 버전 차이와 분리해 설명해야 합니다.

**(b) 비율 대신 절대값 고정으로 전환하려 합니다.** vLLM이 `--kv-cache-memory=<bytes>` 옵션을 제안하고 있으며(요청 메모리 기준 17,057,444,148 바이트 = 15.89 GiB), 바이트로 고정하면 기준값과 무관하게 두 장비에서 동일한 KV cache 크기를 재현할 수 있습니다. 장비 간 대조에는 이쪽이 더 정확하다고 판단하여 적용을 검토 중입니다.

**(c) 최대 컨텍스트 길이 하한이 있습니다.** 저희 파이프라인의 확장 캡슐 토큰 상한이 24,000이므로 `--max-model-len`을 8,192로 두면 해당 요청이 거부됩니다. 32,768 이상으로 설정했습니다.

## 7. 실험 5 — 모델 벤치마크 (registry 실측)

### 7.1 목적

모델 registry의 `benchmark` 항목이 전부 0(미측정) 상태였으며, 실측 체크리스트의 대상입니다.

### 7.2 결과

| 항목 | 값 |
| --- | --- |
| 단일 스트림 처리량 | **39.65 tok/s** |
| 배치 32 합산 처리량 | **127.69 tok/s** |
| 측정 장비 | `atom` (기록됨) |
| 측정 시각 | 2026-08-17T15:16:27Z |
| 모델 checksum | `sha256:ab78c8e5fc2b4f8f6972c3c19c6888a39a31642b11d857185ebbd14c03e5ff72` |
| 컨텍스트 8K/16K/32K KV 점유·처리량 | **통과** |
| structured output (JSON 스키마 강제) | **통과** |
| prefix caching 동작 | **통과** (장부 기록 방식은 후속 과제) |
| `mem_gb_ctx8k` (메모리 점유) | **미측정** |

두 차례 측정에서 39.7 → 39.65, 126.81 → 127.69로 변동폭 0.7% 이내였습니다.

### 7.3 해석

**(a) 구조화 출력이 동작합니다.** scout 역할은 JSON 스키마 준수가 강제되는 자리이므로, 이 항목의 통과는 **실모델 경로가 실제로 성립함**을 의미합니다. 스키마 파싱 실패율이 이제 측정 가능한 지표가 되었습니다.

**(b) `mem_gb_ctx8k`는 측정 방식을 바꿔야 합니다.** 저희 도구가 `nvidia-smi`의 `memory.used`를 참조하는데, 통합메모리 구조에서는 별도 VRAM이 없어 이 항목이 `[N/A]`로 표시됩니다.

```
$ nvidia-smi --query-gpu=name,compute_cap,memory.total,memory.used --format=csv,noheader
NVIDIA GB10, 12.1, [N/A], [N/A]
```

**값 자체는 확보 가능합니다.** §6.3에서 보시는 것처럼 vLLM 기동 로그가 비-KV 점유 7.91 GiB를 명시하고 있습니다. **저희 도구가 참조하는 소스를 바꾸면 되는 사안**이며, 후속 작업으로 정리하겠습니다. 값을 임의로 채우지 않고 사유와 함께 미측정으로 남기도록 도구가 정상 동작한 점은 확인했습니다.

**(c) production 승격 조건은 아직 충족되지 않았습니다.** 세 측정값 중 일부만 채워진 상태라 해당 프로필은 production으로 올라가지 않으며, 이를 막는 항목이 위 `mem_gb_ctx8k` 하나입니다.

### 7.4 모델 식별 절차

측정값의 재현을 위해 다음을 함께 기록했습니다.

| 항목 | 값 |
| --- | --- |
| 리포지터리·리비전 | `hf://Qwen/Qwen3-4B-Instruct-2507-FP8@8591804019c8b22094c3b5b4454e0edc05dffc98` |
| checksum 산출 대상 | 스냅샷 4.9 GB, 해시 파일 7개 (문서 파일 3개 제외) |
| manifest | `config/checksums/qwen3-4b.txt` — 스냅샷에서 `sha256sum -c` 전량 성공 |

서버는 리포지터리 이름이 아니라 **checksum을 산출한 스냅샷 경로**로 기동하여, `/v1/models`의 `root` 필드가 해당 경로를 가리키는 것을 확인했습니다. registry의 checksum과 실제 서빙 대상이 일치함을 보장하기 위한 절차입니다.

## 9. 실험 7 — GPU 사용 시간 회계 실측 (하네스 결함)

### 9.1 배경

비용 지표 중 "Finding당 GPU-hour"의 분자에 해당하는 값이 모든 실행 기록에서 0 또는 비정상적으로 낮게 남아 있었습니다. 실제 계측을 수행했습니다.

### 9.2 결과

컨테이너 도구 실행 시간을 실측하여 저희 장부 기록값과 대조했습니다.

| 실행 환경 | 실제 소요 | 장부 기록 | 손실률 | 0으로 기록된 호출 |
| --- | --- | --- | --- | --- |
| x86 | 8,492 ms | **3초** | 65% | 11건 중 8건 |
| **ATOM (aarch64)** | 4,491 ms | **0초** | **100%** | **11건 중 11건** |

또한 동일한 도구 11건을 동일한 순서로 실행한 세 차례 실행이 각각 3초 / 6초 / 8초를 기록했습니다. 실제 소요는 1.6배 차이였으나 장부는 2.7배 차이를 보였습니다.

### 9.3 원인 — 저희 코드 결함 세 가지

1. **모델 호출 경로에 계측 지점 자체가 없었습니다.** 반환 값 구조에 GPU 시간을 담을 필드가 존재하지 않아, 값을 전달하지 않은 것이 아니라 전달할 값이 없는 상태였습니다.
2. **검색·도구 경로가 밀리초를 초 단위로 버렸습니다.** 임베딩 호출은 통상 50~300 ms이므로 전량 0이 됩니다.
3. **GPU를 사용하지 않는 컨테이너 도구 시간이 GPU 예산에 청구되고 있었습니다.** 해당 도구들은 정적 분석기와 컴파일러입니다.

장비가 빠를수록 손실이 커지는 구조입니다. ATOM에서 100% 손실이 확인된 것은 장비 성능이 좋아 모든 도구 호출이 1초 미만에 끝났기 때문입니다.

### 9.4 조치

별도 PR로 수정하고 검증을 마쳤습니다. 회귀 테스트에 두 환경의 실측값을 그대로 반영했으며, 수정 이전 코드로 되돌렸을 때 해당 테스트가 실제로 실패하는지 확인했습니다. 부수적으로, GPU 사용 시간을 측정하지 못한 실행은 모델 비교표에서 자동 제외되도록 판정 로직을 추가했습니다.

## 10. 실험 8 — ARM64 회귀 검증

### 10.1 목적

전체 테스트 스위트가 x86에서만 실행되어 왔습니다. 회귀 테스트 일부가 aarch64 실측값을 단언하고 있고 주 실서빙 장비가 aarch64이므로, 해당 아키텍처에서의 검증이 필요했습니다.

### 10.2 결과

| 환경 | 결과 |
| --- | --- |
| x86 (Windows) | 470건 통과 / 3건 건너뜀 |
| **ARM64 (ATOM)** | **473건 통과 / 0건 건너뜀** (4.58초) |

### 10.3 해석

x86에서 건너뛴 3건이 ATOM에서는 전부 실행되어 통과했습니다. Docker 런타임이 실제로 존재해야 실행되는 테스트들입니다. **이번 검증이 x86보다 넓은 범위를 덮었으며, 아키텍처 특이 실패는 발견되지 않았습니다.**

다만 CI 러너가 x86인 경우 해당 3건은 CI에서 실행되지 않으므로 ATOM이 유일한 실행 환경이 됩니다. 확인 후 별도로 정리하겠습니다.

| `mem_gb_ctx8k` | `nvidia-smi memory.used`가 `[N/A]` — 통합메모리라 별도 VRAM이 없다 | 소스를 vLLM 기동 로그의 비-KV 점유(7.91 GiB)로 바꾼다. **production 승격을 막는 유일한 항목** |
| 배치 8·16 처리량 | registry 스키마에 자리가 없다 | 스키마에 자리를 만들거나 보고서에만 남긴다 |
| prefix cache 적중률 (bench 판정) | 프로브(§3)에서는 쟀으나 bench 경로에서는 미판정 | 읽는 소스를 응답 대신 `/metrics`로 바꾼다 (§3.4c) |
| NVFP4 Critic 반박 정확도 | bench 범위 밖 — 고정 반박 표본이 없다 | 데이터셋 확보 후 |
| `bench` stdout 원문 | **보존하지 않았다.** stdout으로만 나오는데 `tee`를 쓰지 않았다 | 다음 측정에서 `tee`로 파일에 받는다. 반복되면 코드로 옮긴다 |

**이 실험들이 실패했다면 무엇이 틀린 것이었나.** 성공만 적으면 그 성공이 무엇을 뜻하는지
알 수 없습니다.

| 실험 | 실패했다면 |
| --- | --- |
| §3 프로브 | 우리가 읽는 메트릭 이름이 이 서버 버전에 없다는 뜻. **성공했으므로 버전별 이름 매핑은 아직 불필요**하고, 부재 1건이 그 경계가 어디인지를 가리킨다 |
| §4 이미지 빌드 | tree-sitter 파서 또는 semgrep의 arm64 휠이 없다는 뜻. 빌드 시점 검사가 그 둘을 함께 확인하므로 **빌드 성공 자체가 가용성 검증**이다 |
| §5 fp8 기동 | (실제로 실패했다) 세대 요건(sm_89+)만 보는 우리 이식성 서술이 불완전하다는 뜻. **세대는 충족했는데 백엔드가 못 다뤘다** |
| §6 util 기준 | 분모가 물리 메모리가 아니라 프로세스 범위였다는 뜻. 로그가 직접 답해 산술로 확인됐다 |
| §8 실모델 파이프라인 | 실모델 Finding이 Fake와 같았다면 — **"실모델이 판정을 바꾼다"가 성립하지 않고** 제거율 지표의 분자가 여전히 0이었을 것이다 |
| §9 GPU 회계 | 장부와 실측이 일치했다면 하네스에 결함이 없다는 뜻이었다. **100% 손실이 나왔으므로 지표의 분자를 지금까지 못 쓰고 있었다** |
| §10 ARM64 회귀 | 아키텍처 특이 실패가 있다는 뜻. 0건이므로 x86 CI 결과를 aarch64에 적용해도 된다 — **단 Docker 의존 3건은 CI에서 안 돈다** |

### 14.1 B1 조건 모델 구성에 관한 사전 조사

B1 조건은 세 LLM 역할 전부를 단일 30B MoE 모델로 실행하도록 정의되어 있습니다. 해당 모델의 배포 형태를 사전 조사한 결과, **저희 registry가 상정해 둔 양자화 형식이 실제로는 공개 배포되지 않고 있음**을 확인했습니다.

| 형식 | vLLM 서빙 | 크기 | 비고 |
| --- | --- | --- | --- |
| NVFP4 | — | — | **registry에 상정해 둔 형식이나 공개 배포 미확인** |
| W4A16 / AWQ (4비트) | 가능 | 약 17 GB | 이 규모 모델에 표준적으로 사용되는 형식 |
| FP8 / W8A8 (8비트) | 가능 | 약 31 GB | 공식 배포 포함 |
| MLX / GGUF / MNN | 불가 | — | vLLM 미지원 형식 |

30B 규모에서는 **4비트 배포가 표준적으로 사용**되고 있어, 그쪽으로 구성을 조정하려 합니다. 8비트는 가중치만 약 29 GiB를 차지해 KV cache 여유가 크게 줄어들므로, 동시 요청 처리 측면에서도 4비트가 적합하다고 판단됩니다. (MoE 구조는 처리 속도에는 유리하나 전문가 전체가 메모리에 상주하므로 메모리 절감 효과는 없습니다.)

이에 따라 registry의 양자화 표기를 정정하고 관련 리스크 항목을 재정의할 예정입니다. 또한 4비트 MoE 커널이 sm_121에서 동작하는지는 §5 사례를 고려할 때 **별도 확인이 필요한 사항**으로 보고 있습니다.

## 16. 부록 — 재현 절차

```bash
# 환경
source /srv/tenants/user/venv-probe/bin/activate
export CPATH="$HOME/pyhdr/usr/include/python3.12:$HOME/pyhdr/usr/include:${CPATH:-}"

# 프로브
GPU_MEMORY_UTILIZATION=0.2 WAIT_S=900 tools/probe/atom.sh --port 8001 --out ~/probe

# 도구 이미지
docker build -t harness-tools:v1 tools/harness-tools/
docker run --rm harness-tools:v1 cat /opt/semgrep-rules/COMMIT

# 실서빙 (VLLM_USE_DEEP_GEMM=0 필요)
VLLM_USE_DEEP_GEMM=0 VLLM_HOST_IP=127.0.0.1 \
NCCL_SOCKET_IFNAME=lo GLOO_SOCKET_IFNAME=lo \
vllm serve <스냅샷 경로> --served-model-name qwen3-4b \
  --host 127.0.0.1 --port 8001 \
  --gpu-memory-utilization 0.2 --max-model-len 32768 --enable-prefix-caching

# 벤치마크 (--device 필요 — 생략 시 측정 장비가 기록되지 않습니다)
python -m src.cli bench --profile single_gpu_12g --device atom --apply
```

**재현 시 유의사항 네 가지**

1. `CPATH` 미설정 시 Triton 컴파일 단계에서 기동하지 않습니다.
2. `VLLM_USE_DEEP_GEMM=0` 미설정 시 fp8 모델이 기동하지 않습니다.
3. `--device` 미지정 시 벤치마크 결과에 측정 장비가 기록되지 않아, 어느 하드웨어의 수치인지 사후에 확인할 수 없습니다.
4. **`--gpu-memory-utilization`의 스크립트 초기 기본값 0.6은 이 장비에서 즉시 OOM kill 구간입니다**(71.8 GiB > `memory.max` 64 GiB). 반드시 0.2를 명시하십시오 (§6.2).
