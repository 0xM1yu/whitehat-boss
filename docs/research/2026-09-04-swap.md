# 모델 교대(swap) 조사 — 웹 출처와 저장소 실체

조사일 2026-09-04 · 대상 `origin/main` `b25e9d28`

> **출처 표기 규약.** 이 문서는 두 종류의 근거를 섞지 않는다.
> **[실측]** = 우리가 ATOM(GB10)에서 직접 잰 것. 원천은 저장소 안의 보고서다.
> **[웹]** = 외부 문서·소스·이슈. 링크를 그 자리에 단다.

## 0. 세 줄 요약

1. **장비는 된다** [실측]. 하지만 **하네스는 못 한다** — 클라이언트가 `build_deps()` 시점에
   전부 만들어져 run 내내 고정이고(`src/adapters/factory.py:291-295`), 교대를 끼울 수 있는
   훅 자리가 없다. 스키마도 `extra="forbid"`가 막는다(`src/schemas/common.py:62`).
2. **교대 비용의 지배 인자는 sleep/wake 지연이 아니라 「몇 번 교대하느냐」다.** 지금 러너는
   후보 단위로 scout→auditor를 왕복하므로(`src/orchestrator/runner.py:1080-1125`)
   `candidate_max: 256` 기준 **512회** 교대가 필요하다 [계산]. 단계 단위로 쪼개면 **3~5회**로
   떨어진다. 100배 차이가 여기서 난다 — 그래서 build-plan §8의 row 5(단계 단위 쪼개기)가
   row 6(교대)의 **선행 조건**이지 병렬 항목이 아니다.
3. **우리 실측에 아직 안 답한 구멍이 셋 있고, 셋 다 웹 출처가 위험하다고 말한다**:
   (a) L2 wake 뒤 `reload_weights`를 안 불렀다 [웹 요구사항], (b) wake 뒤 추론 처리량을
   안 쟀는데 CUDA graph 재캡처 여부에 대해 **vLLM 공식 출처 둘이 서로 모순**한다,
   (c) **DGX Spark(=GB10)에서 wake 크래시 이슈가 열려 있다**.

## 1. 웹 — vLLM sleep mode의 공식 계약

### 1.1 엔드포인트 계약

[vLLM 공식 문서 `features/sleep_mode`](https://docs.vllm.ai/en/latest/features/sleep_mode/)와
[GitHub 원문](https://github.com/vllm-project/vllm/blob/main/docs/features/sleep_mode.md)이
드는 curl 예시가 전부다 [웹]:

| 엔드포인트 | 메서드 | 파라미터 |
| --- | --- | --- |
| `/sleep` | POST | `?level=1` 또는 `?level=2` |
| `/wake_up` | POST | 없음, 또는 `?tags=weights` / `?tags=kv_cache` |
| `/is_sleeping` | GET | — (불리언 반환) |
| `/collective_rpc` | POST | JSON body `{"method":"reload_weights"}` |
| `/reset_prefix_cache` | POST | — |

**응답 본문 스키마는 문서에 없다** [웹] — 문서가 경로와 쿼리 파라미터만 적는다. 우리도
`openapi.json`에서 경로 실재만 확인했다 [실측, 보고서 §3.2]. 배선할 때 응답을 파싱해 판정하려
하지 말고 **`/is_sleeping` 폴링으로 상태 전이를 확인**하는 편이 안전하다 — 우리가 실제로 쓴
방법이 그것이다 [실측].

기동 조건은 **`--enable-sleep-mode` 플래그 + `VLLM_SERVER_DEV_MODE=1` 환경변수 둘 다**다 [웹].
우리 실측도 같다 [실측, 보고서 메타표].

> ⚠ `vllm serve --help`에 `sleep`이 안 걸린다 [실측, 보고서 §4]. `EngineArgs.__dataclass_fields__`에
> `enable_sleep_mode`가 실재한다. 이건 우리 관측이고 웹 출처가 아니다.

### 1.2 level 1 vs level 2 — 설계상의 차이

[공식 문서](https://docs.vllm.ai/en/latest/features/sleep_mode/) [웹]:

- **level 1** — *"offload the model weights and discard the KV cache. The content of KV cache is
  forgotten."* 가중치는 **CPU RAM에 백업**된다. 그래서 *"There must be enough CPU memory to
  store the model weights."*
- **level 2** — *"discard both the model weights and the KV cache (while the model's buffers are
  kept in CPU, like rope scaling tensors)."* RLHF 가중치 갱신처럼 **이전 가중치가 필요 없을 때**,
  또는 CPU 메모리가 모자랄 때.

기전은 [`vllm.device_allocator.cumem`](https://docs.vllm.ai/en/latest/api/vllm/device_allocator/cumem/)
가 답한다 [웹]. `CuMemAllocator`가 CUDA 가상 메모리 API(`cuMemCreate`/`cuMemRelease`)로
**가상 주소는 유지한 채 물리 페이지만 떼었다 붙인다.** 텐서에 태그(`"weights"` / `"kv_cache"`)를
달아 두고, `sleep(offload_tags=...)`에서 **태그가 맞는 것만 pinned CPU 메모리로 복사한 뒤**
물리 페이지를 해제한다. 나머지는 그냥 버린다. 즉 **level 1 = `offload_tags=("weights",)`,
level 2 = `offload_tags=()`** 라는 한 인자 차이다 [웹].

#### 우리 측정에서 구별이 안 된 이유 — 설명 못 한다. 가설 셋을 남긴다

[실측] 세 계측기 전부에서 L1과 L2가 같았다(`free -g` 사용 36/36 · `nvidia-smi` 2,382/2,382 MiB ·
`cuda free` 58.72/58.89). 보고서 §3.3이 *"⚠ 기전은 모른다"*로 유보한 그대로다.

**웹 출처를 붙여도 답이 안 나온다.** 위 기전대로면 L1은 가중치 ~18.63 GiB를 CPU pinned로
**옮기는** 것이라, 통합메모리(CPU·GPU가 같은 물리 풀)에서는 `free -g`의 `사용`이 그만큼
**덜 줄어야** 한다. 관측은 L2와 같은 51 GiB 감소였다. 후보는 셋이고 **어느 것도 확인 안 됐다**:

1. GB10에서 pinned host alloc이 `free -g`의 `사용`에 계상되지 않는다(회계 문제).
2. 이 빌드에서 L1의 offload 경로가 실질적으로 discard로 떨어진다(동작 문제).
3. 통합메모리에서 vLLM이 오프로드를 매핑 해제로 접는다(플랫폼 특수 경로).

**가르는 방법**은 두 가지다. (a) L1 wake와 L2 wake의 소요를 **여러 판** 재서 분포를 본다 —
[vLLM 블로그](https://vllm.ai/blog/2025-10-26-sleep-mode) [웹]는 L2 wake가 *"weight reloading
from disk storage"* 때문에 L1보다 **약 3배 느리다**고 적는다(A100: L1 0.26s/0.82s 대
L2 0.85s/2.58s). 우리 1점 측정은 **L2 wake 2초가 L1 wake 3초보다 빨랐다** [실측] — 상식과
반대다. (b) 비-통합메모리 장비에서 같은 절차를 돌려 대조한다(보고서 §5가 이미 적은 방법).

> **⚠ 우리 L2 측정은 완결된 wake가 아니다.** 공식 블로그가 명시한다 [웹]: *"you must call
> `reload_weights` and `reset_prefix_cache` after waking. Level 1 sleep doesn't require these
> extra steps."* 우리는 L2 wake 뒤 `/v1/models` 응답만 확인했고 `collective_rpc reload_weights`를
> **부르지 않았다** [실측, 보고서 §5 3행이 "추론을 안 돌렸다"고 적는다]. 즉 **"L2 wake 2초"는
> 쓸 수 있는 서버까지의 시간이 아니다.** 이 수치를 설계 근거로 쓰면 안 된다.

### 1.3 깨운 뒤 KV cache · prefix cache · CUDA graph

- **KV cache**: 두 레벨 모두 내용이 사라진다 [웹, 공식 문서 — *"The content of KV cache is
  forgotten"*]. 재구축 비용은 "다음 요청이 prefill을 다시 한다"는 형태로 나온다.
- **prefix cache**: L2는 wake 뒤 `/reset_prefix_cache`가 **필수**, L1은 불필요 [웹, 블로그].
- **CUDA graph** — **공식 출처 둘이 정면으로 모순한다. 이 문서는 어느 쪽도 채택하지 않는다.**

  | 출처 | 주장 |
  | --- | --- |
  | [vLLM 블로그(2025-10-26)](https://vllm.ai/blog/2025-10-26-sleep-mode) | Sleep Mode는 CUDA graph를 wake 사이클 사이에 **보존한다**. *"Compiled kernels were compiled during initial warmup and remain cached."* |
  | [RFC #34303 (CUDA Checkpoint/Restore)](https://github.com/vllm-project/vllm/issues/34303) | *"With sleep/wake-up, CUDA graphs must be re-captured after wake-up, which is expensive (~2-10s)."* 비교표에서 sleep/wake의 「CUDA graphs preserved」가 ❌ · 「torch.compile artifacts」 ❌ · 「CUDA streams/contexts」 ❌. 총 왕복 *"~6-32s (cumem mode)"* |

  **우리 실측이 이 모순을 가르지 못한다** — 왕복 2~6초는 RFC가 말하는 6~32초보다 훨씬 짧아
  블로그 쪽으로 읽히지만, **우리는 wake 뒤 추론을 안 돌렸다** [실측, 보고서 §5]. CUDA graph
  재캡처는 첫 추론 요청에서 드러나지 `/v1/models` 응답에서는 안 드러난다. **이걸 재기 전에는
  "왕복 3초"를 설계 예산으로 쓰면 안 된다.**

  → **가장 싼 반증 실험**: 깨운 직후 `cli bench`를 한 판 돌려 첫 요청 지연과 정상 상태
  tok/s를 콜드 기동 뒤 값과 대조한다. 보고서 §5가 이미 후속 과제로 적어 둔 그것이다.

### 1.4 알려진 제약·버그 — 우리 장비에 걸리는 것부터

> **우리 실측과 이 보고가 어긋난다.** 우리는 vLLM **0.27.1**에서 반환을 관측했고(호스트

### 1.5 `VLLM_SERVER_DEV_MODE=1`이 프로덕션에서 안전한가 — **아니다**

[공식 문서](https://docs.vllm.ai/en/latest/serving/online_serving/) [웹]: 이 플래그가 여는
엔드포인트는 `/sleep` · `/wake_up` · `/is_sleeping` · `/collective_rpc` · `/reset_prefix_cache` ·
`/reset_mm_cache` · `/reset_encoder_cache`이고, *"should only be exposed in trusted networks"* ·
*"should not be exposed to users"*라고 못박는다. 캐시 리셋 계열은 *"can disrupt service"*로
표시돼 있다.

**특히 `/collective_rpc`가 위험하다** — 임의 메서드 이름을 JSON으로 받아 워커에서 실행한다
(`{"method":"reload_weights"}`). 인증이 없다.

**우리 배치에서의 판정.** `config/models.yaml`의 엔드포인트가 전부 `http://127.0.0.1:800X/v1`이라
루프백 바인딩이다 — 우리 실측도 `--host 127.0.0.1`이었다 [실측, 보고서 메타표]. 즉 **지금
배치에서는 노출면이 그 호스트의 로컬 사용자로 한정된다.** 배선할 때 지킬 것:

1. `--host 127.0.0.1`을 유지한다. 0.0.0.0으로 바꾸는 순간 위 7개가 인증 없이 열린다.
2. **관리 엔드포인트를 `endpoint`와 같은 필드로 표현하지 않는다** — `/v1` 접미사가 붙는
   추론 경로와 관리 경로는 성격이 다르다(§6 제안 A가 별 필드를 두는 이유).
3. `RunRecord`에 「이 run은 dev mode 서버에 붙었다」가 남아야 한다 — `tool_runner`를
   막지 않고 기록하는 것과 같은 논법이다(`src/config.py:72-74` 주석의 그 원칙).

## 2. 웹 — 메모리 제약 아래 모델을 교대시키는 기존 패턴

### 2.1 vLLM production-stack — 있다. 다만 **수동이다**

[Sleep and Wakeup Mode 문서](https://docs.vllm.ai/projects/production-stack/en/latest/use_cases/sleep-wakeup-mode.html) [웹]:

- 라우터가 엔진 단위로 `GET /is_sleeping?id=` · `POST /sleep?id=` · `POST /wake_up?id=` ·
  `GET /engines`를 노출한다.
- 라우터는 **잠든 엔진으로 요청을 넘기지 않고** `"Model [name] not found or vLLM engine is
  sleeping"`을 돌려준다.
- 실측 수치를 문서가 든다: **wakeup 약 0.28초, sleep 5.75초, 39.26 GiB 반환** [웹].
- **자동 전환·LRU는 없다** — 문서에 스케줄링 정책이 없다. 즉 **"누가 언제 재우고 깨우는가"는
  여전히 호출자 몫이다.**

[Issue #391](https://github.com/vllm-project/production-stack/issues/391)이 V1 지원 요청 트래킹이다 [웹].

**우리에게**: 이게 사실상 우리가 만들려는 것의 상류판이다. **자동 정책이 없다는 것이 요점이다** —
그 정책이 곧 우리 파이프라인의 단계 순서이고, 그건 상류가 알 수 없는 정보다. 그러니 라우터를
가져다 쓰든 직접 짜든 **정책은 우리가 짜야 한다.**

### 2.2 llama-swap — 프로세스 교대 프록시. **설정 스키마가 우리에게 가장 참고할 만하다**

[Configuration wiki](https://github.com/mostlygeek/llama-swap/wiki/Configuration) [웹]. Go 단일
바이너리 리버스 프록시로, 요청의 `model` 필드를 보고 해당 백엔드 프로세스를 띄우고 유휴
인스턴스를 내린다.

최상위 키: `healthCheckTimeout`(기본 120s, 최소 15s) · `logLevel` · `metricsMaxInMemory` ·
`startPort` · `macros` · `models`(필수) · `groups`(선택) · `hooks`(`on_startup` 프리로드).

모델별: `cmd`(필수) · `name` · `description` · `env` · `proxy` · `aliases` · `checkEndpoint`
(기본 `/health`, `"none"`이면 생략) · `ttl`(초, 0이면 비활성) · `useModelName` ·
`filters.strip_params` · `concurrencyLimit` · `unlisted` · `cmdStop`.

**핵심은 `groups`다** [웹, 위 wiki 인용]:

| 키 | 의미 |
| --- | --- |
| `swap` | *"true: only one model is allowed to run at a time / false: all models can run together"* |
| `exclusive` | *"true: causes all other groups to unload when this group runs a model"* |
| `persistent` | *"prevents other groups from unloading the models in this group"* |
| `members` | 모델 ID 배열 (필수) |

**이 네 키가 우리가 표현해야 할 것과 정확히 겹친다** — 「임베딩·리랭커는 상주(`persistent`),
Scout·Auditor·Critic은 한 번에 하나(`swap: true`)」가 그대로 나온다. §6 제안 A의 스키마가
여기서 왔다.

⚠ **llama-swap은 llama.cpp/vLLM **프로세스**를 죽였다 살린다** — 우리가 쓰려는 sleep/wake와
성격이 다르다. 프로세스 재기동은 우리 실측 기준 **238초**이고 [실측] sleep 왕복은 그 1/50이다.
**스키마는 참고하되 기전은 가져오지 않는다.**

### 2.3 llama.cpp 본체의 router mode — LRU가 상류에 들어왔다

[HuggingFace 블로그 "Model Management in llama.cpp"](https://huggingface.co/blog/ggml-org/model-management-in-llamacpp) [웹]:
`--models-dir`로 GGUF 디렉터리를 주고 요청의 `model` 필드로 라우팅한다. **`--models-max`
기본값 4, 초과하면 LRU 축출** [웹].

⚠ **알려진 결함**: [Issue #20137](https://github.com/ggml-org/llama.cpp/issues/20137) —
*"`--models-max` not enforced under concurrent requests (TOCTOU race in unload_lru)"*.
`--models-max 2`인데 동시 요청으로 3개 이상이 로드된다 [웹].

**우리에게**: LRU를 우리가 짤 때 밟을 자리를 상류가 먼저 밟아 줬다. **동시 요청 아래의
축출 결정은 락이 필요하다.** 그리고 Scout 3개 동시 실행이 정확히 그 조건이다.

### 2.4 Ray Serve `@serve.multiplexed` — LRU가 API에 박혀 있다

[Model Multiplexing 문서](https://docs.ray.io/en/latest/serve/model-multiplexing.html) [웹]:
`max_num_models_per_replica`(**기본 3**)를 넘으면 **LRU로 축출**. 축출 시 자원 해제는
`__del__` 구현으로 한다. 라우팅은 요청 헤더의 모델 ID를 보고 **이미 그 모델을 가진 레플리카로
보낸다**.

**우리에게**: 「몇 개까지 상주」를 **정수 하나**로 표현하는 설계 선례다. 우리 `swap` 스키마에
`max_resident: int`를 둘지 말지의 근거가 된다 — 다만 우리 모델들은 크기가 제각각(0.6B~30B)이라
**개수보다 GiB가 맞는 축**일 수 있다. 그건 우리가 정할 일이지 선례가 답하지 않는다.

### 2.5 KServe — 다른 층위의 답

[Model Cache 문서](https://kserve.github.io/website/docs/model-serving/generative-inference/modelcache/localmodel) [웹]:
가중치를 **노드 로컬 볼륨에 캐시**해 다음 파드가 다운로드를 건너뛴다. Serverless 모드에서
Knative Activator가 요청을 버퍼링하며 scale-to-zero를 한다 [웹].

**우리에게 안 맞는다.** 우리 병목은 다운로드가 아니라 **로드+프로파일+그래프 캡처 238초**이고
[실측], 파드 단위 스케일은 우리가 프로세스 하나짜리 단일 노드라 의미가 없다. **다만 한 가지는
가져올 만하다** — KServe가 파드 격리로 얻는 것(모델 하나가 죽어도 나머지가 산다)을 우리는
**서버 프로세스 분리**로 이미 갖고 있다. 한 프로세스에 여러 모델을 올리는 방향으로 가면 그걸
잃는다.

### 2.6 LiteLLM — 라우팅만 한다

[Router 문서](https://docs.litellm.ai/docs/routing) · [proxy config](https://docs.litellm.ai/docs/proxy/configs) [웹].
`model_list`에 `model_name` + `litellm_params.api_base`로 vLLM 엔드포인트를 등록하고
폴백·재시도·쿨다운을 한다. **생명주기(로드/언로드) 개념이 없다** [웹 — 검색 결과에 resident/
on-demand/sleep 관련 문서가 없다].

**우리에게**: 교대 문제를 안 푼다. `fallback` 필드(`src/config.py:162`)와 겹치는 기능은 이미
우리가 갖고 있다.

### 2.7 vLLM 한 프로세스 다중 모델 — **아직 아니다**

[Q2 2026 로드맵 #39749](https://github.com/vllm-project/vllm/issues/39749) [웹]. SIG Core는
Scheduler·KV Cache Manager·Model Runner V2 마이그레이션·Prefix Cache and Memory Coordination을
든다. **다중 모델은 [vLLM-Omni](https://github.com/vllm-project/vllm-omni/issues/2136)라는 별도
프로젝트로 빠져 있고**, 그건 Omni/TTS/Diffusion/World/VLA 같은 **모델 종류** 다중화이지 우리가
원하는 「같은 프로세스에 LLM 여러 개」가 아니다 [웹].

**결론: 한 프로세스 다중 모델 길은 지금 없다.** 여러 서버 + sleep/wake가 상류가 미는 길이고
([공식 블로그 quick start](https://vllm.ai/blog/2025-10-26-sleep-mode)가 정확히 그 형태다 —
터미널 둘에 각각 `--enable-sleep-mode --port 8001` / `8002`), 우리 포트 배치
(`config/models.yaml`의 8001~8007)와 이미 같은 모양이다.

## 3. 웹 — 교대 비용을 상각하는 전략

### 3.1 단계 재정렬·배칭 — 문헌이 있다

[TOPAS: Workflow-Aware Prefix-State Scheduling for Multi-Agent LLM Serving](https://arxiv.org/html/2608.25523) [웹]가
우리 문제를 그대로 서술한다: *"GPU memory can hold the KV cache for only one Agent prefix at a
time. Prioritizing task progress can sacrifice prefix locality, while preserving locality can
delay workflow completion."*

[Agent Capsules](https://arxiv.org/html/2605.00410) [웹]: *"Batching same-prefix requests
amortizes setup costs"* — 같은 prefix를 묶으면 시스템 프롬프트 ingestion과 스케줄링 고정비가
N개에 나뉜다.

[SAGA: Workflow-Atomic Scheduling](https://arxiv.org/html/2605.00528) · [Maestro](https://arxiv.org/pdf/2606.12950) [웹]도
같은 축이다. **파이프라인 구조는 「워크플로 하나에 한 시점 한 에이전트만 활성」인 async batch
워크로드에 가장 맞는다**는 것이 공통 서술이다 [웹] — 우리 하네스가 정확히 그 형태다.

**우리에게 중요한 것은 이 문헌들이 새 아이디어를 주지 않는다는 점이다.** 이들이 말하는
「같은 역할을 모아 한 번에」는 build-plan §8 row 5가 이미 적어 둔 것이고, 우리 러너 구조상
그게 유일한 길이다(§5.3).

### 3.2 부분 상주 — 산술이 명확하다

우리 registry 기준 [저장소 `config/profiles.yaml:139-188` `local_balanced`]:

| 역할 | 모델 | build-plan §7 소계 |
| --- | --- | --- |
| embedding | `qwen3-embedding-0.6b` | 둘 합쳐 ~2.4 GiB |
| reranker | `qwen3-reranker-0.6b` | ↑ |
| scout | `qwen3-8b` (nvfp4) | 단계 4 ~40 GiB (전문가 셋 + 판별기 기준) |
| auditor | `qwen3-coder-30b-a3b` (nvfp4) | 단계 5 ~20 GiB |
| critic | `devstral-small-2-24b` (nvfp4) | 단계 7 ~16 GiB |

**⚠ 위 소계는 build-plan §7이 스스로 "대역폭·용량 상한 계산이지 실측이 아니다"라고 라벨을
붙인 값이다.** 우리가 실측한 것은 **한 서버(30B NVFP4, `--gpu-memory-utilization 0.45`,
`--max-model-len 32768`)가 약 51 GiB를 잡고 반환한다**는 것뿐이다 [실측].

**부분 상주가 산술적으로 확실한 부분**: embedding+reranker는 합쳐 ~2.4 GiB고 3단계에서 **모든
후보에 대해** 불린다. 교대 대상으로 잡으면 왕복 수가 후보 수만큼 늘어난다 — **상주가 맞다.**
이건 소계가 실측이 아니어도 방향이 안 뒤집힌다(두 모델이 0.6B라는 것은 registry 사실이다).

### 3.3 **잠든 서버도 공짜가 아니다 — 이 숫자가 설계를 가른다**

[실측] L1/L2 SLEEP 상태에서 `nvidia-smi --query-compute-apps`가 **2,382 MiB**를 보고했다
(AWAKE 54,260 MiB). 즉 잠든 vLLM 프로세스 하나가 **약 2.33 GiB**를 계속 잡는다.

[계산] 모델 7개를 전부 서버로 띄워 두고 하나만 깨우는 구성이면
**잠든 6개 × 2.33 GiB ≈ 14.0 GiB**가 상시 소모된다. 119.7 GiB 중이면 12%다.

⚠ **이건 한 서버 한 판의 값을 곱한 것이다.** 프로세스 상수(CUDA 컨텍스트·파이썬 힙)라면
모델 크기와 무관해 곱셈이 성립하지만, **모델 의존이면 안 성립한다.** L2가 *"buffers are kept
in CPU, like rope scaling tensors"*를 남긴다는 [웹] 서술은 모델 의존을 시사한다. **재기 전에는
이 14 GiB를 예산에 못 박지 않는다.** 재는 방법: 0.6B 임베딩 서버를 하나 띄워 재우고 같은
쿼리를 읽는다 — 30분짜리 실험이다.

## 4. 웹 — 설정 스키마 사례 정리

| 프로젝트 | 「상주 vs 교대」를 표현하는 방식 | 출처 |
| --- | --- | --- |
| llama-swap | `groups.<name>.{swap, exclusive, persistent, members}` — **불리언 3개 + 멤버 목록** | [wiki](https://github.com/mostlygeek/llama-swap/wiki/Configuration) |
| llama-swap | 모델별 `ttl`(초) — 유휴 자동 언로드 | 위 |
| llama.cpp router | `--models-max <N>` — **정수 하나 + LRU** | [HF blog](https://huggingface.co/blog/ggml-org/model-management-in-llamacpp) |
| Ray Serve | `@serve.multiplexed(max_num_models_per_replica=3)` — **정수 하나 + LRU** | [docs](https://docs.ray.io/en/latest/serve/model-multiplexing.html) |
| production-stack | 선언 없음 — **명령형 HTTP 호출**(`/sleep?id=`) | [docs](https://docs.vllm.ai/projects/production-stack/en/latest/use_cases/sleep-wakeup-mode.html) |
| KServe | `localmodel` 캐시 + Knative scale-to-zero — **선언적 리소스** | [docs](https://kserve.github.io/website/docs/model-serving/generative-inference/modelcache/localmodel) |

**두 갈래로 갈린다**: (a) **정수 하나 + LRU**(Ray, llama.cpp) — 단순하지만 우리처럼 모델 크기가
0.6B~30B로 50배 갈리면 개수가 메모리를 대표하지 못한다. (b) **역할/그룹별 명시 선언**(llama-swap) —
장황하지만 **우리 파이프라인처럼 순서가 이미 정해져 있으면 LRU가 예측할 것이 없다.**

**우리는 (b)다.** 이유: 우리 단계 순서는 런타임에 정해지지 않는다 — `_analyze`가
`preprocess → index → _triage_all → critic → validate`를 **코드로** 고정한다
(`src/orchestrator/runner.py:731-790`). LRU가 학습할 접근 패턴이 없고, 대신 **정확히 알려진
순서**가 있다. 알려진 순서에 LRU를 씌우는 것은 정보를 버리는 일이다.

## 5. 저장소 — 지금 무엇이 교대를 막는가

### 5.1 스키마 — `extra="forbid"`가 어디에 걸려 있나

**`src/schemas/common.py:62`**

```python
model_config = ConfigDict(frozen=True, extra="forbid")
```

`HarnessModel`의 클래스 변수다. `src/config.py`의 **전 설정 모델이 이걸 상속한다** —
`Benchmark`(57) · `ModelEntry`(136) · `AdapterSelection`(170) · `ProfileEntry`(199) ·
`CapsuleBudgets`(232) · `Thresholds`(240) · `HarnessConfig`(279). 즉 **YAML에 `execution:`이나
`swap:`을 적으면 `load_config()`가 `ValidationError`로 죽는다.** build-plan §1 정정 6이 적은
그대로다.

CI가 이걸 지킨다: `tests/test_config.py:278 test_typo_field_is_rejected`가
`ProfileEntry.model_validate`에 오타 키를 넣어 `ValidationError`를 요구한다.

**`frozen=True`도 같은 줄에 있다.** 런타임에 `config.profile.roles["scout"] = ...` 같은 제자리
변경이 안 된다. 오버라이드는 전부 `transition()`(`src/schemas/common.py:64-70`)으로 새 객체를
만들어야 하고, **그 경로는 이미 있다** — `src/cli.py:102-128 load_profile()`이 `seed`와
`tool_runner`를 그렇게 갈아 끼운다(119-127줄). 교대 관련 CLI 오버라이드가 필요하면 **그 함수
하나만** 늘리면 된다.

### 5.2 `ProfileEntry` — 늘려야 할 자리 (`src/config.py:199-229`)

```
199  class ProfileEntry(HarnessModel):
202      description: NonEmptyStr
203      production: bool = False
205      roles: dict[str, NonEmptyStr]       # 역할 → models.yaml 키
206      adapters: AdapterSelection
208      budget: NonEmptyStr
210      @model_validator _has_required_roles      (211-215)
217      @model_validator _hybrid_needs_retrieval_roles  (218-229)
```

- **`roles`가 `dict[str, str]`이다(205줄).** build-plan §1 정정 7이 지적한 그대로 — 값이
  문자열이라 Scout 풀(리스트)이 파싱되지 않는다. **교대만 하려면 이건 안 건드려도 된다.**
- 새 키는 **선택 필드 + 기본값**으로 넣어야 한다. 기본값이 없으면 **기존 프로필 13개가 전부
  로드 실패**한다(`config/profiles.yaml`에 `dev_fake`~`b3prime_balanced` 13개). 이건 registry에
  `measured_on`·`source`를 `None` 기본값으로 넣은 것과 같은 논법이다(`src/config.py:76-77` 주석).
- `_has_required_roles`와 짝을 이루는 **새 검증기가 필요하다**: 「`swap`에 적힌 역할이
  `roles`에 실재하는가」. 없으면 factory에서 `KeyError`로 터지고 어느 프로필이 잘못됐는지가
  스택 아래에 묻힌다 — `AdapterSelection` docstring(174-177)이 `Literal`을 닫아 둔 이유와 같다.

### 5.3 `ModelEntry` — 관리 엔드포인트를 적을 칸이 없다 (`src/config.py:136-163`)

```
139      endpoint: NonEmptyStr        # "http://127.0.0.1:8002/v1"
140      context_limit: int
141      quantization: NonEmptyStr
146      checksum: Sha256Digest
160      source: NonEmptyStr | None = None
161      prompt_template_version: NonEmptyStr
162      fallback: str | None = None

```

`endpoint`가 `/v1`까지 포함한 **추론 경로**다(`config/models.yaml`의 값이 전부 그렇다).
sleep 엔드포인트는 `/v1` **밖**이다(`http://127.0.0.1:8002/sleep`). `endpoint`에서
`/v1`을 문자열로 떼어내는 코드를 쓰면 안 된다 — `ModelEntry.source`가 형식을 패턴으로 강제하지
않는 이유(153-155줄 주석)와 같은 종류의 결합이 생긴다.

**`is_fake`(165-167)가 `endpoint.startswith("fake://")`로 판정한다.** 교대 정책은 이걸 존중해야
한다 — Fake 역할은 재울 서버가 없다. `served_models()`(323-359)가 이미 「실제로 뜨는 역할」을
계산하고 있고, **그 함수가 교대 대상 집합의 정본이 되어야 한다**(`retriever: fake`면
embedding·reranker를 빼는 두 번째 축까지 이미 들어 있다, 352-354줄).

### 5.4 `AdapterSelection` — 여기는 아니다 (`src/config.py:170-196`)

`retriever`(183) · `tool_runner`(195) · `state_store`(196) 셋뿐이고, docstring(172-177)이

**여기에 `swap: Literal[...]`을 넣으면 그 설계 진술을 깨뜨린다.** `ProfileEntry` 직속으로 간다.

## 6. 저장소 — 클라이언트 수명과 교대 지점

### 6.1 **클라이언트는 run 시작에 만들어진다. 호출 시점이 아니다.**

`src/adapters/factory.py:291-295`:

```python
clients: dict[str, ModelClient] = {
    role: _model_client(config.profile.roles[role], config)
    for role in PROMPTED_ROLES
    if role in config.profile.roles
}
```

`build_deps()`(260) 본문이다. `_model_client`(425-442)가 `OpenAICompatModelClient`를 만들고,
그게 `Deps.models = RoutingModelClient(clients)`(352)로 들어간다. 이후 run 내내 그 dict는
**불변**이다 — `RoutingModelClient`(`src/adapters/routing_model.py:26-39`)는 생성자에서
`dict(clients)`로 복사만 하고 갱신 메서드가 없다.

호출 경로는 `RunContext.call_model`(`src/orchestrator/context.py:145`) →
`self.models.complete(role=...)` (174줄) → `RoutingModelClient.complete`(38-39) →
`OpenAICompatModelClient.complete`(`src/adapters/openai_compat.py:71`) →
`_post`(186) → `urllib.request` POST to `f"{self.endpoint}/chat/completions"`(188).

**교대 설계에 중요한 두 가지**:

1. **클라이언트 객체는 상태가 없다.** `endpoint`·`model_name`·샘플링 파라미터를 들고
   매 호출 새 HTTP 요청을 만든다(연결 풀도 세션도 없다 — `urllib.request.urlopen`을 매번
   부른다). **즉 서버를 재웠다 깨워도 클라이언트를 다시 만들 필요가 없다.** 교대를 넣기에
   유리한 구조다.
2. `_request_payload`(158-184)가 `"model": self.model_name`(165줄)을 싣는데, **그 값이 registry
   키다**(`qwen3-8b` 등, `_model_client`의 `model_name=model_key` 433·436줄). vLLM 서버는 보통
   `--served-model-name`으로 이 이름을 맞춰야 한다. **프록시 방식(§7 제안 B)이 바로 이 필드로
   라우팅하므로 그쪽에는 이게 이미 갖춰져 있다.**

`build_deps()`가 콜러블을 경계 너머로 나르는 패턴이 **이미 세 번** 쓰였다 —
`symbols_for`(factory.py:83) · `counter_for_role`(92) · `counter_report`(102). 셋 다 이유가
같다: **러너는 `src/adapters/`를 import 하지 않는다**(계층 규칙, `tests/test_policy.py`가
`test_orchestrator_source_has_no_adapter_import`로 강제). 교대 훅도 **같은 자리에 같은 모양으로**
들어가야 한다. 새 패턴이 아니다.

### 6.2 호출 순서 — 교대 지점 후보

`run_pipeline`(`src/orchestrator/runner.py:532`) → `preprocess.run`(577) → `_analyze`(731):

```
731 _analyze
735   index.run(ctx)                          ← 1단계 (도구, 모델 없음)
736   _plan_targets(...)                      ← 2단계
737   _triage_all(...)                        ← 3~6단계 ★ 후보 루프
743   critic.select(ctx, promoted)            ← 7단계 선별
745   for finding in selected:
747       critic.run(...)                     ← 7단계 ★ Critic 호출
781   for finding in state.in_state(VALIDATED):
782       validate.run(...)                   ← 8단계 (도구)
```

`_triage_all`(906-963)의 루프(927줄 `for target in plan.targets:`)가 `_triage_one`(1080-1125)을
후보마다 부른다:

```
1080 _triage_one
1095     retrieval.run(..., LIGHT)      ← 3단계 (hybrid면 embedding+reranker 호출)
1099     scout.run(...)                 ← 4단계 ★ Scout 모델
1108     retrieval.run(..., EXPANDED)   ← 3단계 재진입 (hybrid면 또)
1109     auditor.run(...)               ← 5단계 ★ Auditor 모델
1117     gate_node.run(...)             ← 6단계 (결정론, 모델 없음)
```

**이것이 교대의 핵심 장애물이다.** 한 후보 안에서 scout→auditor를 왕복하고, 다음 후보에서
다시 scout로 돌아온다. `config/budgets.yaml:72`의 `candidate_max: 256` 기준:

| 배치 | 교대 횟수 | 비용 [계산] |
| --- | --: | --- |
| 지금 구조에 교대를 그냥 끼움 | 256 × 2 = **512** | 512 × (sleep 1~6s + wake 2~3s) = **26~77분** |
| 단계 단위로 재배열 | **3~5** | 3~5 × 3~9s = **9~45초** |

**계산 근거**: sleep 1~6초·wake 2~3초는 우리 실측 전이값이다 [실측, 보고서 §3.2]. 한 번의
교대 = sleep 1건 + wake 1건 = **3~9초** [계산]. build-plan §7이 "왕복 2~6초"라고 쓴 것보다
넉넉하게 잡았다. **⚠ 이 값들은 상태별 한 점씩이고 산포를 모른다** — 보고서 §5 첫 행이
"이 보고서의 가장 큰 결손"이라 부른 그것이다. 그리고 §1.3의 CUDA graph 모순이 안 풀리면
**wake 뒤 첫 추론에 2~10초가 더 붙을 수 있다** [웹, RFC #34303].

비교 기준: 실제 run이 16분 26초(`run_20260827_0002`, 저장소 기록) 규모다. **9~45초는 5% 미만,
26~77분은 run을 두 배 이상 늘린다.** 이 한 줄이 설계 선택을 결정한다.

## 7. 설계 제안

### 제안 A — 단계 재배열 + 프로필의 `execution.swap` 선언 (**권장**)

**(a) 스키마 변경 — 파일:줄**

    """어느 역할이 상주하고 어느 역할이 교대하는가."""
    resident: tuple[str, ...] = ()      # 재우지 않는 역할

### 제안 B — 외부 교대 프록시. **하네스 스키마를 안 건드린다**

llama-swap/production-stack 형태의 프록시를 8000번에 띄우고, 모든 `ModelEntry.endpoint`를
그 한 주소로 바꾼다. 프록시가 요청의 `model` 필드로 대상 서버를 골라 깨우고 나머지를 재운다.

**(a) 스키마 변경 — 없다.** `config/models.yaml`의 `endpoint` 값만 바꾼다. 이유:
`openai_compat.py:165`가 이미 `"model": self.model_name`(= registry 키)을 싣고 있어
**프록시가 라우팅할 키가 이미 페이로드에 있다.** `src/config.py`·`factory.py`·`runner.py`
한 줄도 안 바뀐다.

**(b) 교대 지점** — 하네스 밖. 프록시가 요청을 받은 시점에 동기적으로 판단한다.

**(c) 비용** [계산]
- 교대 횟수는 **§6.2의 512회 그대로다** — 프록시는 파이프라인 순서를 모른다.
- 512 × 3~9초 = **26~77분/run**. **받아들일 수 없다.**
- 단, `mode: per_stage` 재배열을 하고 나면 프록시도 3~5회로 떨어진다 — **그때는 제안 A의
  코드 절반이 필요 없어진다.**

**(d) 대가**
- **지금 구조 그대로면 못 쓴다.** 단계 재배열이 여전히 선행 조건이다.
- 재현성 기록이 나빠진다. `RunRecord.model_checksums`(`src/config.py:302-304`)는 registry에서
  오므로 유지되지만, **"이 run이 실제로 어느 서버에 붙었는가"가 하네스 기록에 안 남는다** —
  프록시 로그에만 있다. 이 저장소가 `tool_images`를 어댑터에게 물어 기록하는 이유
  (`factory.py:357-359` 주석: *"어댑터가 무엇을 실제로 물렸는지와 갈라질 수 있고, 갈라진
  재현성 기록은 없는 것보다 나쁘다"*)와 정면으로 어긋난다.
- 프록시가 새 실패 지점이다. `_is_droppable`(`runner.py:260`)이 상태 코드로 「서버가 죽었다」와
  「이 요청이 거절됐다」를 가르는데(906-963 표), **프록시가 자기 사정으로 5xx를 내면 러너가
  즉시 멈춘다.**
- **다만 이 제안이 옳은 자리가 하나 있다**: `bench`(`src/cli.py:691`)와 `doctor`(132)처럼
  파이프라인 순서가 없는 경로. 거기서는 프록시가 정확히 맞는 답이다.

### 제안 C — 부분 상주 + run 분할. **가장 싸고 가장 정직하다**

교대를 코드에 안 넣는다. 대신 (1) 작은 모델은 상주시키고 (2) run을 단계 구간으로 쪼개
**사람/스크립트가 서버를 갈아 끼운다.**

**(a) 스키마 변경**
- `src/config.py`: **없거나 거의 없다.**
- `config/profiles.yaml`: 새 프로필. 예 — Scout·Auditor·Critic 중 하나만 실서빙이고 나머지는
  `fake`인 프로필 셋. **이건 이미 표현 가능하다** — `single_gpu_12g`
  (`config/profiles.yaml:106-137`)가 정확히 그 형태다(scout만 실서빙).
- ⚠ **`RunSpec`에는 `stop_after`만 있고 `start_from`이 없다**(`runner.py:312-340`).
  구간 실행을 하려면 그걸 만들어야 하고, `_analyze`(731)가 `last <` 비교로만 자르는 구조라
  **재개 지점을 상태에서 복원하는 코드가 통째로 없다.** `SqliteStateStore`가 있어
  (`config/profiles.yaml`의 실서빙 프로필이 전부 `state_store: sqlite`) 저장은 되지만,
  **읽어서 이어가는 경로가 없다.**

**(b) 교대 지점** — run 경계. 하네스 밖.

**(c) 비용**
- 교대 횟수 = **run 분할 수 - 1** = 2~3회.
- 각 교대는 **콜드 스타트 238초** [실측] — sleep/wake를 안 쓰면 이게 비용이다.
  2~3회 × 238초 = **8~12분**. 16분 run 대비 50~75% 추가.
- sleep/wake를 스크립트로 쓰면 **9~27초**로 떨어지고 [계산], **하네스 코드는 여전히 0줄**이다.

**(d) 대가**
- **run이 쪼개지면 `RunRecord`가 쪼개진다.** `run_id`가 갈리고 `source_hash`(`runner.py:1314`)·
  `repo_commit`·예산 장부(`BudgetLedger`)가 구간마다 따로 생긴다. **evaluation.md의 조건 간
  비교에 그대로 못 올린다** — 지금 비교표 규칙이 run 하나를 단위로 한다.
- 자동화가 아니다. 사람이 순서를 틀리면 아무것도 안 막는다.
- **그래도 이게 옳은 첫 수일 수 있다.** 이유: §1.3(CUDA graph 모순)·§1.4(GB10 wake 크래시)·
  §3.3(잠든 서버 잔류량)이 **전부 미확인**이다. 제안 A는 러너 중심부를 재작성하는데, 그
  전제 셋이 흔들리면 재작성이 헛일이 된다. **제안 C로 먼저 한 판 돌려 sleep/wake가 실제 추론
  경로에서 버티는지를 확인하고**, 그 다음에 A로 간다. CLAUDE.md §7과 build-plan §8 말미의
  *"⚠ 1·2·6번이 끝나기 전에는 7번(코드 작성)에 들어가지 않는다 — 먼저 재고 나서 짓는다"*가
  요구하는 순서가 이것이다.

## 8. 배선 전에 반드시 지킬 운영 규칙 (근거 있는 것만)

1. **서버를 하나씩 순차로 띄우고, 전부 뜬 뒤에 재운다.** 동시에 띄우면 죽는다 [실측 09-04].
   상류 근거: [#9232](https://github.com/vllm-project/vllm/issues/9232) —
   *"This happens when the GPU memory was not properly cleaned up before initializing"* [웹].
   vLLM은 기동 시 free memory를 프로파일링해 KV cache 예산을 잡으므로, **다른 프로세스가 메모리를
   반환하는 중이면 그 프로파일이 깨진다.**
2. **in-flight 요청이 0일 때만 sleep을 부른다.**
   [#28714](https://github.com/vllm-project/vllm/issues/28714): 요청 처리 중 sleep → CUDA
   illegal memory access [웹]. Scout 3개 동시 실행이 정확히 그 조건이다.
3. **level 2를 쓰면 wake 뒤 `collective_rpc reload_weights` + `reset_prefix_cache`를 반드시
   부른다** [웹, 공식 블로그]. **level 1이면 부르지 않는다.** 우리 09-03 L2 측정은 이 단계를
   빠뜨렸으므로 그 수치를 재사용하지 않는다.
4. **`--host 127.0.0.1`을 유지한다.** `VLLM_SERVER_DEV_MODE=1`이 인증 없는 관리
   엔드포인트 7개를 연다 [웹].
5. **`PYTORCH_CUDA_ALLOC_CONF`에 `expandable_segments`를 켜지 않는다** —
   `CuMemAllocator`와 양립 불가 [웹, vllm-ascend PR #9242].
6. **`nvidia-smi --query-compute-apps`를 계측기로 쓴다.** `--query-gpu`는 이 장비에서 `[N/A]`다
   [실측 09-03 §3.4]. `torch.cuda.memory_allocated()`는 sleep 뒤 신뢰할 수 없다
   [웹, #33625] — `mem_get_info()` 차분을 쓴다(우리가 이미 그렇게 했다 [실측]).
