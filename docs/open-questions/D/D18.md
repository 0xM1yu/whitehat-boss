# D18 — 8단계 정책이 게이트 등급을 읽지 않는다

| 상태 | 관련 문서 |
| --- | --- |
| 열림 | [architecture.md](../architecture.md) §4, `src/orchestrator/policy.py` |

> 인덱스: [docs/open-questions.md](../open-questions.md) · 작업 추적은 GitHub Issue

## 내용

`evaluate_gate(stage=VALIDATE)`가 등급을 계산해 `gate_eval` trace에 남기지만, `REPRO_RESULT` 정책(`policy._repro_result()`)이 보는 것은 `ok`·`tool_allowed` 둘뿐이고 `basis`에도 `grade`가 없다. 그래서 게이트가 E3인 Finding도 `ok=True`면 `proven`이 부여될 수 있고 **상태 축과 등급 축이 어긋난 채로 남는다.** **2026-08-21 ATOM 실측(run_20260821_0001, `dev_docker`/aarch64)**: stage 8 `gate_eval`이 `grade=E3, p4=False`인데 같은 시점의 `policy_decision`은 `basis.ok=False`·`basis.tool_allowed=True`만 싣는다 — 6·7단계의 `policy_decision`에는 있는 `basis.grade`가 **8단계에만 없다.** 즉 W3이 8단계에서 등급을 **계산하게는** 만들었지만 소비하는 쪽은 그대로다. **판단이 필요한 것**: (a) `RoutingRequest.signals`에 `grade`를 넣고 정책이 E4를 요구한다 (b) 등급을 **집계 전용**으로 명문화하고 승격은 계속 `ok`로 한다. (a)는 승격 동작이 바뀌므로 evaluation.md §2.3에 따라 **이전 run과 직접 비교할 수 없게 된다** — 그래서 W3과 같은 PR에 얹지 않았다. 지금은 (b)의 상태이고 그 사실을 `nodes/validate.py`의 게이트 호출 옆 주석이 적어 둔다(설명 없는 미소비 계산은 다음 사람이 죽은 코드로 지운다 — `GATE_STAGES`가 참조 0건이던 자리와 같은 종류다) . **이 항목은 "등급이 왜 E3인가"가 아니라 "그 E3가 왜 소비되지 않는가"다.** 전자는 게이트 층이고 구체 근거가 따로 있다 — `run_20260821_0004`에서 8단계 `asan`이 `ok=False`라 `usable`에서 빠져 `p4`가 False였다([실험 보고서](../experiments/harness/2026-08-22-pipeline-atom.md) §3 해석 ⑧'). 두 층을 섞으면 "정책이 등급을 안 읽는다"와 "등급이 낮게 나올 이유가 있었다"가 한 문장이 된다
