- `main_26` `esp_transfer_data` — `s->async_len = len`(field write); 같은 샘플의 sink `esp_do_nodma`도 미포착(B=8134)

### 기제 [코드]

Case A의 `api`(`candidates_a_query`)는 조건을 거른 메서드를 **순회 순서대로** `.take(CASE_A_CANDIDATE_CAP)`로 자른다 — 순회 순서는 메서드 노드 순서이고 제목의 `method.id` 순서는 그 근사다. 메서드 수가 cap을 넘으면 **뒤쪽 메서드가 통째 탈락**한다. (`budget()`(#311)의 `method.id` 정렬 뒤 round-robin은 Case B 쪽이다 — Case A는 그것을 거치지 않는다.) GT 함수가 강한 앵커를 가져도 파일 내 위치가 뒤면 후보에서 빠진다. ~~정렬이 결정론적이라 재현되고 우회 손잡이가 없다.~~ -> 2026-09-29 정정: main의 Case A에는 정렬이 없고, 순회 순서는 문서화된 안정 순서가 아님(`slicer_queries.py`의 `.take` 주석). 맞는 건 「우회 손잡이가 없다」까지.

⚠ **측정 json의 `case_a`(≈4000)는 cap에 잘린 뒤 값**이라, 자르기 전 진짜 후보 수와 GT 메서드의 실제 순위는 안 실린다. 그래서 "cap을 몇까지 올려야 하나"는 **cap-off 재측정 없이는 못 정한다**(4001번째면 5000, 15000번째면 15000).

⏵ 2026-10-04 PR #470 -> 위 기제는 `--priority-case-a`(기본 꺼짐, `--priority-files`와 같이만)가 꺼진 동안의 서술이다. 켜면 `api` 정렬이 목록 파일 -> hot -> 나머지 셋이라 선택지 (a)의 「hot 층이 cap 이하면 안 잘림」은 「목록 층 + hot 층이 cap 이하면」이 된다. 같은 PR의 본문 필터(기본 켬)는 본문 없는 METHOD를 `api`·`readers`에서 빼 캡 자리를 걷으므로 위 A 수(4037 등)는 그 전 코드의 값이다. 근거·한계는 [slicer-README](../../slicer-README.md)의 Case A
