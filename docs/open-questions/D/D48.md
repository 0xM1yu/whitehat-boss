# D48 — target_skipped.stage가 실제로 실패한 단계를 안 가리킨다

> 인덱스: [docs/open-questions.md](../open-questions.md) · 작업 추적은 GitHub Issue

## 내용

**해소 · PR #50.** `_drop()`이 실패 단계를 인자로 받아(a) `target_skipped.stage`가 실제 단계를 가리킨다. **2026-08-28**([run A 보고서](../experiments/harness/2026-08-28-runA-harness-validation-atom.md) §5 피해 ②). `run_20260828_0002`의 `target_skipped` 3건이 전부 `stage: 4`인데 그 target에서 실패한 `model_call`은 셋 다 **`stage: 5` auditor**다(seq 75·136·232). **기제**: `runner._drop()`이 `_emit_skipped(..., stage=Stage.SCOUT, ...)`로 단계를 **하드코딩**한다. `_triage_one`은 scout(4)과 auditor(5)를 연달아 부르므로 어느 쪽에서 죽었든 기록은 4다. **왜 중요한가**: D45가 방금 연 대조("무엇을 봤는가")의 짝이 "어디서 못 봤는가"인데, 그 답이 한 값으로 뭉개져 있다. 실패가 scout 쪽인지 auditor 쪽인지는 원인이 다르다 — scout 실패는 후보 생성 자체가 안 된 것이고 auditor 실패는 후보는 났는데 심층 분석이 막힌 것이다. 지금은 `target_skipped`의 `stage`와 같은 target의 `model_call`을 사람이 대조해야만 갈린다. **`target_planned`와 같은 필드를 같은 이름으로 싣는다는 D45의 판단은 유지된다** — 갈리는 것은 `stage` 하나다. 선택지: **(a)** `_drop()`이 실패 단계를 인자로 받는다 — `_triage_one`이 어느 노드에서 예외가 났는지를 알아야 하므로 그 함수가 단계를 들고 있어야 한다 **(b)** 예외에 단계를 실어 올린다 — `ModelGatewayError`·`SchemaParseError`에 필드가 늘고 `src/interfaces/` 변경이다 **(c)** 그대로 두고 대조를 문서화한다 — 자동 채점에는 여전히 못 쓴다
