## 내용

**하네스가 조용히 죽거나 멈춰도 외부에서 그것을 알 수단이 없다.** 모델을 붙이지 않고 파일·타이머·로그만으로 잡을 수 있는데 그 자리가 비어 있다.

**관측 [코드 · 2026-09-15].**

1. **live로 안 보인다.** `TraceWriter.emit`이 `self._stream.write(...)`만 하고 **flush를 안 한다**(`trace.py`). `cli.py`가 `trace.jsonl`을 `open("w")`로 여는데 기본이 **블록 버퍼링**(≈8KB)이다. 그래서 run 도중 이벤트가 파일에 **덩어리로 지연**되고, `tail -f`가 실시간이 아니다.
2. **크래시에 마지막이 증발한다.** 버퍼가 안 비워진 상태로 프로세스가 죽으면(ATOM 통합메모리 초과 → SSH 먹통 → 하드리셋 — [ATOM util 함정](../../portability.md) 계열) **직전 이벤트가 통째로 사라진다.** 정작 원인을 봐야 할 순간이 안 남는다.
3. **멈춘 호출은 침묵한다.** trace는 단계·호출 **경계**에서만 이벤트를 낸다. 모델 호출 하나가 폭주·교착이면 그 호출이 돌아올 때까지(최대 `_TIMEOUT_S = 300`초) **아무 이벤트도 안 난다** — "프로세스가 죽었나 / 느린 호출 중인가"를 밖에서 못 가른다.
4. **재발 에러를 밖에서 읽을 플래그가 없다.** `_MAX_CONSECUTIVE_DROPS` 차단기가 같은 실패 연속 N회에 **내부에서** 멈추지만, 그 신호를 외부 관찰자가 읽는 형식이 없다. `RunRecord.is_complete`·`stopped_after`는 **run이 끝난 뒤**에만 채워진다.

**즉 재료(trace 이벤트·차단기·타임아웃·RunRecord)는 있으나 ① live로 안 보이고 ② 죽음/멈춤/에러 폭주를 밖에서 못 읽는다.**

## 왜 중요한가

이 저장소의 산출물은 판정이고, 그 판정을 내는 run이 **조용히 죽거나 부분 결과로 끝나면** 그 사실이 늦게(또는 크래시 땐 아예) 드러난다. ATOM은 종료가 가깝고(대형 run이 몇 시간) 통합메모리 초과 시 박스가 얼어붙는 최악이 있는데, 그 순간의 로그가 버퍼에 갇혀 사라지면 원인 규명이 불가능하다. 모델을 붙이면 결정론이 깨지고 온프레미스(에어갭 포함)에서 외부 메트릭 스택은 기조에 안 맞으므로, **타이머·파일·로그만으로 푸는 것이 제약상 옳은 유일한 방향**이다.

## 선택지

- **(a)** 산출물 셋 + 외부 폴러를 단계로 얹는다 — **① flush**(`emit`에 `flush()` 한 줄, 모든 것의 전제) → **② heartbeat 파일**(러너 타이머 스레드가 N초마다 `{now, pid, last_event_seq, current_stage}` 갱신 — 호출이 멈춰도 틱해 죽음↔느림을 가름) → **③ status.json**(불리언 플래그 `stuck`·`error_storm`·`budget_exhausted`·`incomplete`; `error_storm`은 `target_skipped`·`critic_failed`의 같은 사유 K회 반복) → **④ 모니터 프로세스**(`tools/`의 stdlib 로컬 폴러가 셋을 읽어 보고·경보; kill은 안 함 — 기존 타임아웃·차단기와 겹친다). 대가: 임계값 T·K를 **실측 baseline**에서 뽑아야 한다(§0 — 추측 상수 금지). 역할별 T(critic 길다·scout 짧다).
- **(b)** **flush만** 넣는다 — `tail -f`와 크래시 보존이 생긴다. 가장 싸고 ①의 하드 전제를 닫는다. 대가: 멈춤/에러를 사람이 trace를 직접 읽어야 안다(heartbeat·status 없음).
- **(c)** **status.json 플래그만** 낸다 — 외부가 한 파일로 상태를 읽는다. 대가: flush가 선행이라야 최신이고, heartbeat 없이는 "죽음↔느림"을 못 가른다.
- **(d)** 그대로 두고 서술만 한다 — **지금 상태다.** 대가: run이 조용히 죽는 것을 밖에서 못 잡는 채로 실서빙 run에 들어간다.

⚠ **임계값을 추측 상수로 박지 않는다(§0).** "몇 초 무응답이면 멈춤"은 실 run의 `wall_ms` 분포에서 나와야 한다 — critic은 `reasoning_effort: high`라 원래 오래 걸리고 scout는 짧다. baseline run 몇 개가 선행 입력이다.

## 진행

**2026-09-15 — ① flush 착수(부분).** `TraceWriter.emit`이 write 뒤 `self._stream.flush()`를 하도록 고쳤다(`src/orchestrator/trace.py`). 이제 이벤트가 emit 즉시 파일에 남아 `tail -f`가 실시간이고, **스트림을 닫지 못한 채 프로세스가 죽어도**(SIGKILL·OOM-kill·미처리 예외) 직전 이벤트까지 남는다. ⚠ flush가 닫는 것은 거기까지다 — OS 페이지 캐시로 넘긴 것이라 전원 차단·하드리셋(더티 페이지 유실)은 보장하지 못한다(그건 fsync 급이고 trace에 그 대가를 치르지 않는다). `tests/test_trace.py`가 그것을 고정한다 — `cli.py`와 같은 기본(블록) 버퍼링으로 파일을 열고, **스트림을 닫기 전에** 이벤트가 디스크에 있는지 본다(flush 없으면 0줄이라 이 검사가 회귀를 잡는다). 선택지 표현으로는 **(b)**에 해당한다 — ①의 하드 전제를 닫았다.

**남은 것: ②③④.** heartbeat 파일·status.json 플래그·외부 폴러는 아직이다. 그중 "stuck" 판정의 무응답 임계값 T와 "error_storm"의 반복 횟수 K는 **추측 상수로 박지 않는다(§0)** — 실 run의 `wall_ms` 분포(역할별)에서 뽑아야 하고 baseline run 몇 개가 선행 입력이다. 그래서 이 축은 flush와 같은 PR에 넣지 않는다. 상태는 그래서 `부분`이다.

## 닫히는 조건

외부 관찰자가 run에 붙지 않고 **① 하네스가 살아 있는가(죽음↔느림 구분)** ② **에러가 같은 방식으로 반복되는가**를 파일·플래그로 읽을 수 있고, `emit` flush로 **하드크래시에도 직전 이벤트까지 파일에 남으며**, 그것을 고정하는 검사가 함께 들어오면 닫힌다. (b)나 (c)만 하면 그 사실을 이 본문에 적고 상태는 `부분`이다.
