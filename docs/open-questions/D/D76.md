## 내용

**하네스가 조용히 죽거나 멈춰도 외부에서 그것을 알 수단이 없다.** 모델을 붙이지 않고 파일·타이머·로그만으로 잡을 수 있는데 그 자리가 비어 있다.

**관측 [코드 · 2026-09-15].**

1. **live로 안 보인다.** `TraceWriter.emit`이 `self._stream.write(...)`만 하고 **flush를 안 한다**(`trace.py`). `cli.py`가 `trace.jsonl`을 `open("w")`로 여는데 기본이 **블록 버퍼링**(≈8KB)이다. 그래서 run 도중 이벤트가 파일에 **덩어리로 지연**되고, `tail -f`가 실시간이 아니다.
2. **크래시에 마지막이 증발한다.** 버퍼가 안 비워진 상태로 프로세스가 죽으면(ATOM 통합메모리 초과 → SSH 먹통 → 하드리셋 — [ATOM util 함정](../../portability.md) 계열) **직전 이벤트가 통째로 사라진다.** 정작 원인을 봐야 할 순간이 안 남는다.
3. **멈춘 호출은 침묵한다.** trace는 단계·호출 **경계**에서만 이벤트를 낸다. 모델 호출 하나가 폭주·교착이면 그 호출이 돌아올 때까지(최대 `_TIMEOUT_S = 300`초) **아무 이벤트도 안 난다** — "프로세스가 죽었나 / 느린 호출 중인가"를 밖에서 못 가른다.
   ⏵ 2026-09-29 — 그 최대는 이제 모델마다 다르다. 모델의 `request_timeout_s`가 정하고(Auditor 7,500 · Scout 1,200 · 1,800 · Critic 900 s, 계산값), 선언이 없으면 300이다. 폴러의 stuck 상한도 그 값을 쓴다(#274).
4. **재발 에러를 밖에서 읽을 플래그가 없다.** `_MAX_CONSECUTIVE_DROPS` 차단기가 같은 실패 연속 N회에 **내부에서** 멈추지만, 그 신호를 외부 관찰자가 읽는 형식이 없다. `RunRecord.is_complete`·`stopped_after`는 **run이 끝난 뒤**에만 채워진다.

**즉 재료(trace 이벤트·차단기·타임아웃·RunRecord)는 있으나 ① live로 안 보이고 ② 죽음/멈춤/에러 폭주를 밖에서 못 읽는다.**

## 왜 중요한가

이 저장소의 산출물은 판정이고, 그 판정을 내는 run이 **조용히 죽거나 부분 결과로 끝나면** 그 사실이 늦게(또는 크래시 땐 아예) 드러난다. ATOM은 종료가 가깝고(대형 run이 몇 시간) 통합메모리 초과 시 박스가 얼어붙는 최악이 있는데, 그 순간의 로그가 버퍼에 갇혀 사라지면 원인 규명이 불가능하다. 모델을 붙이면 결정론이 깨지고 온프레미스(에어갭 포함)에서 외부 메트릭 스택은 기조에 안 맞으므로, **타이머·파일·로그만으로 푸는 것이 제약상 옳은 유일한 방향**이다.

## 선택지

- **(a)** 산출물 셋 + 외부 폴러를 단계로 얹는다 — **① flush**(`emit`에 `flush()` 한 줄, 모든 것의 전제) → **② heartbeat 파일**(러너 타이머 스레드가 N초마다 `{now, pid, last_event_seq, current_stage}` 갱신 — 호출이 멈춰도 틱해 죽음↔느림을 가름) → **③ status.json**(불리언 플래그 `stuck`·`error_storm`·`budget_exhausted`·`incomplete`; `error_storm`은 진행 이벤트 없이 한 자리(`scout_member`)에서 실패가 K회 연속되면 선다 — 차단기가 `item.role`을 키로 세는 그 축이고, 실제 트립은 종료 전이 사유 `consecutive_target_failures`로 사후 확정한다. ⚠ 등재 초안은 이를 "같은 사유 K회"로 적었으나 그 정의는 차단기가 터지는 모양을 놓쳐 구현에서 바꿨다 — 아래 「진행」 참조) → **④ 모니터 프로세스**(`tools/`의 stdlib 로컬 폴러가 셋을 읽어 보고·경보; kill은 안 함 — 기존 타임아웃·차단기와 겹친다). 대가: 임계값 T·K를 **실측 baseline**에서 뽑아야 한다(§0 — 추측 상수 금지). 역할별 T(critic 길다·scout 짧다). ⏵ 2026-10-10 -> 차단기의 키는 `item.role`이 아니라 둘이다 -> 자리 카운터 `_caller(단계, 자리)`와 자리를 안 가르는 run 카운터([D73](D73.md)). 폴러의 자리별 근사는 자리 카운터와 맞고 run 카운터 모양(여러 자리·여러 대상에 걸친 연속 실패)은 라이브 미탐이다 -> 종료 전이 사유가 뜬 뒤에야 참이다(`tools/monitor.py`의 `_error_storm`, `test_a_run_counter_stop_is_invisible_to_the_live_flag_until_the_transition_lands`).
- **(b)** **flush만** 넣는다 — `tail -f`와 크래시 보존이 생긴다. 가장 싸고 ①의 하드 전제를 닫는다. 대가: 멈춤/에러를 사람이 trace를 직접 읽어야 안다(heartbeat·status 없음).
- **(c)** **status.json 플래그만** 낸다 — 외부가 한 파일로 상태를 읽는다. 대가: flush가 선행이라야 최신이고, heartbeat 없이는 "죽음↔느림"을 못 가른다.
- **(d)** 그대로 두고 서술만 한다 — **지금 상태다.** 대가: run이 조용히 죽는 것을 밖에서 못 잡는 채로 실서빙 run에 들어간다.

⚠ **임계값을 추측 상수로 박지 않는다(§0).** "몇 초 무응답이면 멈춤"은 실 run의 `wall_ms` 분포에서 나와야 한다 — critic은 `reasoning_effort: high`라 원래 오래 걸리고 scout는 짧다. baseline run 몇 개가 선행 입력이다.

## 진행

**2026-09-15 — ① flush 착수(부분).** `TraceWriter.emit`이 write 뒤 `self._stream.flush()`를 하도록 고쳤다(`src/orchestrator/trace.py`). 이제 이벤트가 emit 즉시 파일에 남아 `tail -f`가 실시간이고, **스트림을 닫지 못한 채 프로세스가 죽어도**(SIGKILL·OOM-kill·미처리 예외) 직전 이벤트까지 남는다. ⚠ flush가 닫는 것은 거기까지다 — OS 페이지 캐시로 넘긴 것이라 전원 차단·하드리셋(더티 페이지 유실)은 보장하지 못한다(그건 fsync 급이고 trace에 그 대가를 치르지 않는다). `tests/test_trace.py`가 그것을 고정한다 — `cli.py`와 같은 기본(블록) 버퍼링으로 파일을 열고, **스트림을 닫기 전에** 이벤트가 디스크에 있는지 본다(flush 없으면 0줄이라 이 검사가 회귀를 잡는다). 선택지 표현으로는 **(b)**에 해당한다 — ①의 하드 전제를 닫았다.

**2026-09-15 — ② heartbeat writer 착수(부분).** `src/orchestrator/heartbeat.py`가 데몬 타이머 스레드로 `run_dir/heartbeat.json`을 N초마다 원자적으로 갱신한다(`{ts, pid, last_event_seq, current_stage, interval_s}`). `run_pipeline`이 `PromptLog`와 같은 가드(run_dir 있고 dry_run 아님)로 켜고 `finally`에서 끈다. **핵심: 모델 호출이 멈춰 trace가 침묵해도 이 스레드는 계속 틱한다** — 그래서 외부 관찰자가 "죽음(heartbeat stale)↔느림(heartbeat 살아있고 trace만 침묵)"을 가른다. N(`_INTERVAL_S`)은 판정 상수가 아니라 갱신 해상도이고, 파일에 `interval_s`를 실어 관찰자가 stale 판정(나이 > c×N)을 코드에서 N을 안 세고 내린다. `tests/test_heartbeat.py`가 "trace 침묵 중에도 틱한다"를 고정하고, `tests/test_pipeline_e2e.py`가 실 run 배선(run_dir → heartbeat.json)을 고정한다.

**2026-09-15 — ③④ status·폴러 착수. 이 항목이 닫힌다.** `tools/monitor.py`(stdlib 폴러)가 run에 붙지 않고 `heartbeat.json`·`trace.jsonl`·`run_manifest.json`만 읽어 `{alive, stuck, error_storm, budget_exhausted, incomplete}`를 도출하고, 한 줄 보고와 `status.json`을 낸다. 죽이지 않는다(가시화·경보만 — kill은 `_TIMEOUT_S`·차단기 소관). **임계값은 코드 상수에서 온다(§0):** stuck 하드 상한 T = `(schema_retries+1)×_TIMEOUT_S`(그 run의 `run_manifest.json` `thresholds.schema_retries`, 없으면 config 기본) — 정상 호출이 구조적으로 못 넘는 침묵 길이라 오경보 0으로 지금 방어된다(끝난 run은 매니페스트의 실제 적용값, 도는 run은 config 기본 — 폴 루프가 매니페스트가 생기면 다시 읽어 좁힌다). error_storm은 **진행 이벤트 없이 한 자리(`scout_member`)에서 연속된 실패 K개**로 본다 — K는 `_MAX_CONSECUTIVE_DROPS`에서 빌리고, 자리별로 세는 것이 차단기(`item.role` 키)와 같은 축이다. 실제 트립은 종료 전이 사유 `consecutive_target_failures`로 사후 확정한다. ⚠ 차단기와 **systematic 축 하나만** 다르다 — `role`은 `target_skipped.scout_member`에 있어 맞추지만 `systematic`(크기 거절 400/413 제외)은 trace에 없어, 큰 심볼이 한 자리에서 K회 연속 잘리면 오탐이 난다(알려진 한계 — `_emit_skipped`가 `status`를 실으면 닫힌다, 러너 몫). `src/orchestrator/**`가 `src.adapters`를 import 못 하므로(CI) `_TIMEOUT_S`를 아는 폴러(tools/, orchestrator 아님)가 stuck을 도출한다 — 그래서 status는 러너 스레드가 아니라 폴러가 낸다. `tests/test_monitor.py`가 stuck 경계·error_storm(연속 실패·번갈이·리셋·차단기 트립)·완주/budget(사후·라이브) 도출·상수 대조·상한 계산을 고정한다. ⏵ 2026-10-10 -> 차단기의 키는 `item.role`이 아니라 둘이다 -> 자리 카운터 `_caller(단계, 자리)`와 자리를 안 가르는 run 카운터([D73](D73.md)). 폴러의 자리별 근사는 자리 카운터와 맞고 run 카운터 모양(여러 자리·여러 대상에 걸친 연속 실패)은 라이브 미탐이다 -> 종료 전이 사유가 뜬 뒤에야 참이다(`tools/monitor.py`의 `_error_storm`, `test_a_run_counter_stop_is_invisible_to_the_live_flag_until_the_transition_lands`).

> ⏵ 2026-09-29 — 위 「stuck 하드 상한 T = `(schema_retries+1)×_TIMEOUT_S`」는 #274(2026-09-25) 전의 식이다. 지금 T의 한 호출 몫은 `_TIMEOUT_S`와 프로필이 부르는 모델들이 선언한 `request_timeout_s` 중 가장 긴 값이다(`tools/monitor.py`의 `call_timeout_s`). 끊는 쪽도 모델의 `request_timeout_s`이고 선언이 없을 때만 `_TIMEOUT_S`다(`openai_compat.py`). 이 절의 다른 `_TIMEOUT_S` 둘(kill 소관 · 폴러가 아는 상수)도 그 기본값으로 읽는다.

## 닫히는 조건

외부 관찰자가 run에 붙지 않고 **① 하네스가 살아 있는가(죽음↔느림 구분)** ② **에러가 반복되는가**를 파일·플래그로 읽을 수 있고, `emit` flush로 **스트림을 닫지 못한 채 프로세스가 죽어도 직전 이벤트까지 파일에 남으며**(전원 차단·하드리셋은 fsync 급이라 범위 밖), 그것을 고정하는 검사가 함께 들어오면 닫힌다. (b)나 (c)만 하면 그 사실을 이 본문에 적고 상태는 `부분`이다.
