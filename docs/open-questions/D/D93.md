### 기제 [코드]

- `_chunk_tree()` -> `sorted(root.rglob("*"))` 순서로 40줄씩 자름. 확장자는 `SOURCE_SUFFIXES` 13종(대상 언어 무관)
- `_collect()` -> 대상 본문과 겹치는 조각만 빼고, 키워드가 비면 필터 없이 통과, `picked[:MAX_CHUNKS]`(400)
- Auditor는 `retrieval.run(..., level=EXPANDED)`를 `keywords` 없이 부름([D63](D63.md)이 적은 것과 같음) -> 풀 = 경로 정렬 앞 400조각
- 그 400에서 embedding이 32, 리랭커가 5를 골라 `related` 섹션으로 Auditor 프롬프트에 실림

## 왜 위험한가

hybrid 프로필(`harness_pool_hybrid`)을 켜면 후보 풀에 대상 파일·폴더가 없어 Auditor의 「관련 코드」 5조각도 그 밖에서 나옴(최종 5조각 자체는 안 잼 — [D63](D63.md) 몫). 정본 `harness_pool`은 `retriever: fake`라 지금 run에는 영향 없음. 켜는 순간 조용히 틀림.

## 선택지

- **(a) 풀을 대상 근처부터 채움** -> 같은 파일 · 호출 그래프 이웃 파일(callers·callees 정의 파일) · 같은 폴더 · 나머지 순. 대상이 C/C++면 C/C++ 조각만. 풀 크기 400·embedding 호출 수는 그대로. **권장**
- **(b) `MAX_CHUNKS` 상향** -> 후보당 embedding 입력이 늘어 비용↑. qemu는 6만 조각이라 올려도 앞쪽 편향은 그대로
- **(c) 풀을 그래프 이웃만으로** -> 인덱스가 없거나 간선이 적으면 풀이 비어 `related`가 사라짐
- **(d) 그대로 두고 hybrid 프로필을 안 씀** -> 결함은 남음

질의 모양(식별자 하나)은 이 항목이 아니라 [D63](D63.md)의 몫.
