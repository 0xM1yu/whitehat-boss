## 관측

### 결정 직전의 기존 계약 [코드 대조 · 2026-09-28]

- `EvidenceKind`에는 `static`·`sanitizer`·`crash`·`fuzz_coverage`·`build`·`poc_run`·
  `diff`·`graph` 여덟 종류가 있고, 디버거 전용 종류는 없다(`src/schemas/enums.py`).
- `fake_tools.TOOL_KINDS`에는 gdb가 없고, 실행까지 가야 `ok=True`가 되는 Fake 도구는
  `_REPRO_TOOLS = {"asan", "poc"}`뿐이다.
- 컨테이너 경로도 `_RUNTIME_TOOLS = {"asan", "poc"}`뿐이다. `judge()`는 실행류 도구에서
  빌드 단계 중단과 exit 125·126·127을 `ok=False`로 내리고, 실제 프로그램이 뜬 뒤의
  non-zero는 대상 신호로 보아 `ok=True`와 원 프로세스 종료 코드를 보존한다(asan·poc — 마지막
  명령이 대상이라 그 종료 코드가 대상의 것이다).
- `tests/test_pipeline_e2e.py`가 E4 도달을 보이는 경로는 `dev_fake`의 `_run_repro()`다.
  실컨테이너 ASAN 실행을 거쳐 E4까지 가는 검사는 아니다.

### 기존 ASAN 선행 확인 [실험 보고서 대조 · 2026-09-28]

- [2026-08-22 파이프라인 run](../../experiments/harness/2026-08-22-pipeline-atom.md)은 stage 8
  ASAN이 `ok=false`, exit 1이고 링크 단계에서 끊겨 E3에 머문 기록이다.
- [2026-08-26 재측정](../../experiments/harness/2026-08-26-pipeline-zlib542-remeasure-atom.md)은
  ASAN 8/8이 `repro_failed`, E4 0건이다. 보고서가 적은 직접 원인은 Fake auditor의
  자리표시자 `repro_spec`과 실재하지 않는 빌드/PoC 경로다.
- `docs/experiments/`에서 ASAN `ok=true` 또는 양수 E4를 찾는 느슨한 검색에도 실제 ASAN
  E4 run은 나오지 않았다. 따라서 **저장소에 기록된 실컨테이너 ASAN E4 도달은 0건**이다.
  이것은 성능 수치가 아니라 기록 유무를 센 값이다.
- 현재 `validate._call()`은 `repro_spec.steps`를 요청 argv에 싣지만, 컨테이너 러너의
  `plan()`은 그 argv를 실행하지 않고 workdir의 소스를 자체 링크한다. 기존 ASAN 경로의
  도달성 수리는 이 작업과 분리해 추적한다. 다만 이번 gdb 배선은 ASAN을 호출하거나 고치지
  않으므로 코드 배선의 선행 조건은 아니다([#326](https://github.com/0xM1yu/whitehat-boss/issues/326)). **실동적 도구가 E4에 도달한다고 주장하거나
  프롬프트에 gdb 사용 규칙을 넣는 일에는 ASAN 수리·실행 검증이 선행한다.**

### ptrace 권한 [Docker·Podman 실측 · 2026-09-28]

Docker 실측 환경은 Docker Desktop의 Linux/x86_64 엔진(Docker Engine 29.5.3)과 로컬
`uaf-note-verify:latest`(Ubuntu 24.04 · gdb 15.1) 이미지의 gdb다. Podman은 ATOM의 rootless Podman 4.9.3/aarch64에서
현재 브랜치의 `tools/harness-tools/Dockerfile`을 직접 빌드해 쟀다. gdb가 기존 프로세스에
attach하지 않고 자기 자식 프로세스를 `run`하는 이번 배치 경로만 비교했다.

| 런타임 | 권한 없음 | ptrace 권한 추가 | 판정 |
| --- | --- | --- | --- |
| Docker (`uaf-note-verify:latest` · gdb 15.1) | `/bin/true` 실행 완료. SIGSEGV 대상은 정지·전체 백트레이스 출력, `--return-child-result`를 쓴 gdb 종료 255 | 같은 두 실행과 같은 결과 | **자식 실행형 배치에는 `--cap-add=SYS_PTRACE` 불필요** |
| Podman | 정상 대상 exit 0. SIGSEGV 대상은 소스 줄·전체 백트레이스 출력, exit 1 | 같은 두 실행과 같은 결과 | **rootless 자식 실행형 배치에는 `--cap-add=SYS_PTRACE` 불필요** |
| Singularity/Apptainer | **미실측(0회)** — 로컬 실행 파일 없음, Seraph 접속 경로 확보 실패 | **미실측(0회)** | 판단 보류 |

두 Docker 실행 모두 gdb가 ASLR 비활성화를 시도할 때 `Operation not permitted` 경고를 냈다.
ptrace capability를 추가해도 같았다. 기본 스크립트는 `set disable-randomization off`로 그
시도를 하지 않고 현재 ASLR을 유지한다. 주소 고정은 이번 실측이 보증하지 않는다.

Podman 실측에서는 정상/크래시 두 대상을 capability 없음과 추가 조건에서 각각 한 번씩,
**총 4회** 실행했다. 두 조건의 stdout과 종료 코드는 각각 같았다. 그 전에 같은 v3 Dockerfile의
arm64 빌드도 통과했고, 빌드 안 gdb 연막은 정상 종료했다. 로컬에는 Podman 실행 파일이 없어서
SSH로 ATOM에서 실행했으며, 측정 뒤 임시 디렉터리와 `gdb-probe-20260928` 이미지는 지웠다.

Singularity는 로컬 실행 파일이 없고 `ssh seraph`가 호스트 이름 해석에 실패했다. 저장소가
교외 접속용으로 적은 포트 30080을 로컬 SSH 설정의 `163.180.160.167`에 대입한 접속도
`Connection refused`였다. 따라서 실행 횟수는 0이며 권한 판정도 내리지 않는다.

### 구현·검증 결과 [실측 · 2026-09-28]

- Fake·컨테이너 양쪽에 gdb를 `CRASH`로 배선했고, 컨테이너 계획은 디버그 심볼 컴파일 후
  `gdb --nx -batch --return-child-result -x /opt/gdb.batch -- /work/gdb.bin`을 실행한다.
  pwndbg는 설치·로드하지 않는다.
- `docker build --progress=plain -t harness-tools:v3 tools/harness-tools/`가 통과했다. 그 빌드
  로그에서 gdb 배치 연막 대상은 정상 종료했고, ASAN·clang-tidy·semgrep·인덱서 연막도 같은
  빌드에서 통과했다. gdb를 ASAN 연막 뒤에 둔 앞선 빌드 2회는 해당 `RUN` 단계가 exit 139로
  끝났다. 순서 변경 후 전체가 통과했다는 것까지가 실측이며 exit 139의 원인은 실측하지 않았다.
- `harness-tools:v3`와 `ContainerToolRunner`를 직접 쓴 테스트는 capability를 추가하지 않은
  기본 `SandboxSpec`으로 정상 C 프로그램(exit 0)과 SIGSEGV C 프로그램(non-zero·전체
  백트레이스)을 둘 다 실행했다. 테스트 결과는 1 passed였다.
- ATOM rootless Podman 4.9.3/aarch64에서도 v3 이미지 빌드와 capability 없음/추가 비교가
  통과했다. 정상 대상은 두 조건 모두 exit 0, SIGSEGV 대상은 두 조건 모두 exit 1과 소스
  줄·전체 백트레이스를 냈다. Singularity/Apptainer만 **0회/미실측**이므로 D92는 열림을
  유지하고 그 런타임의 ptrace 권한 필요 여부와 gdb 지원은 확정하지 않는다.
- **v3 이미지(gdb 12.1) Docker 재측정 [실측 · 2026-09-30].** `plan("gdb")` argv 그대로,
  capability 추가 없이(`--cap-add` 미사용) 정상 대상 **exit 0**, SIGSEGV 대상 **gdb 종료 255**
  (Docker Engine 29.5.3 · x86-64 — 이 장비의 Docker Desktop은 2026-10-01 확인 시 4.79.0 — 이미지
  `sha256:98b440ab…`). 즉 위 Docker 행의 255는 gdb 버전(15.1) 탓이 아니다 — 같은 x86-64에서
  gdb 12.1도 255다. ATOM Podman(aarch64)의 SIGSEGV 1은 **원인 미실측**이다 — ATOM 이미지의 gdb
  버전은 확인하지 않았다(v3 Dockerfile이 ubuntu:22.04 apt라 12.1일 것으로 **추정**할 뿐이다).
  SIGSEGV로 멈춘 대상에는 「원 종료 코드」가 없고 `Evidence.exit_code`에 남는 것은 gdb
  프로세스의 값이다.
- **스레드 형태의 신호 정지 [실측 · 2026-10-01].** 스레드를 한 번이라도 만든 대상이 신호로
  멈추면 gdb가 `Program received signal`이 아니라 `Thread N "이름" received signal`을 찍는다
  (gdb 12.1·15.1 같음, join 뒤 main이 죽어도 같다). 판정 규칙이 처음에 이 형태를 몰라 진짜
  크래시를 「띄우지 못했다」로 읽었다(독립 검토가 찾았다). 정규식에 그 갈래를 더했고, 실제 gdb로
  돌린 30개 시나리오 × 두 판(`tests/fixtures/gdb/thread_and_stderr_recordings.json`이 그중 9개를
  싣는다)에서 오판 0이다. ⏵ 2026-10-01 2차 검토: 이름 안의 CR은 gdb가 그대로 찍지만(gdb 12.1·15.1이
  comm을 `fgets`로 읽고 LF만 지운다) `_execute`의 text 모드 캡처가 LF로 바꿔 이름 자리가 못 넘었다 —
  진짜 크래시가 다시 「띄우지 못했다」가 됐고, 입력 쪽 변형이라 실컨테이너 테스트는 못 본다. 이름
  자리가 줄바꿈까지 받게 고쳤다(64자 묶음 그대로). CR 이름 8종·다른 구분 문자·15자 이름·`Thread 13`·
  출력 뒤 크래시를 22개 시나리오로 더 녹음해 그중 12개를 같은 JSON에 두 판씩 실었고, 저장된 실제 gdb
  stdout 434건(시나리오 163종 — 이 녹음들과 두 독립 검토의 녹음)에서 뜬 대상을 거절한 것은 0이다.
- **한계와 후속.** 판정이 gdb의 안내 문구(대상 수명주기 줄)에 기댄다 — 문서화된 인터페이스가
  아니고, 위 스레드 형태처럼 같은 판 안에서도 형태가 갈린다. 문구가 바뀌면 멀쩡한 실행이
  `ok=False`가 되는 쪽(fail-closed)이다. **후속: 빌드 시점 연막에 수명주기 줄 grep을 더한다** —
  이미지 재빌드가 필요해 이번에는 넣지 않았다.

## 선택지와 결정

### EvidenceKind

- **(a) `CRASH`를 재사용한다 — 채택.** 이번 gdb 도구의 목적은 디버거 아래에서 대상을
  실행해 크래시와 백트레이스를 기록하는 것이다. 기존 E4 런타임 근거 집합과 의미가 맞고
  스키마·직렬화 종류를 늘리지 않는다. 단, `ok=True`만으로 실제 기대 신호까지 보증하지
  못하는 문제는 [D80](D80.md)을 그대로 상속한다.
- **(b) `DEBUGGER`를 새로 만든다.** 디버깅 세션과 크래시 근거를 구분할 수 있지만, 게이트가
  이것을 E4로 볼지와 과거 직렬화 호환까지 함께 정해야 한다. ToolRunner 배선 범위를 넘는다.
- **(c) `SANITIZER`나 `BUILD`에 담는다.** gdb는 sanitizer가 아니고, 실행·백트레이스를 단순
  빌드로 부르면 근거 의미가 거짓이 되므로 기각한다.

### 실행 판정

- **(a) gdb를 실행류 도구로 넣고 ASAN처럼 컴파일 → 실행 두 단계로 돌린다 — 채택.** 컴파일 뒤
  `gdb --nx -batch --return-child-result -x /opt/gdb.batch -- <binary>`를 실행한다. 빌드 실패는
  컴파일 단계에서 끊긴 것으로(`len(steps) < total`, ASAN과 같다), 정상 종료·대상 신호 종료는
  gdb가 stdout에 남기는 대상 수명주기 줄로, 대상 기동 실패(gdb·컨테이너·대상이 안 뜬 경우)는
  그 줄이 **없음**으로 가른다 — ASAN과 달리 종료 코드로는 못 가른다(`return 127`·exit 255의
  두 뜻, 2026-09-30 실측).
- **(b) `_run_debug()`·별도 컨테이너 판정을 만든다.** gdb 출력에서 별도 구조화 필드를
  추출할 때는 필요할 수 있지만, 현재 네 갈래 판정은 `judge()`(빌드 끊김 검사와 gdb 갈래의
  stdout 수명주기 줄)로 충분해 별도 컨테이너 판정은 중복만 만든다.

### ptrace와 SandboxSpec

- **(a) `SandboxSpec`에 ptrace 필드를 추가하고 capability를 준다.** attach 모드에는 필요할 수
  있으나, 현재 Docker 자식 실행 실측은 필요 없음을 보였다. 기본 권한을 넓히므로 기각한다.
- **(b) 이번 자식 실행형 배치에는 capability를 추가하지 않는다 — Docker·Podman에 채택.**
  `SandboxSpec`도 바꾸지 않는다. Singularity는 실측 전이므로 지원을 확정하지 않는다.
- **(c) attach 모드를 별도 도구/샌드박스로 둔다.** 기존 PID namespace와 대상 프로세스를
  공유하는 설계, capability, seccomp를 함께 정해야 한다. 이번 범위 밖 후속이다.

### 이미지 태그

- **(a) 기본 이미지를 `harness-tools:v3`로 올린다 — 채택.** gdb 패키지와 배치 스크립트가
  이미지 내용·도구 능력을 바꾸므로 v2 태그를 덮으면 과거 run의 이름과 현재 내용이 갈린다.
- **(b) v2를 유지한다.** 같은 태그가 서로 다른 도구 집합을 뜻하게 되므로 기각한다.

## 닫히는 조건

1. Fake와 컨테이너 양쪽이 gdb를 허용하고 `CRASH` Evidence를 만든다.
2. 컨테이너 계획은 컴파일과 비대화형 gdb 실행 두 명령을 내며, 기본 경로에서 pwndbg를
   로드하지 않는다.
3. 정상 실행·대상 크래시(스레드 형태 포함)·대상 기동 실패 세 갈래는 녹음한 gdb 출력
   (12.1·15.1, `tests/test_gdb_lifecycle_judgement.py`)으로, 빌드 실패는 단위 테스트
   (`test_gdb_build_failure_never_counts_as_a_debug_session`)로 고정된다.
4. v3 이미지 빌드 시 gdb 배치 연막 검사가 통과한다.
