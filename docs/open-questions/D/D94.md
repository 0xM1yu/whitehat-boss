## 내용

### 관측 [2026-09-29 vast 51931415 · 원소별 진단 run · main `c2a8de0`과 같은 Case A]

줄 기준 판정(`measure_candidates.py`, 88.3% 계열)에서 main(#324 포함)이 놓친 7개를 CPG에 직접 질의해 진단.

| 원소 | GT 함수 | 호출 횟수 | hot | Case B 앵커 → GT 문장 최단 거리 |
| --- | --- | --- | --- | --- |
| inj_17 sink | `sql_resolved_append_text` | 3 | ○ | 12줄 |
| inj_19 sink | `dsync_ibc_stream_send_value_stream` | 3 | ○ | 6줄 |
| main_17 sink | `_dwarf_destruct_elf_nlaccess` | 6 | ○ | 10줄 |
| main_26 sink | `esp_do_nodma` | 3 | ○ | 18줄 |
| main_27 source | `GetHttp1HeaderData` | 2 | ○ | 9줄 |
| main_33 source | `block_skip_read` | 47 | ○ | 8줄 |
| main_38 sink | `end_query` | 8 | ○ | 13줄 |

- 7개 모두 매개변수 있음 · hot(WRITER/EXEC 호출 또는 index/field/deref 대입) · 호출 2회 이상 -> `CASE_A_CALL_LIMIT = 1`에 걸려 Case A 탈락
- 7개 모두 GT 함수 안에 Case B 앵커는 있으나 GT 문장 ±3줄 밖 -> 줄 기준 판정의 창 밖
- main_17만 GT 줄에 derefWrite·free 패턴이 걸리는데도 후보 없음 -> 함수당 앵커 예산(#311)에서 잘린 것으로 추정, 미확인

### 기제 [코드]

`candidates_a_query`의 `api` -> `cpg.call.nameExact(m.name).take(LIMIT + 1).size <= LIMIT` 필터로 두 번 이상 불리는 메서드를 통째로 뺌. 원래 목적은 흔한 이름(`read` 등)의 폭증 막기. hot인지는 안 봄.

## 왜 위험한가

recall 천장. 여러 곳에서 불리는 메모리 쓰기 함수가 곧 흔한 취약 지점인데 Case A에서 체계적으로 빠짐. [D91](D91.md)의 「앵커 패턴 공백」으로 보였던 다섯도 실제 원인은 이쪽.

## 선택지

- **(a) hot이면서 두 번 이상 불리는 메서드를 별도 목록으로 Case A에 추가, 유계 둘** -> 호출 횟수 상한 `CASE_A_HOT_CALL_MAX`(64, GT 최대 47을 보고 정한 초기값) · 추가 개수 상한 `CASE_A_HOT_EXTRA_CAP`(2000, 호출 적은 것부터). 기존 `api`와 그 cap은 그대로라 이미 뽑힌 후보가 안 밀림. **권장**
- **(b) `CASE_A_CALL_LIMIT` 상향** -> hot 아닌 흔한 함수까지 들어와 후보 폭증. 원래 필터의 목적과 충돌
- **(c) Case B 앵커 확장으로 GT 문장 자체를 잡기** -> [D91](D91.md)의 길. 프로젝트별 패턴이라 개별적·유지비 큼

**이 수가 말하지 않는 것**

- (a)의 두 상한은 **이 평가셋의 미포착을 보고 정함** -> 평가셋 밖 일반화는 미확인

## 대조군 — 2026-09-29 (과적합 확인)

(a)를 이 평가셋의 미포착을 보고 설계했으므로, 「후보를 늘린 것」과 「hot 신호」를 가르려고 대조군을 잼.

**대조군** -> (a)와 같은 조건(매개변수 있음 · 호출 2~64회)의 메서드를 **hot 여부 없이** 결정론적 무작위 순서(메서드 id 해시)로, 샘플마다 (a)의 추가 목록과 **같은 개수**만큼 넣음. 측정용이라 저장소에는 없음. 같은 박스(vast 51931415)·같은 판정

- **(a) 효과의 절반 이상은 후보 증가 몫, hot 신호가 더한 몫은 +3(inj_17·19 · main_33)**
- hot 신호 근거 -> 조건 풀의 hot 비율은 약 38%(2,902/7,664, 계산값)인데 GT 7개는 전부 hot. 우연히 이럴 확률 0.38^7 ≈ 0.1%(계산값). 단 메모리 안전 GT가 메모리 쓰기 함수에 몰리는 건 어느 정도 예상된 일
- **과적합 판단** -> 100%는 후보 +34%와 이 평가셋에 맞춘 설계 위의 수. 신호 자체(hot)는 평가셋 밖에서도 의미 있을 가능성이 크나, 평가셋 밖 recall은 미측정

## 닫히는 조건

level-3 전체 실측에서 회복 7의 슬라이스가 GT 문장을 품는지 확인하고, 후보 증가의 level-3 비용을 잰다. 그 전에는 열림.
