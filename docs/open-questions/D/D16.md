## 내용

`.inc`가 `ArtifactKind.SOURCE`가 되면서(D13) 인덱서는 보게 됐지만 **semgrep은 여전히 보지 않는다.** 2026-08-20 실측(semgrep 1.173.0, 로컬 룰 `pattern: strcpy(...)` / `languages: [c]`): 디렉터리(`target.c` 28B + `session_core.inc`)를 주면 exit 0, `results` 0건, `paths.scanned`에 **`target.c`만**. `.inc`를 직접 주면 exit 0, `results` 0건, `paths.scanned`가 **빈 목록**. 같은 내용을 `session_core.c`로 **이름만** 바꾸면 exit 1에 strcpy 1건이 잡힌다 — 즉 코드가 아니라 확장자 때문이다. **`errors`도 `skipped`도 비어 있다**: 인덱서는 못 읽은 파일을 `skipped`로 세지만 semgrep은 세지 않는다. 그래서 `judge_semgrep()`은 결과 문서가 있고 크래시가 없으므로 `ok=True, exit_code=0`을 내고, `with_signal()`이 그것을 걸러 **"정적 신호 없음"으로 기록된다** — 도구가 파일을 아예 안 본 것과 봤는데 깨끗한 것이 구별되지 않는다. clang-tidy에는 이 문제가 없다(`target.c`를 주면 전처리가 `.inc`를 펼쳐 진단 위치가 `.inc:NNN`으로 나온다) — **지금 `.inc` 코드에 정적 신호를 낼 수 있는 것은 clang-tidy 뿐이다.** 선택지: (a) semgrep이 `.inc`를 C로 보게 만드는 방법을 찾는다(확장자→언어 매핑을 사용자에게 여는지 미확인) (b) `.inc` artifact에는 semgrep을 돌리지 않고 "해당 없음"으로 남긴다 (c) **`paths.scanned`가 대상 파일을 포함하는지 검사해 포함하지 않으면 `ok=False`로 내린다** — 지금 결여된 것은 "도구가 그 파일을 실제로 봤는가"라는 사실 자체이므로 D11의 (a)(`Evidence.findings`)와 같은 방향이다. **함께 생긴 것**: `.inc`가 분석 대상이 되면서 `target.c`와 `session_core.inc`가 같은 코드에 대해 후보 2개를 만들고, `.inc` artifact의 clang-tidy는 `compile_sources`가 비어 `ok=False`("컴파일할 C 소스가 없다")가 된다. 후자는 거짓 신호는 아니다 — 게이트가 `ok=False`를 제외만 하고, `.inc`를 컴파일러에 넘긴 것이 아니라 넘길 것이 없는 상태다
