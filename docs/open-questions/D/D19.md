## 내용

**2026-08 부분 해소.** 프롬프트 본문이 `{run_dir}/prompts/`에 남게 됐다(D19 구현). 남은 것: W1 실행 검증(③)이 auditor 실서빙·D20에 걸린 것과 재시도 본문 미보존(D49). `context.py`는 `model_call` 이벤트에 `prompt_version`만 싣고 프롬프트 본문은 어디에도 쓰지 않는다. run_dir에 남는 것은 `run_manifest.json`(runner) + `trace.jsonl`·`report.md`(+`report.sarif.json`)(cli)인데 **그 어느 것도 프롬프트를 담지 않는다.** 그래서 "캡슐 섹션 본문이 프롬프트에 실린다"(W1)의 **증거가 픽스처와 Fake 모델로 뽑은 테스트 덤프뿐이고**, 실제 run에서 그 주장을 확인할 방법이 없다 — 실모델·실도구 run에서 무엇이 모델에게 갔는지는 사후에 답할 수 없다. 이것은 evaluation.md §4 누출 방지 표 7행 중 **Prompt Logging**과 같은 구멍이고, R3의 미구현 5개에 이미 들어 있다(그쪽은 누출 검증 관점, 이쪽은 측정 가능성 관점). **배관이 붙는 일이다**: `RunContext`가 run_dir을 모르므로 경로를 넘기는 인자가 하나 늘거나 훅이 하나 는다. 누출 스캐너 대상이 `prompts/`에서 run 산출물로 넓어지는 것도 함께 판단해야 한다 — 별도 PR. **2026-08-22 — 구현했다.** `{run_dir}/prompts/NNNN_{role}.md`에 prefix+body 전체가 남고 `model_call`이 `prompt_ref`(run_dir 상대)·`prompt_sha256`으로 가리킨다. trace `data`에 본문을 싣지 않은 이유는 셋이다 — (a) `canonical_line()`이 `ts`·`wall_ms`만 빼므로 본문이 **재현성 비교 대상**이 되고, 그것은 D14가 아직 열어 둔 축(`_canonical`을 `data`까지 확장할 것인가)에 답을 만들어 버린다 (b) `trace.jsonl` 한 줄이 수 KB가 된다 (c) `Evidence.payload_ref`가 도구 출력에 대해 이미 같은 모양을 쓴다(`container_tools`). **응답은 남기지 않는다**(⏵ 2026-10-11 — 예외: 스키마 소진·게이트웨이 거절로 끝난 호출의 스키마 실패 시도 원문은 `…_response[_retryK].txt`로 남는다. 재시도가 성공한 호출의 앞 시도 원문과 성공 응답은 안 남는다, 이슈 #603) — `Candidate`·`Finding`·`Decision`이 이미 `state.db`에 있고 usage는 `model_call`에 있다. 사본을 만들면 정본을 물어야 한다. **호출이 실패해도 남는다**(호출 전에 쓴다) — 실패 분기가 "스키마 파싱 실패율"의 분자인데 그 입력이 없으면 조사할 수 없다. **`prompts/` 산출물이 누출 스캐너 기본 대상에 들어갔다**(`eval/leakage/__main__.py` — ⏵ 2026-10-11 `*/prompts/*.md`만이다: #603의 `…_response*.txt`는 `RUN_GLOBS` 밖이다) — 이제 CVE·문제명 마스킹 검사가 템플릿이 아니라 **실제 모델 입력**에 걸린다. **남은 것**: §4 표가 요구하는 "로그 존재 검사"는 미구현이다(R3 — 누출 자동 검증 스크립트 부재). / **용량 상한을 재지 않았다** — 콜당 실측은 ATOM run ≈4.4 KB(input 4,389토큰/4콜), 로컬 `dev_docker` 스모크 2.4~4.8 KB뿐이고, 캡슐 예산(scout 4,000 / auditor **18,000**토큰 — 2026-08-25 24,000에서 축소, D21)이 큰 실대상에서 얼마가 되는지는 그 run을 돌려야 나온다 — D17의 2배 계상 때문에, 그리고 **대상 원문이 예산 밖에서 따로 실리기 때문에**(D21) 프롬프트는 캡슐 예산보다 크다. prefix가 역할마다 중복 기록되므로 큰 대상에서 줄일 여지가 있으나 **그것이 필요하다는 측정이 아직 없다**(D15와 같은 논법). **W1 검증 상태 — 세 층 중 둘이 확인됐다.** ① 캡슐에 본문이 실린다: `run_20260821_0004`의 `expanded` 캡슐 `callees.body` = `["handle_header parser.c:25", "memcpy parser.c:24"]` — 확인. ② **그 본문이 렌더된 프롬프트에 실린다: `run_20260821_0007`에서 확인됐다** — `graph_index status=loaded`(심볼 4·호출 5)인 상태에서 `memcpy parser.c:24`를 담은 프롬프트 파일이 `0002_auditor.md` **하나뿐**이었다. **이 층은 D19 이전에는 물을 수조차 없었다** — 프롬프트가 산출물에 안 남았기 때문이다. ③ 실모델이 그것을 보고 판단한다: **여전히 미확인**. 그 프롬프트를 받은 auditor가 이번에도 Fake였다(`single_gpu_12g`는 scout만 실서빙한다). **③를 여는 경로는 둘이다**: **(가) D20을 (a)나 (b)로 정한다** — 그러면 scout이 그래프를 받고, scout은 이 프로필의 유일한 실서빙 역할이므로 **`single_gpu_12g` 그대로 ③가 열린다**. **(나) auditor가 실서빙되는 프로필로 돈다**(`local_balanced`·`b1_single`) — D20과 무관하게 열린다. 즉 이 프로필로 ③를 못 여는 것은 **D20이 (c)로 확정될 때뿐**이다
