### 관측 2 — Auditor 입력에서도 GT 함수를 밀어냄 [2026-10-01 · vast 2대 · main `b53de80` 하네스 · s500 실패 표본 중 저장소 전체 8개]

같은 꼬리가 Scout 몫만이 아니라 **Auditor `SOURCE`에서도 GT 함수를 밀어냄**(#349 옵션 실측 중 발견)

- Auditor `SOURCE` 상한을 20k 토큰까지 올려도 GT 지점이 안 실린 GT 보는 슬라이스 7개(libucl 5 · gifsicle 2) 중 6개가 이 모양 -> 슬라이스가 6,500~7,800줄 · 함수 100~350개를 걸침 · 20k에서도 상한에 빠진 함수 37~304개
- 하네스 빌더는 걸친 함수를 (파일, 줄) 순으로 상한까지 실음 -> GT 함수가 뒤쪽이면 빠짐(빌더 순서 문제는 #349 쪽)
- 나머지 하나(libucl `slice_0228`)는 이 꼬리가 아니라 인덱스 미커버(매크로가 만드는 함수 `KHASH_INIT`)
- ⚠ 8표본 · GT 보는 슬라이스 30개, 실패 표본만 고른 편향 표본 -> 비율로 일반화 안 함. 원자료 저장소 밖 로컬 `measure_results/s500_whole/` · run ID 없음

### 기제 [코드]

- `src/orchestrator/nodes/scout.py` -> 슬라이스 렌더(`read_slice`)를 자르지 않고 `SOURCE`에 통째로
- 슬라이서는 Scout 몫을 모름 -> 역추적(`--backward-depth`·`--backward-nodes`)과 context 고정점이 줄 수 상한 없이 키움
- 몫을 넘는 프롬프트가 서빙에서 크기 거절(413 · 컨텍스트 초과 문구가 실린 400)되면 그 후보 하나만 폐기 -> `runner._is_size_rejection`이 참이라 `_drop`이 연속 폐기 차단기를 안 올림([D88](D88.md) · #296). run은 계속

## 왜 위험한가

- 그 슬라이스는 Scout 판단을 한 번도 못 받음 -> GT를 품어도 recall로 안 셈(main_38·main_33 sink)
- 같은 run에서 몫 초과 후보마다 요청 한 번씩 거절됨 -> run은 안 멈추지만 그만큼 서빙 시간을 씀
- level-3 시간을 쓰고 결과는 못 씀

## 선택지

- **(a) 슬라이서가 Scout 몫에서 멈춤** -> context 확장 중 렌더 크기가 몫을 넘으면 멈추고 표시(앵커 주변만 남김 또는 degraded). 몫 안에 들 수 있는 슬라이스를 자르지 않게 기준은 토큰(또는 여유 둔 글자)
- **(b) 하네스가 Scout 전에 줄임** -> 렌더가 몫을 넘으면 entry 주변·데이터 의존 줄 우선으로 잘라 넣음. 슬라이서는 그대로
- **(c) 역추적 상한 조임** -> `--backward-nodes`·깊이를 낮춤. 단순하나 GT를 담던 경로도 끊김(main_38 sink는 호출자 쪽으로 올라가 담김) -> level-3 recall(크기 조건)로 재야 함
- **(d) 안 고침** -> 몫 초과 슬라이스는 Scout가 못 받는 채로 둠

## 닫히는 조건

선택한 안을 넣고 같은 평가셋 샘플로 level-3 판정(GT 포함 + Scout 몫 이하)을 다시 잼 -> 몫 초과 수 0 · 크기 조건 포착이 안 줄어야 함.
