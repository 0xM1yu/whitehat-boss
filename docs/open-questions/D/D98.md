## 내용

### 기제 [코드]

- 게이트 E3(`validated`) 조건 = `p2 and upheld and repro_spec is not None`(`gate.evaluate`). 8단계(`_run_pov`·`validate.run`)는 `validated` 이상만 돈다(`runner`. ⏵ 2026-10-04 — `thresholds.pov_attempt_top_n`이 양수면 `_run_pov`는 `validated` 밖의 Finding도 돈다. `validate.run`은 그대로다)
- Auditor 모델이 `Finding`을 내는데 `repro_spec`은 모델이 채운다. CyberGym Level 1 과제 입력은 저장소 + 설명뿐이고 **재현 방법을 안 준다**(`task_loader`) -> 모델이 `repro_spec`을 비워 냄 -> E3 못 받고 F-9(`repro_spec_missing`)로 `hypothesized`에 멈춤
- 결과 -> 8단계가 **0건**. PoC가 하나도 안 만들어져 채점 서버에 보낼 것이 없다. 「모델이 못 찾아서 0점」이 아니라 「배선이 없어 시도조차 안 함」

### 수정 [이 PR · 기본 꺼짐]

- `ReproOrigin{model, harness}` + `ReproSpec.origin`(기본 `model`) 신설. 모델이 낸 명세는 `origin=model`로 덮고(참칭 방지 — 발급값 도장 #279와 같은 결), `synthesize_repro_spec`이 켜졌고 모델이 비워 냈으면 후보 위치로 합성한다(`origin=harness`, `auditor._ensure_repro_origin`). 합성 명세는 E3까지 올라가 8단계가 돈다
- **등급은 출처로 안 갈린다** -> `gate.evaluate`의 `p3`·`p4`는 그대로다. E4(`proven`)는 출처와 무관하게 실행 로그(runtime Evidence, `p4`)를 요구하므로 합성 명세만으로는 proven이 안 된다(아무것도 실행 안 됨). 게이트는 `repro_is_harness`를 `gate_eval` trace에만 싣는다
- 합성 자체는 `repro_spec_synthesized` 이벤트로 남긴다. 기본 꺼짐이라 켜지 않은 run은 종전과 동일(F-9)

### 검증 [2026-10-02 · 로컬]

- 단계 0(채점 경로 증명, arvo:1065 libmagic MSan) -> 저자 정답 PoC가 「vul 터짐(77) + fix 안 터짐(0)」 판정. 채점 경로 자체는 작동(S6b·S11 설계 근거). ⚠ 채점 호스트 `vm.mmap_rnd_bits<=28` 필요 — 32면 MSan 과제가 입력 무관 segfault로 정답도 오판. 로컬 · run ID 없음
- 이 수정은 아직 end-to-end run에서 8단계가 실제로 PoC를 내는 것까지는 안 봄(dev_fake 단위·게이트 단위만) -> 「닫히는 조건」 참조

## 왜 위험한가

- 8단계가 한 번도 안 돌아 PoC·채점이 0건 -> 벤치마크 점수가 구조적으로 0
- 합성 명세를 `validated`로 올리면 「모델이 재현법을 제시하고 critic이 인정함」이라는 `validated`의 뜻이 약해진다 -> `origin`·`repro_is_harness`로 그 약함을 **데이터에** 박지 않으면 비교표가 두 경로를 못 가른다
- 잘못 넓히면 아무것도 실행 안 된 Finding이 `proven`으로 찍힐 수 있다 -> 그래서 등급은 출처로 안 올리고 E4는 실행 로그를 그대로 요구한다
- ⏵ **2026-10-05 정정 — 아래 줄의 기제 서술이 낡았다.** `gate`의 `p4`는 런타임 Evidence의 종료 코드가 **0도 `None`도 아닐 것을 이미 요구한다**(좁은 절반은 [#401](https://github.com/0xM1yu/whitehat-boss/issues/401)이 닫았다 — [D80](D80.md)의 2026-10-02 ⏵와 [build-plan.md](../../build-plan.md) §11.5의 2026-10-04 ⏵가 든다). 그리고 **합성 명세가 먹이는 술어는 `p4`가 아니라 `p3`**다 — E3(`validated`)에 들어가고 `p4`(E4 = `proven`)는 `repro_spec`을 읽지 않는다. 그래서 합성으로 날 수 있는 거짓 등급은 **`validated`**이고 `proven`이 아니다. 남은 한계 둘은 **비-0 종료가 크래시의 대용 지표**라는 점과 **`expected_signal` 미대조**다. 아래 줄은 등재 시점의 기록으로 둔다
- ⚠ **합성을 켜면 [#232](https://github.com/0xM1yu/whitehat-boss/issues/232)(D80)가 잠복에서 도달 가능으로 바뀐다**(#393 리뷰 MEDIUM-1) -> 전엔 8단계에 아무것도 안 올라와 #232가 닿을 수 없었다. 합성이 Finding을 `validated`로 올려 8단계가 도구를 돌리는데, `gate`의 `p4`가 `ok=True`만 보고 크래시(non-zero)와 exit 0을 안 가른다(`container_tools` — 크래시는 실패가 아니라 신호) -> 크래시 0건으로 proven이 날 수 있다. **켜기 전에 #232를 먼저 본다.** 합성 명세로 돌린 asan은 추출 트리를 ASan으로 새로 빌드한 것이라 채점 이미지와 다른 바이너리이고, 점수는 oracle이 정한다(S6b)

## 선택지

- **(a) `ReproSpec.origin` 필드** (이 PR) -> 출처를 데이터에 박아 비교표가 가른다. 스키마에 노출돼 모델이 참칭할 수 있어 하네스가 덮는 수고가 든다
- **(b) trace 이벤트만** -> 스키마 불변, 그러나 산출물(Finding)에는 출처가 안 남아 run 기록만으로 두 경로를 못 가른다
- **(c) 합성한 명세의 `steps`를 과제에서 더 정확히** -> 지금은 후보 위치로 generic. 진입점(#380 `fuzz_entrypoint`)을 쓰면 더 맞는 명세. #380 머지 뒤 후속
- **(d) 안 고침** -> Level 1에서 8단계가 영영 안 돈다(점수 0 고정)

## 닫히는 조건

`synthesize_repro_spec`을 켠 end-to-end run에서 Level 1 과제의 Finding이 `validated`에 올라 8단계가 실제로 돌고(PoV 루프 진입·`pov_generated`/`pov_skipped` 관측), 그 PoC가 채점 경로(S6b)까지 닿는 것을 한 번 확인한다. 등급이 출처만으로 `proven`에 오르지 않는 것도 같이 본다.
