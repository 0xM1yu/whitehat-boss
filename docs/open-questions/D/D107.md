## 내용

### 기제 [코드]

- `Finding.cwe`·`AuditProcedure.cwe`가 `Cwe`(`^CWE-\d+$`) -> null 불가
- `no_signal` = 뿌리 원인을 못 세운 판정 -> 참인 CWE가 없음
- v10 산문은 「후보 CWE가 주어지면 유지」만 적음. `Candidate.suspected_cwe`는 빈 리스트일 수 있음(기본값 `list`) -> 그때 `CANDIDATE` 블록은 `추정 CWE: (없음)` -> 모델이 쓸 참인 값이 없는데 스키마가 null을 거절 -> 지어냄
- v8·v9도 같음. v10 첫 판 산문은 `"cwe": null`을 적었는데 스키마가 거절해 v9 규칙으로 되돌림(PR #521) -> 결함을 그대로 물려받음

### 그 값을 읽는 자리 [코드]

여섯
- `src/cli.py` SARIF `ruleId`
- `nodes/critic.py` 반박 요청 `CLAIM`
- `nodes/pov.py` Finding 서술(옛 판 · 넓은 판 두 줄이 한 함수 `_cwe_label`)
- `nodes/report.py` 중복 제거 키(`_dedupe_key`)
- `nodes/report.py` 항목 줄(`_entry`)
- `tools/probe/critic_output_budget.py`가 Critic `CLAIM`을 되만듦

⚠ 이슈 본문은 보고서 쪽을 「정렬 키」라 적지만 `_dedupe_key`는 **정렬되지 않고** 키 소속만 봄(`dedupe_with_merges`의 `seen` — 키 → 대표 id `dict`). 순서는 `_rank`(등급 · `finding_id`)

### 관측 [미측정]

- 후보 `suspected_cwe`가 비는 비율 -> 안 잼
- 그때 모델이 무엇을 쓰는지 -> 안 잼. v10으로 돈 run 1건([10-08 run](../../experiments/harness/2026-10-08-first-real-serving-run-arvo1065-vastai-remote.md))에 `no_signal` 1건(`cand_0004`)이 있으나 보고서가 그 `cwe`를 안 적음 -> 미확인

## 왜 위험한가

- CLAUDE.md §0 -> 지어낸 CWE가 SARIF 규칙 ID와 보고서 묶음 키로 갈 수 있음(실제로 지어냈는지는 위 「관측」대로 미측정)
- SARIF 소비자는 `ruleId`로 같은 규칙끼리 묶음 -> 없는 약점이 규칙으로 집계됨

## 선택지

1. `Finding.cwe`를 `Cwe | None`으로 넓힘 -> 읽는 자리를 같이 고침, 옛 행 호환 확인
2. `AuditProcedure.cwe`만 `no_signal`에서 nullable, 하네스가 채움 -> 무엇으로 채울지가 같은 질문(후보 CWE가 없으면 답이 없음)
3. non-null 유지, 하네스가 후보 CWE로 덮음 -> 후보에 CWE가 없을 때 답이 없음
4. 그대로 둠 -> 지어낸 값이 계속 SARIF·묶음 키로 감

## 결정 [2026-10-09 · 사용자 결정]

1 -> 이 등재와 같은 PR

- **스키마**: `cwe`는 `trigger_status`가 `no_signal`일 때에만 `None` 가능. 다른 상태에서 `None`이면 거절(`Finding`·`AuditProcedureNullableCwe` 각자 검증기). 반대 방향(`no_signal`이면 `None`이어야 함)은 안 걸음 -> v1~v10 Finding은 `no_signal`에도 CWE 문자열을 들고 저장돼 있고 다시 읽혀야 함
- **요청 바이트**: `Finding.cwe`의 JSON 스키마는 종전 그대로(`WithJsonSchema`) -> `Finding`을 요청하는 한 방 판·`AuditorAction`(v8·v9)·`AuditorProcedureAction`(v10)의 `model_json_schema()`가 바이트 동일. `audit`의 `SkipJsonSchema`와 같은 규율
- **새 판 v11**: v10의 `AuditProcedure`를 넓히면 v10 요청 바이트가 바뀜 -> 한 판 번호가 두 요청을 가리킴(agent-contracts §4 규칙 1). 그래서 형제 봉투 `AuditorProcedureNullableCweAction` + 최종 답 `AuditProcedureNullableCwe`(`AuditProcedure`의 서브클래스, `cwe: Cwe | None`) -> v10이 `AuditorAction`을 안 고치고 형제를 둔 선례와 같음. prefix는 v10에서 `cwe` 서술 네 줄만 바꿈. 서빙 좌석 `qwen3.8-27b`를 v11로 올림
- **읽는 자리**: CWE가 있으면 렌더가 종전과 바이트 동일, `None`일 때만 다름
  - SARIF -> `ruleId`를 CWE 꼴이 아닌 센티넬 `no-cwe`로 둠. `ruleId`는 스키마상 선택(`result.required`는 `message`뿐)이지만 규범 본문은 조건부 SHALL -> OASIS SARIF 2.1.0 §3.27.5 *"If `rule.id` is absent, `ruleId` SHALL be present"*, 이 결과는 `rule`을 안 실음 -> 키를 빼면 규범 위반(⏵ 2026-10-10 정정: 첫 판은 키를 뺐다 · 적대적 리뷰 M1)
  - 보고서 항목 줄 -> `CWE 없음`
  - 중복 제거 키 -> `(None, 파일, candidate_id)`. `no_signal`은 `audit`가 null이라 `path=[]`가 늘 -> `_target_symbol`이 대상 함수가 아니라 **모델이 쓴 제목**으로 떨어짐 -> `(None, 파일, 제목)`이면 다른 후보의 부정 결론이 제목만 같아도 한 건이 됨. 그래서 셋째 칸을 후보 ID로 둠 -> 같은 후보 둘만 한 건, 다른 후보·같은 자리의 CWE 있는 Finding과는 별건. CWE 있는 키는 종전 그대로(⏵ 2026-10-10 · 적대적 리뷰 H5 — 첫 판 서술의 「같은 대상 함수의 `no_signal` 둘」은 `no_signal`에 대상 함수가 없어 일어날 수 없는 모양이었음). 실제 제목 분포는 미측정
  - Critic `CLAIM` -> `<제목> (CWE 없음)` · PoV -> `CWE: (없음)`(Auditor 후보 서술과 같은 표시)
- **저장 호환**: 저장은 JSON 블롭이라 칼럼 제약 없음. CWE 문자열이 든 옛 행은 그대로 읽힘
- **관측**: v11 `answer` 홉이 `no_signal`인데 `cwe`가 있으면 `cwe_present_on_no_signal` 키(`nodes/auditor._answer_observed`). v11 답(`AuditProcedureNullableCwe`)만 셈 -> v8~v10은 계약이 non-null이라 규칙 준수. `audit is None` 조기 반환 앞에 둠(`no_signal`은 늘 `audit is None`) · ⏵ 2026-10-10 적대적 리뷰 H2

## 한계

- `no_signal`에 CWE 문자열을 내는 것은 스키마가 안 막음 -> 산문만 null을 시킴. 위반 비율은 안 잼(거절하면 최종 답을 통째로 재생성하는 비용)
- v10 이하로 저장된 `no_signal` Finding의 CWE가 지어낸 값인지는 못 가름 -> `produced_by.prompt_version`으로 판을 가를 뿐
- v11이 `no_signal`에서 실제로 null을 내는지 -> v11로 돈 run 0건, 미측정
- **효과는 아직 안 잼** -> 이 D는 구조(스키마·판·읽는 자리·관측 키)로 닫고, 효과(null 산출률 · `suspected_cwe` 공백률 · `cwe_present_on_no_signal` 비율)는 v11 첫 실서빙 run에서 봄 -> 후속 이슈로 추적(D104 선례)
- 테스트는 철자·바이트를 묾 -> 모델 행동은 안 묾. v11 prefix는 「v10 줄에서 `cwe` 조각만 바꾼 것 = v11 줄 전체」 등식으로 묾 -> 덧붙인 반대 문장도 죽음. 그 문장을 모델이 따르는지는 못 묾
- **단방향 문** -> `cwe=None` 행이 든 `state.db`를 이 변경 **전** 코드로 열면 `Finding` 검증이 거절해 `query("finding", …)` 전체가 `ValidationError`로 죽음(행 하나가 쿼리 전체를 막음). 반대(옛 행 -> 새 코드)는 정상. 롤백·구버전 체크아웃의 비용이고 가드 없음
- **문법 대 파싱 비대칭** -> `triggerable` + null `cwe`는 v10에서 문법·파싱 모두 거절이었는데 v11에서는 **문법 통과 · 파싱 거절**(`anyOf[string, null]`은 상태와 안 묶임) -> 제약 디코더가 낼 수 있는 출력이 `retries` 뒤 `schema_parse_failed`로 떨어짐. 이 길을 가를 계측 없음. 같은 부류(`audit` null ⟺ `no_signal`)가 v10에 이미 있어 종류가 새롭지는 않음
- 서빙 제약 디코더가 `anyOf[{type:string, pattern}, {type:null}]`를 받는지 -> 서빙 스키마에 pattern-in-anyOf 선례 없음, 실서빙 미확인

## 닫히는 조건

스키마 · v11 판과 배선 · 읽는 자리 여섯 · 관측 키가 들어가고 테스트가 null 허용·거절, 읽는 자리의 `None` 렌더(`no_signal` + CWE 문자열 모집단 포함), v8·v9·v10·한 방 요청 스키마 바이트 동일, 관측 키를 묾 -> 이 등재와 같은 PR. 효과 측정은 이 조건 밖(위 「한계」)
