## 내용

~~지금은 `queue.py`가 **run 범위 in-memory 카운터**로 들고 있었다~~ → **2026-08-31 D25 (b)로 그 카운터가 사라졌다.** 이제 재평가 횟수를 **아무 데도 보관하지 않는다** — `policy.py:191`이 `requeue_count` 신호를 읽지만 그 값을 만드는 코드가 저장소에 없다(테스트만 만든다). 질문은 그대로 열려 있고 **답이 "in-memory"에서 "없음"으로 바뀌었다.** Candidate는 SQLite에 `queued`로 남지만 "몇 번 재평가됐는지"는 run이 끝나면 사라지므로, 다중 run·resume에서 `requeue_limit_reached` 전이가 성립하지 않는다(매 run이 0부터 센다). 선택지: (a) `Candidate.requeue_count` 필드 추가 (b) StateStore에 run 밖 카운터 테이블 (c) 단일 run 전제를 명문화하고 resume 비지원 확정 — **현재 코드는 (c) 가정**. (a)는 `src/schemas/` 변경이라 전원 공지 대상. **resume를 지원하게 되면 스키마 버전 문제도 함께 풀어야 한다**: `adapters/sqlite_store.py`가 `model_validate`로 객체를 되읽으므로 구버전 `state.db`의 `RunRecord`는 필수 필드(`repo_dirty` 등) 누락으로 로드에 실패한다. 지금 안전한 이유는 호환성이 있어서가 아니라 `state.db`가 run 디렉터리 안에 있어 **구버전을 읽는 경로 자체가 없기** 때문이다. resume 설계 시 마이그레이션 또는 버전 게이트가 필요하다
