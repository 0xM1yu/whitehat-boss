# D59 — Critic과 Auditor가 다른 계열이어야 한다는 조건을 강제하는 장치가 코드에 없다

## 내용

`evaluation.md`가 B3/B3′의 **조건**으로 못박은 "Critic은 Auditor와 다른 제작사"를 **검사하는 코드가 저장소에 하나도 없다**. 지금은 사람이 프로필을 손으로 맞추는 것이 유일한 방어다. **지금 위반하는 프로필은 없다** — "틀렸다"가 아니라 **"틀려도 아무것도 안 잡는다"**는 항목이다.

**기제**: 요구는 네 곳에 문장으로 있으나(evaluation.md:21 "제작사가 다른 모델", model-serving.md:31, profiles.yaml:309-310, critic.py:1) 강제하는 것이 없다 — `ModelEntry`(config.py:115-142)에 계열·제작사 필드가 없고(9필드 전부 무관), `ProfileEntry` 검증기 둘(`_has_required_roles`·`_hybrid_needs_retrieval_roles`)은 auditor↔critic을 대조하지 않으며, `src/`·`config/`에 `family`/`vendor`/`제작사` 0건, `doctor` 8검사에도 없고 `run`은 `doctor`를 안 부른다. #118 리뷰 검증 중 "누가 보장하는가"를 찾다가 확인.

**왜 중요한가**: 어긋나면 조용히 어긋난다 — 프로필 한 줄로 Critic이 Auditor와 같은 계열이 되어도 아무도 경고 안 하고, 그 run은 `B3prime@…` 라벨을 달고 완주하며 **registry에 두 모델이 같은 계열인지 판정할 필드가 없어 사후에도 자동으로 못 가린다**. 같은 형태(served-model-name 미검증으로 Qwen3-0.6B를 4B로 서빙, 2026-08-18)가 이미 실현된 전례다. **타이밍**: 모델 로스터가 곧 확정되고(보류 8건) 새 프로필이 들어오는 그때가 위험 지점이며, build-plan의 Scout 분업이 모델 수를 늘리면 손 방어는 더 약해진다.

**선택지**: (a) `ModelEntry`에 계열 필드 + `ProfileEntry` 검증기 — 강제력 최강이나 registry 10항목 채우고 **"계열" 정의를 정해야 한다**(foundation-sec-8b는 Cisco 배포·Llama-3.1 계열이라 제작사/베이스로 답이 갈린다). (b) `doctor` 검사만(`_check_family_split`, WARN) — config 불변 그러나 `run`이 `doctor`를 안 불러 안 볼 수 있다(#119가 같은 문제로 `run` 진입에 검사 이동). (c) 조건 라벨로 — `B3*`면 다른 계열, `B1*`이면 같은 것 허용(B1이 의도적으로 auditor==critic이라 단순 부등은 못 씀); `condition`이 run 인자라 검사가 `cli.run`이 된다. (d) 현행 유지 + 주석만.
