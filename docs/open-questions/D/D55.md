## 내용

**2026-08-29 실측**([v2 스모크 보고서](../../experiments/harness/2026-08-29-prompt-v2-smoke-atom.md) §5 해석 ⑥). `openai_compat.complete()`가 재시도를 **자기 안에서** 끝내고 usage를 합산한 뒤(88~94·127행) 성공하면 `ok=true` **한 건**을 낸다. 그래서 **1차 시도가 파싱에 실패했다가 2차에 살아난 호출이 trace에서 성공 한 건과 구별되지 않는다.** run B가 그 모양이다 — `model_call` 25건이 전부 `ok`인데 그중 하나의 `output_tokens`가 **8,402**이고 요청당 상한이 8,192라 **1회 시도로 나올 수 없다.** v2도 3건(8,386·8,428·8,481)이 같다. **무엇이 틀리나**: [evaluation.md](../../evaluation.md) §5.1의 "모델별 구조화 출력 실패율"이다. `context.call_model` docstring이 그 지표의 분자를 `model_call`의 실패 이벤트로 못박아 뒀는데("스키마 파싱 실패율의 분자가 여기서 나오므로 삼키면 지표가 0이 된다"), **분자가 "회복 못 한 실패"만 세고 "일어난 실패"를 안 센다.** run B의 실패율은 지금 기록으로 **0%**인데 실제로는 시도 26회 중 1회가 실패했다. D46의 관측 건수도 같은 이유로 과소다. **사후 복원 규칙**: 시도 하나가 요청 하나이므로(`_post`가 시도마다 한 번) **`서빙 stdout의 POST /v1/chat/completions 수 − trace의 model_call 수 = 재시도 수`**다. **서버 로그를 파일로 받은 run만 복원된다** — 안 받은 run의 실패율은 못 쓴다([experiments/README.md](../../experiments/README.md) 「서빙 서버 stdout을 파일로 받는다」). 선택지: **(a)** `model_call`에 `attempts`를 싣는다 — 한 필드이고 기존 이벤트 수가 안 바뀐다. 실패 사유별 분해는 못 한다 **(b)** 시도마다 `model_call`을 낸다 — 분자·분모가 둘 다 시도 단위가 되어 지표 정의와 맞지만 **이벤트 수가 바뀌어 과거 run과의 대조가 끊긴다** **(c)** 재시도를 별도 `kind`(예: `model_retry`)로 낸다 — 과거 대조를 지키면서 수를 얻는다. **⚠ ~~팀 2×2가 도는 중에는 고치지 않는다~~ → **2026-09-01 2×2 전량 폐기로 이 대기 단서는 소멸했다. 아래는 그때의 사유다.** — (b)·(c)는 trace 스키마 변경이라 셀마다 다른 코드로 돌면 집계가 갈린다. 그때까지는 위 복원 규칙으로 사후 집계한다
