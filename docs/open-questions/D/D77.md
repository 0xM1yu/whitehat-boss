## 관측

2026-09-14 ATOM smoke의 sample_01 slice_0043에서 src/tftpcmd.c의 switch case/break가 빠졌다.
sample_03은 436후보 중 415개를 완료한 뒤 JVM heap OOM으로 중단됐고 미처리 후보는 21개였다.
원문은 `_workspace/atom-slicer/results/smoke-samples-20260914/`와 ATOM의 원문 실행 디렉터리에
보존했다. 기존 보고서는 PR #203에 있다. 이 수치는 v1 실행의 관측이며 v2 성능이 아니다.

기존 flows_query는 A/B 모두 후보 소속 함수 파라미터를 source로 사용하고 선택된 sink를
전달받지 않는다. 이것과 Case 간 클러스터링은 최초 의뢰 명세에 따른 구현이었다. 실험팀이
요청한 sink 인자 중심 역추적과 의미가 다르므로 변경된 계약으로 구분해야 한다.

## 선택지

1. v1 의미를 유지하고 한계만 알린다.
2. B를 호출 인자 기반 backward DDG로 바꾸고 v2로 구분한다. 노드 수와 경로 수를 구별하고
   제어 구조·구성 후보 출처·단계별 체크포인트를 함께 보존한다.
3. 별도 source 집합을 정한 sink별 reachableByFlows를 쓴다. source 정의와 eager 경로 비용이 남는다.

사용자가 2026-09-15에 2번을 포함한 계획의 구현을 승인했다. [slicer_backward.py](../../../slicer_backward.py),
[slicer_checkpoint.py](../../../slicer_checkpoint.py), [slicer_pipeline.py](../../../slicer_pipeline.py),
[slicer_source.py](../../../slicer_source.py)가 각각 추적·저장·재개·복원을 담당한다.

## 닫히는 조건

- 후보의 정확한 sink 식별, A/B별 흡수, 구성 후보 metadata가 보존된다.
- switch label, break/continue/goto의 원문 복구를 fixture와 실대상에서 확인한다.
- flow 저장 이후 중단·재개가 완료 flow를 재요청하지 않고 연속 실행과 같은 결과를 낸다.
- 입력·코드·Joern·설정이 다르면 재개를 거부하고 미실측을 수치로 채우지 않는다.
- sample 01/02/03 실행 결과·미처리·절단·로그를 저장소 실험 규칙에 따라 기록한다.

## 닫은 근거 — 2026-09-15 ATOM 실측

[실험 보고서](../../experiments/harness/2026-09-15-joern-slicer-v2-atom.md)가 원천이다.
Joern 4.0.605, 16 GiB heap, 전용 포트.

- **재개 동등성** — fixture에서 첫 `flow_saved` 커밋 직후 중단하고 같은 체크포인트로
  재개하니 `slices`가 연속 실행과 같았다(`slices_equal: true`, 5/5). 재개 실행의 HTTP
  trace는 `flows`를 **1회**만 보냈다(연속 실행은 2회) — 완료 단계를 다시 묻지 않는다.
- **제어문 복구** — [#205](https://github.com/0xM1yu/whitehat-boss/issues/205)가 지목한
  `src/tftpcmd.c:323~367` switch에서 `case` 5개·`default`·`break` 여덟 줄이 **누락 0**이다.
- **표본 3종 완주** — sample_01 `150/68`, sample_02 `52/30`, sample_03 `436/143`.
  셋 다 `queries_aborted=0`·`candidates_not_processed=0`. sample_03은 600초 기한에 걸린
  1차를 **재개로 이어 완주**했고, 재개 구간은 완료 후보 331건을 재질의 없이 건너뛰었다.
- **계약 거부** — 원본·코드·Joern 버전·설정·후보 manifest가 다르면 재개를 거부한다.

**이 검증이 결함 둘을 잡았다.** 버전 배너의 timestamp가 재개 계약을 매번 깨뜨리던 것과,
문맥 질의가 JVM 문자열 상수 상한(65,535바이트)을 넘겨 질의가 컴파일되지 않던 것이다.
둘 다 단위 테스트가 못 잡았고 실서버에서만 드러났다.

**닫으면서 남긴 것.** 재개 결과의 **바이트 동등성은 fixture 규모에서만** 쟀다 — 실대상
규모에서는 「완료 후보를 재질의하지 않는다」까지 확인했고 무중단 대조군이 없다. 또한
절단된 Case A 후보의 `analysis`는 CPG를 다시 만들면 같지 않다(보고서 §4.5). 둘 다 보고서
§6·§8에 미측정·후속으로 적었고, 이 항목이 아니라 그 목록이 그것을 든다.

Scout·캡슐 배선과 [D74](D74.md)의 결정을 대신하지 않는다.
