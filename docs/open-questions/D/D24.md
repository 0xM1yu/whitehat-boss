## 내용

**⏸ 모델 선정 대기로 보류 (2026-08-30, 5차 회의).** scout·auditor·critic 모델과 오케스트레이션(큰 모델 하나 vs 소형 앙상블)이 확정되기 전엔 이 값·판정의 수정이 무의미하다 — 그 기조가 바뀌면 실측 축이 통째로 달라진다. 결정 뒤 재개한다. W2가 후보 단위를 심볼로 바꾸면서 `thresholds.candidate_max`를 신설했고 값이 **256**인데, 그 수를 고른 유일한 이유는 `queue_maxsize`**(D25로 제거된)**가 in-process 작업 항목 수에 대해 당시 이미 쓰고 있던 값이라 **새 숫자를 지어내지 않기 위해서다** — 근거가 아니라 관례다. 지금 가진 실측은 파일 단위 후보 32건짜리 run뿐이고, 심볼 단위 후보 1건의 비용이 그와 같다는 근거가 없다. `budgets.tool_seconds`가 D15에 대해 있는 것과 **같은 상태**이고 같은 이유로 지금은 폭주 차단이 유일한 목적이다. **근거를 만드는 측정**: zlib 급 실대상 1회 run. 그 run이 후보 1건당 input/output 토큰과 wall time을 주고, 그때 이 값과 `_MAX_CONSECUTIVE_DROPS`(3, 같은 이유로 잠정치)를 함께 정한다. **초과분이 사라지지는 않는다** — `target_skipped(reason=over_candidate_max)`와 run 경고·report.md에 남으므로, 상한이 낮아서 잘렸다는 사실 자체는 기록에서 읽을 수 있다. **2026-08-23 — 첫 실측이 생겼다**([실험 보고서](../../experiments/harness/2026-08-23-pipeline-zlib-atom.md)): zlib에서 후보 **256건 / 18 m 54 s**, 실서빙 input **514,960 tok**, 최대 단일 프롬프트 **9,707 / 32,768**. 도구는 `tool_call` 238건 합계 112,578 ms다. **그래도 `candidate_max`를 정하지 않는다.** 이유 둘: ① 표본이 1건이다 ② **542 전량을 돌린 적이 없다** — 286건이 이 상한에 잘렸으므로 이 run은 "256건이 얼마 걸리는가"를 쟀지 "542건이 얼마 걸리는가"를 재지 않았다. **다음 입력은 상한을 542 이상으로 올린 zlib run 1회다.** `_MAX_CONSECUTIVE_DROPS`(3)도 같은 상태로 남는다 — 이번 run의 후보 단위 실패가 0건이라 그 값이 걸린 적이 없다. **2026-08-25 — 입력이 확보됐다. 값은 여기서 확정하지 않는다**([보고서](../../experiments/harness/2026-08-25-pipeline-zlib542-atom.md) §3 해석 ①). 위에서 “다음 입력은 상한을 542 이상으로 올린 zlib run 1회”라고 적었고, `run_20260825_0001`(`candidate_max: 1024`, 542건 전량 · `deferred 0` · `target_skipped 0`)이 그것이다. **후보 1건당**: wall **3.99 s** · GPU **3.73 s**(p50 3.56 / max 6.66) · input **2,161 tok** · output **167 tok**. **총계**: wall **2,161 s** = GPU **2,021.9 s**(93.6%) + tool **114.7 s**(5.3%) + 나머지 24 s — **GPU-bound이고 도구는 5%다.** **예산 역산으로 완주 가능한 후보 수**: `input_tokens` 4,000,000 → **≈ 1,850**(**가장 먼저 걸린다**) · `gpu_seconds` 7,200 → ≈ 1,930 · `output_tokens` 400,000 → ≈ 2,390. → **`candidate_max: 256`은 폭주 차단용으로도 과하게 낮다** — 예산이 실제로 묶는 선의 **14%**다. 542건은 예산의 30%만 쓰고 완주했다(`stopped_after` None). **⚠ 이 상한은 `single_gpu_12g` 한정이다.** GPU 2,021.9 s는 **전부 scout**이고 auditor·critic은 Fake라 `gpu_ms`가 `None`이다 — 장부에 0으로도 안 들어간다. **실서빙 auditor를 붙이면 후보당 GPU가 크게 오르고 위 세 값이 전부 내려간다.** 그래서 **이 run만으로 값을 확정하지 않는다**: 확정은 실서빙 auditor 프로필 run 뒤이고, `config/` 변경이라 어차피 별도 PR이다. `_MAX_CONSECUTIVE_DROPS`(3)는 **이번에도 걸린 적이 없다** — `model_call` **605건 전부 `ok=True`**라 후보 단위 실패가 0건이다. **같은 상태로 남긴다**. **2026-08-26 — 역산값이 ≈1,850에서 ≈1,783으로 내려왔다.** 후보당 input이 2,161 → 2,243으로 올라 `input_tokens`가 여전히 **가장 먼저 걸린다**(gpu 1,836 · output 2,222). 결론은 안 바뀐다 — `candidate_max: 256`은 예산이 묶는 선의 **14%**이고 zlib 542건은 예산의 **30.4%**만 썼다. 도구 비중은 5.3% → **6.3%**로 올랐다(build가 실제로 컴파일하고 8단계 도구 16건이 새로 생겼다). 여전히 GPU-bound다

## ⏵ 2026-09-24 — 제목의 앞 절이 등재 당일에 거짓이 됐다. 뒤 절은 그대로다

2026-08-23 11:01(`495f3ea`)이고 같은 날 13:41(`b3b88e9`)에 위 「내용」의 *"2026-08-23 — 첫 실측이
생겼다"*가 들어왔다 — **앞 절은 그때 거짓이 됐다.** 2026-08-25 run(`run_20260825_0001`)은 후보 1건당
값까지 냈다(wall 3.99 s · GPU 3.73 s · input 2,161 · output 167 tok). 그래서 앞 절에 취소선을 긋고
인덱스 행도 같이 고쳤다.

**뒤 절은 참이다.** `config/budgets.yaml`의 `candidate_max`는 여전히 **256**이고 그 주석이 스스로
