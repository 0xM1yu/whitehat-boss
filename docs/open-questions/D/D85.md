## 내용

**관측 [코드 + run · 2026-09-24 · origin/main `b99c863`].** 아래 코드 줄은 그날 origin/main을
열어 확인했고, 실패 run은 ATOM `d23-slicer-remeasure-20260923/out-enum/runs/sample_08`이다.

슬라이서는 대상 저장소의 모든 소스를 **엄격 UTF-8**로 읽는다 —
`raw.decode("utf-8")`, `errors=` 없음(`slicer.py:590`). 실패하면 그 파일은
`source_hashes`에 **안 들어가고**(성공했을 때만 등재, `slicer.py:596`),
`files_read_failed`만 오른다(`slicer.py:600`). 그 뒤 `prepare_checkpoint()`가
`len(source_hashes) != files_seen`이면 `raise ValueError`한다(`slicer_pipeline.py:170-171`).
`run()`이 그 예외를 안 삼키므로 status는 초기값 `failed` 그대로다(`slicer.py`의 `initial_result`).
CPG 빌드·후보 열거는 시작조차 못 한다.

**sample_08 실측.** `result.json`이 `status: failed`, `files_read_failed: 1`,
`candidates_case_a`·`candidates_case_b` 전부 `null`(단계 미도달)이고 `error` 필드가:

```
Source read failed: xmms/src/ui.cpp: 'utf-8' codec can't decode byte 0xb0
  in position 9061: invalid start byte; ValueError: Cannot checkpoint incomplete source reads
```

그 바이트는 `xmms/src/ui.cpp:246`의 `gtk_label_new("Track n°:")` — 취약점과 무관한 UI
문자열의 `°`(0xb0, Latin-1) 한 개다. **취약점 파일도 아닌 곳의 한 바이트가 run 전체를 죽인다.**

**실제 C/C++ 저장소에서 흔하다.** Latin-1 악센트·`°`·`©`가 주석(저자·저작권)이나 UI 문자열에
섞이는 것은 일상적이다. 그런 저장소는 슬라이스를 한 건도 못 낸다.

### 두 가지 실패 모드

이 abort는 **`--checkpoint`일 때만**이다 — 가드가 `if self.checkpoint:` 아래에 있다
(`slicer_pipeline.py:169`). 체크포인트를 안 켜면 예외가 안 나고 그 파일은 **`files_read_failed`로
세지고 `Source read failed: …`가 `errors`에 남아 status가 `partial`이 된다**(수정 전
`slicer.py`의 `except`, main `c301342` 실측: `exit 2 · status: partial · files_read_failed: 1`).
즉 조용하지는 않다 — 다만 그 파일 안의 후보·GT는 여전히 사라진다. 둘 다 나쁘고 성격이
다르다 — 하나는 요란한 실패(abort), 하나는 카운트되지만 그 파일을 못 보는 미포착.

### 지금 동작은 의도된 것이다 — 결함은 그 위쪽이다

엄격 디코딩과 완전성 가드 둘 다 일부러 그렇게 짰다. 주석이 근거를 든다 —
디코딩은 *"invalid bytes raise instead of turning into replacement characters that silently
change evidence"*(`slicer.py:588-589`), 가드는 부분 소스로 만든 체크포인트를 재사용하지
않으려는 것이다(`slicer.py:591-595` 주석). **둘 다 옳다.** 결함은 그 위쪽 —
**UTF-8 말고는 읽을 방법이 없다**는 것이고, Latin-1 한 바이트를 「읽을 수 없는 파일」로
취급하는 것이 과하다.

## 해소 [2026-09-24 · #254]

**선택지 (a)를 택하되 「무효 바이트만」으로 정밀화했다.** `load_sources()`가 UTF-8 strict로
읽고, 실패하면 **무효 바이트만** Latin-1 문자로 옮기는 오류 핸들러(`slicer.py`의
`slicer_latin1_bad_bytes`)로 다시 푼다. 파일 통째 `latin-1` 재해석이 아니라 **정상 UTF-8은
그대로 보존**한다(`©`·한글 주석이 안 깨진다). `surrogateescape`는 안 쓴다 — `\udcb0`가
UTF-8로 재인코딩되지 않아(`UnicodeEncodeError`) 출력 JSON(`assemble`·`export_sources`,
`slicer_export.py`)에서 크래시가 아래로 옮겨질 뿐이다(2026-09-24 실측 확인). 이 핸들러는
서로게이트를 안 만들어 재인코딩이 깨끗하다.

⚠ **`run_signature`는 바뀐다** — contract digest가 `source_hashes`뿐 아니라 모든 `slicer*.py`의
`code_hashes`를 담으므로(`slicer_pipeline.py:161-168`) 이 PR이 `slicer.py`를 고친 것만으로
달라진다(옛 체크포인트 이어달리기 불가). 안 바뀌는 것은 **파일별 `sha256`이 원바이트라
디코딩 방식과 무관**하다는 것까지다(`slicer.py:596`). 폴백된 파일은 `diagnostics`
(`stage: load_sources`)에 남는다 — 선택지 (a) 초안은 `measurement_notes`라 적었으나
`diagnostics`가 실제 자리다(카운터·status 영향 없음).

회귀는 `tests/test_slicer.py`가 고정한다 — `0xb0`(°)이 든 파일이 읽히고
`len(source_hashes) == files_seen`(prepare_checkpoint 완전성 조건)이 성립하는지, 폴백이
읽기 실패로 세지지 않는지, 그리고 **정상 non-ASCII UTF-8(`©`·한글)은 폴백 없이 원문 그대로**인지.

**남는 것.** 인코딩은 더 이상 파일을 못 읽게 만들지 않는다. 진짜 I/O 실패(OSError)는
그대로 `files_read_failed`로 세고, `--checkpoint`면 완전성 가드가 abort한다.

## 선택지

- **(a) 손실 없는 폴백 디코딩.** UTF-8 실패 시 `errors="surrogateescape"`(또는 latin-1)로
  다시 디코딩한다. `source_hashes`는 지금처럼 **원바이트** `sha256`이라(`slicer.py:596`)
  재현성 해시는 안 바뀌고, 바뀌는 것은 표시 문자열뿐이다. 증거 오염 없음 — 대체문자를
  안 만들고 바이트를 왕복 보존한다. 폴백된 파일 목록을 `measurement_notes`에 남긴다.
- **(b) 인코딩 감지 후 디코딩.** 파일별 휴리스틱/BOM. (a)보다 무겁고 비결정적 위험이 있어
  재현성 축과 충돌할 수 있다.
- **(c) 디코딩은 그대로 두고 실패 모드만 정리.** 못 읽은 파일이 있으면 run을 죽이지 말고
  `status: partial` + 누락 파일 명시로 내린다(조용한 누락도 없앰). 근본 원인(못 읽음)은
  안 고치므로 (a)·(b)와 배타가 아니라 **병행**이다 — 무엇을 읽을지와 못 읽었을 때 무엇을
  낼지는 다른 질문이다.

## 닫히는 조건

**증상(체크포인트 abort)은 제거됐다** — 수정 전 재현·수정 후 미재현을 단위 테스트에서 확인.
**아직 남은 것**: 비-UTF8 바이트가 든 **실제 저장소에서 슬라이스가 끝까지 나오는지**는
아직 안 쟀다(회귀 픽스처는 `load_sources()` 뒤 완전성 조건까지만 고정한다 —
CPG 반영·후보 열거·조립을 태우는 테스트는 없다). ATOM `sample_08` 재슬라이스로 그것을
확인하면 닫힌다. 그때까지 상태는 `부분`, 이슈는 **`Refs #254`**(닫지 않는다).
