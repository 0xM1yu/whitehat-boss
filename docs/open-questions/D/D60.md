# D60 — bench --apply가 --device 없이도 registry에 measured_on: null을 영구히 쓴다

| 상태 | 관련 문서 |
| --- | --- |
| 열림 | `src/bench_report.py` `apply`·`missing_run_labels` 경로, `src/config.py` `Benchmark.measured_on`, [portability.md](../../portability.md) §4, 선행 #119(#118 배치의 pre-run 검사) |

> 인덱스: [docs/open-questions.md](../../open-questions.md) · 작업 추적은 GitHub Issue

## 내용

#119가 `run` 진입에 소급 불가 필드 검사를 넣으면서 **`bench --apply`와 비대칭**이 생겼다. `run`은 실서빙 프로필에서 `--device` 없이 시작하지 않는데(없으면 `exit 2`, `_claim_run_dir` 앞이라 아무것도 안 남음), `bench --apply`는 같은 결여에 **경고만 하고 추적되는 `config/models.yaml`에 `measured_on: null`을 영구히 쓴다**.

**무엇이 더 나쁜가**: `run` 산출물은 `artifacts/` 아래 그 run 하나에 갇히고 `incomplete_fields()`가 비교표 제외를 판정한다. **registry는 그렇지 않다** — `measured_on: null`인 benchmark 값은 이후 모든 run의 예산 추정과 `cli estimate`가 읽는 공용 값이 되고, "어느 하드웨어 기준인지 사라진다"는 위험을 `portability.md`가 이미 그 필드에 적어 뒀다. #119의 자기 적대적 재검토(LOW)에서 나왔고, bench의 판정 축이 run 라벨이 아니라 registry 갱신이라 그 PR에서 안 닫았다.

**선택지**: (a) `bench --apply`에 `missing_run_labels` + serving 게이트를 재사용, `--device` 없으면 `exit 2` — 문구·판정이 한 곳에서 옴. 대가: 라벨 없이 bench 돌려 보던 흐름이 막힘. (b) **`--apply`일 때만** 막고 읽기 전용 bench는 그대로 — 결여의 대가가 "이 run이 빠짐"이 아니라 "공용 파일 오염"인 것과 맞음(**유력**). (c) `measured_on: null`을 안 쓰고 그 항목을 건너뜀 — `--apply`가 부분 성공이 됨. (d) 현행 유지 + 문서 명시. bench 다른 흐름을 아는 사람 판단 필요.
