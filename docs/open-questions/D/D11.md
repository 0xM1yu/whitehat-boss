## 내용

정적분석 도구는 아무것도 못 찾아도 정상 종료하므로 `Evidence(kind=static, ok=true)`가 남는다. 그대로 두면 "돌렸는데 없었다"가 신호로 세어져 Scout 점수가 오르고 Evidence Gate E1이 모든 Finding에서 참이 된다. 지금은 `nodes/signals.with_signal()`이 `exit_code`로 판별하는데, 이는 ToolRunner의 관례에 기댄 것이다 — **Semgrep은 발견이 있어도 0을 반환하는 모드가 있고 clang-tidy는 다른 관례를 쓴다.** 선택지: (a) `Evidence.findings: int` 추가(결합점을 건드린다) (b) 신호 없음은 Evidence로 남기지 않고 trace에만 기록 (c) 도구별 어댑터가 `ok`의 의미를 계약으로 고정. **2026-08-14: (c)를 채택하고 `ContainerToolRunner`가 플래그로 관례를 성립시킨다** \| — semgrep `--error`(붙이지 않으면 발견해도 0이라 모든 정적 신호가 "없음"이 된다), clang-tidy `--warnings-as-errors=*`. semgrep은 0·1만 정상 종료로 보고 나머지는 도구 실패(`ok=False`)다. **남은 구멍**: clang-tidy는 exit code만으로 "경고를 찾음"과 "대상이 컴파일되지 않음"을 구분하지 못한다 — 둘 다 non-zero다. 지금은 출력에 `clang-diagnostic-error`가 있으면 컴파일 실패로 보고 `ok=False`로 내리는데, **문자열 매칭이라 clang이 표기를 바꾸면 조용히 깨진다.** 그때는 컴파일 실패가 정적 신호로 집계된다 — (a)가 최종 해법인 이유가 여기 있다. **2026-08-14 실측으로 semgrep 부분은 해소**: `--json`을 붙이고 결과 문서의 유무로 "실제로 돌았는지"를 판정한다. 계기는 exit code 관례가 조용히 깨진 사건이다 — semgrep이 `--read-only` 아래 `$HOME/.semgrep`에 쓰려다 처리되지 않은 예외로 죽었고, 파이썬 크래시라 exit=1이었으며, `_SEMGREP_OK = (0, 1)`이 그것을 "발견함"으로 읽어 **한 번도 돌지 않은 도구가 정적 신호를 만들었다.** 이제 문서가 없거나 stderr에 Traceback이 있으면 `ok=False`다. `exit_code`는 프로세스가 반환한 값 그대로 남긴다(합성하지 않는다) — `--error`와 `--json`이 함께 동작하는 것을 실측으로 확인했다(발견 0건 → exit 0, 발견 있음 → exit 1). **clang-tidy 부분은 그대로 미해결**이고, 마커의 범위를 분명히 해 둔다: `clang-diagnostic-error`는 **컴파일 불가만** 잡는다. `--warnings-as-errors`로 승격된 `clang-diagnostic-*` 경고(예: `implicit-function-declaration`)는 파일이 실제로 컴파일된 상태의 진단이므로 정당한 발견으로 센다. **2026-08-23 — 이 구별이 실측에서 79 대 19로 드러났다**([실험 보고서](../../experiments/harness/2026-08-23-pipeline-zlib-atom.md)): zlib run에서 `Evidence(kind=static, ok=True)`는 **79건**인데 그중 `exit_code != 0`인 것은 **19건**이다. `ok`만 세면 분석 대상 artifact 79건 전부가 "정적 신호 보유"가 되고, 그 값이 (a′)의 정렬 키에 들어가면 **키가 상수가 되어 정렬이 아무 일도 안 한다.** 지금은 `signals.with_signal()`이 `exit_code`로 가르고 `runner._plan_targets()`가 그 결과만 세므로 19가 쓰인다. **이 항목이 (c)로 닫혔다고 보기 어려운 이유가 여기 있다** — 관례가 성립하는 것과 읽는 쪽이 두 수를 안 섞는 것은 다른 일이고, 후자는 지금 호출부 두 곳의 주석이 지키고 있다
