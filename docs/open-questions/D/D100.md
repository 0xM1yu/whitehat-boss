### 기제 [코드 · origin/main 64bd566]

> 이 문서의 줄 번호는 전부 `64bd566` 기준이다(관계 절의 `runner.py:2315` 포함). 줄을 고쳐 적지 않는다 — 인용한 슬라이서 파일은 `176b492`까지 안 바뀌었다.

- 후보 순서 -> `collect()`가 후보를 `(case, entry.file, entry.line, entry.symbol, selector, candidate_key)`로 정렬한다(`slicer_candidates.py:43-53`). 첫 키가 `case`라 문자열 순서로 `"A"` 전부가 `"B"`보다 앞이다. 후보 id(`slice_NNNN`)는 이 정렬 **뒤에** 발급된다(`:54-55`)
- `slicer_candidates.prioritize`(`--priority-files`) -> 엔트리나 앵커가 목록 파일에 있는 후보를 앞 층으로 옮기는 **안정 분할**이라 각 층 안의 순서는 `collect()` 그대로다. 실행 순서 = 우선 층의 A -> 우선 층의 B -> 나머지 A -> 나머지 B(이 기제 절은 `64bd566`의 것이다 — ⏵ 2026-10-04 이 순서는 이제 `--case-order ab`의 것이고, 기본 `ba`는 `prioritize()`가 case 묶음마다 나눠 우선 B -> 나머지 B -> 우선 A -> 나머지 A다 · 선택지 (a)·관측 3). 처리 순서는 체크포인트의 `candidates` 목록에 남는다(스스로 후보를 발견한 run의 결과 `candidate_manifest`에도 그 삽입 순서로 남지만, 체크포인트의 발견 기록을 되읽는 `--export-only`(병합 뒤 export — `slice_sharded.py`의 샤딩 run 전부)와 `--cpg` run의 결과 `candidate_manifest`는 키 순이라 처리 순서를 못 읽는다 — `slicer_pipeline`의 `restore_export`·`restore_discovery`와 체크포인트의 canonical JSON · [#434](https://github.com/0xM1yu/whitehat-boss/issues/434))
- 비용이 갈린다 -> Case A는 후보마다 `flows` 질의(`reachableByFlows`) 하나(`slicer_pipeline.py:160-162`), Case B는 `backward` 질의 하나(`:176-178`)이고, 둘 다 그 뒤에 `context` 확장 질의가 고정점까지 이어진다(`expand_context`, `:220-232`)
- 끊기면 순서 뒤쪽이 degraded -> `slice_sharded.py --wall-seconds`가 시간이 되면 샤드를 멈추고, 청구했지만 못 끝낸 후보는 export에서 앵커 줄만 든 슬라이스(`degraded_slice`, `:234-269`)가 된다. `slicer.py:880-883`의 주석과 README(「우선 파일」)가 어느 후보가 degraded로 남는지는 순서에 달려 있다고 이미 적는다. 이 항목이 짚는 것은 그 순서 안에서 **A가 B 앞**이라는 점이다
