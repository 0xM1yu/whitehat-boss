## 내용

[D68](D68.md) 선택지 (a)가 연속 폐기 차단기를 **역할별**로 바꿨다(#195) — 풀 멤버 하나가 전량 실패해도 형제의 성공에 카운터가 지워지지 않게. 그 수정이 맹점(D68)을 닫으면서 **두 가지를 함께 바꿨고**, 둘 다 #195 적대적 리뷰(MEDIUM-1·MEDIUM-2)가 짚었다.

### ① 교차역할 전역 장애가 N배 늦게 걸린다

역할별 카운팅은 D68을 닫는 동시에 **반대 방향으로 둔해진다.** 전역 게이트웨이 장애(모든 역할이 매 target에서 실패)에서, 카운터가 역할별이므로 각 역할이 따로 상한까지 올라가야 한다.

**계산 [코드 · `_MAX_CONSECUTIVE_DROPS = 3` · 풀 3역할].**

| | 발화 시점 |
| --- | --- |
| 단일 `scout` (역할 하나) | **3번째 시도** |
| 풀 3역할 (전역 장애) | **7번째 시도** (target1: 각 1 · target2: 각 2 · target3에서 `scout_memory`가 3에 닿음) |

일반화하면 N역할에서 전역 장애는 대략 **N배 늦게** 걸린다. D68 본문의 선택지 (a)가 *"per_stage에서 run 전체가 견디는 총 폐기 수가 또 달라진다"*고 이 방향을 예고했지만, **살아 있는 docstring에는 그 바뀐 의미가 안 적혔다** — #195가 지운 문장(*"연속 셋이 죽으면 그 단계가 체계적으로 고장"*)이 정확히 그 경우를 들고 있었다.

### ② `item.role`은 4단계 자리인데 5·6단계도 그 키로 센다

`_InFlight.role`은 팬아웃에서 **한 번 정해지고 재대입이 없다**(`runner.py`의 유일한 대입은 팬아웃 지점 하나 — `grep -n "\.role = " src/orchestrator/runner.py`). 그런데 `_TRIAGE_STEPS` 루프는 **같은 items로 3~6단계를 전부 돈다.**

그래서 **5단계 auditor가 체계적으로 고장 나면** 그 연속 카운터가 `consecutive[scout_memory]`·`[scout_boundary]`·`[scout_injection]` **세 버킷으로 갈린다** — 실패하는 역할은 auditor 하나인데. 후보 단위(`_triage_by_candidate`, `execution.mode` 기본값)도 같은 구조라 **풀이 아닌 살아 있는 경로에도 걸린다.** 여전히 발화하므로(①의 N배 지연을 안고) 결함이 아니라 **의미가 안 맞는 키**다.

## 왜 위험한가

둘 다 **차단기가 아예 안 걸리는 것은 아니다** — 그래서 D68 같은 「거짓 완주」는 아니다. 비용은 **더 오래 태운다**는 것이다: 전역 장애나 auditor 체계적 고장에서, 예전이면 3번째 시도에 멈췄을 run이 이제 수 배 더 많은 target을 태우고 멈춘다. `_MAX_CONSECUTIVE_DROPS`가 *"실대상 run에서 후보 단위 실패가 얼마나 자주 나는지 재 본 적이 없다"*는 잠정치라, 그 잠정치의 **실효 의미가 자리 수에 따라 달라진다**는 것이 안 적히면 다음 사람이 「3이면 3번째에 멈춘다」로 읽는다.

## 범위 — 지금 물리는가

**부분적으로 산 경로다.** ②는 풀이 아니어도(단일 `scout`에서도 auditor·critic 단계가 `scout` 키로 셈) 동작하지만, 단일에서는 키가 하나뿐이라 **오분류가 무해하다**(어차피 한 버킷). ①은 **풀 프로필이 켜져야** 난다. 그러므로 지금 코드에서 관측 가능한 실해는 없고, **풀 프로필을 실서빙으로 켜는 순간**(build-plan §8 swap) ①이 실측 가능해진다.

## 선택지

- **(a)** 연속 폐기 카운터를 **`(단계, 역할)`으로** 키를 잡는다 — 5단계 auditor 장애는 `(auditor, ...)` 버킷에 쌓여 4단계 자리로 안 갈린다(②). 대가: ①의 N배 지연은 **단계 안에서는** 여전하다(풀 3역할이 같은 단계에서 전역 장애면 그 단계에서 7번째에 걸림). 그리고 「단계」축이 늘어 `_MAX_CONSECUTIVE_DROPS`의 실효 상한이 또 달라진다.
- **(b)** 차단기를 **run 전역 카운터 + 역할별 카운터 둘**로 본다 — 전역이 `_MAX_CONSECUTIVE_DROPS`(교차역할 장애 조기 발화, ① 회복)를, 역할별이 D68(멤버 맹점)을 각각 막는다. 대가: 상한이 둘이 되어 상호작용을 다시 실측해야 한다.
- **(c)** **안 고치고 서술만 한다** — `_run_stage_for_all`·`_triage_by_candidate` docstring에 ①②를 명시하고 이 항목에 등재한다. 가장 싸고, **풀이 실서빙으로 안 켜진 동안 ①은 안 물린다.** 대가: ②의 오분류가 단일 경로에 남지만 무해하고, ①의 실효 의미가 자리 수에 걸린다는 것을 사람이 읽어야 안다.
- **(d)** `_MAX_CONSECUTIVE_DROPS` 자체를 자리 수로 나눈다 — ①의 N배를 상쇄. 대가: 잠정치를 실측 없이 또 만진다(§0). D68이 이미 그 값을 안 건드린 이유와 충돌.

**#195는 (c)를 골랐다** — D68 (a) 수정의 부수 결과를 **정직하게 서술**하되, 상한 재설계((a)·(b)·(d))는 `_MAX_CONSECUTIVE_DROPS`의 첫 실대상 실측이 선행이라서다(그 값이 잠정치인 것과 같은 상태). 풀을 실서빙으로 켜는 PR이 ①을 실측하고 (a)·(b)를 정한다.

## 닫히는 조건

`consecutive`의 키가 실패하는 단계의 역할을 정확히 반영하고(②), 교차역할 전역 장애의 발화 시점이 자리 수와 무관하게 상한에 걸리면(①) 닫힌다. (c)만 하면 상태는 `열림`으로 남는다 — 서술은 됐지만 두 의미 변화가 코드에 그대로다.

> ⏵ 2026-10-10 — ①의 「자리 수와 무관하게 상한」은 자리 수가 상한 미만일 때만 문자 그대로 성립한다. 자리 수 ≥ 상한이면 `자리 수 + 1`번째다(위 「해소」의 ⏵). 한 대상의 팬아웃 전멸과 구별할 수 없어서다 -> 이 조건은 그 해석으로 닫았다.

## 해소 (2026-10-10)

**고른 것 -> (a)+(b).** (a)만으로는 닫히는 조건 ①이 안 된다 -> 같은 단계 안 전역 장애가 여전히 자리 수만큼 늦다(선택지 (a)의 대가). 그리고 (a)만 하면 단일 `scout`도 바뀐다 [코드 읽기 · 미실행] -> 4단계·5단계 실패가 번갈아 나면 예전엔 한 버킷이라 3번째에 섰는데 단계로 갈리면 더 늦다. (b)의 run 카운터는 #195 전 카운터와 같은 것이라(키 없음, 죽지 않고 끝난 시도가 지움) 단일 `scout`의 동작이 그대로 남는다. (d)는 잠정치를 실측 없이 만지므로 안 했다(§0). `_MAX_CONSECUTIVE_DROPS` 값은 그대로 3이다.

**동작.**

| 카운터 | 키 | 지우는 것 | 막는 것 |
| --- | --- | --- | --- |
| run | 없음 | 후보 단위: 죽지 않고 끝난 시도(끝까지 갔든 승격이 안 돼 멈췄든) · 단계 단위: 그 행의 아무 성공 | ① 전 자리 장애 — 폐기가 서로 다른 대상 둘 이상에 걸쳐 상한에 닿으면 선다 |
| 자리 | `_caller(단계, 자리)` -> 4단계는 Scout 자리, 5단계부터는 자리 없음 | 그 단계를 지난 시도 | D68 멤버 하나의 전량 실패, ② 뒤 단계 고장 |

- 후보 단위 리셋은 시도가 끝날 때만 한다(국면 A에서 죽음 또는 국면 B 끝). 국면 A 통과만으로는 안 지운다 -> 4단계는 개시·정착이 같은 키라, 개시 통과가 지우면 정착이 매번 죽어도 0과 1을 오간다.
- Scout가 안 올린 대상의 완주는 5단계 키를 안 지운다 -> D88이 첫 건 정지의 이유 하나로 든 구멍(*"Scout가 안 올린 대상이 카운터를 0으로 되돌리고 키가 Scout 자리라"*)도 같이 닫힌다. 첫 건 정지 자체는 그대로다.
- 단계 단위는 카운터가 행(`_run_stage_for_all` 호출) 안에서만 산다 -> ADR 0009의 리셋 경계 그대로.

변이 -> `_caller`가 5단계에서도 자리를 키로 쓰게 바꾸면 5단계 키 검사 다섯(단위 하나 · Auditor 둘 · #296 백스톱 둘)이, run 카운터 판정을 끄면 풀 전역 장애 검사 둘과 단위 검사 둘이, 자리 카운터 판정을 끄면 일곱(D68 둘 · Auditor 둘 · 단위 둘 · D88 하나)이 빨개진다(2026-10-10 PR #584 리뷰 §3 — 처음 판은 상한 판정 둘을 다 꺼도 D68 검사가 초록이었다. 성공 0 백스톱이 같은 정지를 내서다. 그 검사는 이제 백스톱을 끄고 돈다). `passed`가 안 거친 단계의 키까지 지우게 바꾸면(D88 구멍) 후보 단위 검사 둘이 빨개진다.

**⏵ 2026-10-10 (PR #584 리뷰 §1) — 처음 판의 run 카운터는 한 대상의 팬아웃 전멸로 run을 죽였다.** 처음 판은 run 카운터가 폐기 수만 셌다. 풀 자리 3 = 상한 3이면 **한 대상의 세 자리가 죽는 것만으로** 상한에 닿았다 [리뷰 실측 · Fake · 대상 4 중 하나만 422] -> `is_complete=False`, `stopped_after=4`, 풀 호출 3, 출력 토큰 0 (origin/main 러너: 완주, 호출 18, 출력 토큰 1,386). 첫 대상만이 아니라 앞 대상이 완주해 카운터가 0이 된 뒤의 대상(둘째·셋째)도 같았다. 트리거는 422만이 아니다 -> `ModelGatewayError(status=None, generating=True)`(#261)도 `_is_droppable`이 참이라 느린 슬라이스 하나가 세 자리를 타임아웃시키면 같다. 조건은 「자리 수 ≥ 상한」이다 -> 자리 3 · 상한 3이 정확히 같아 드러났다.

고친 것 -> run 카운터는 폐기가 **서로 다른 대상 둘 이상**에 걸쳐 있을 때만 선다(`_ConsecutiveDrops.run_targets`). 한 대상의 팬아웃 전멸은 증거 하나이고 뒤 대상이 멀쩡하면 그 완주가 카운터를 지운다. 「대상 단위로 센다」(대상이 바뀔 때만 올림)는 쓰지 않았다 -> 대상 수 `(상한-1)·자리 수 + 1`번째 시도(7)에서야 서서 조건 ①을 되돌린다(리뷰 검증자가 적용해 봤다). 상한 값을 자리 수로 나누거나 곱하는 것도 안 했다(§0, (d)와 같은 이유).

**대가 -> 조건 ①의 「자리 수와 무관하게 상한번째」는 줄었다.** 첫 대상의 세 자리 전멸은 전 자리 장애와 **둘째 대상이 죽기 전까지 구별되지 않는다**(둘 다 같은 trace다). 그래서 전 자리 장애는 `max(상한, 자리 수 + 1)`번째 시도에 선다 [코드 읽기 + e2e 실측: 자리 3 · 상한 3에서 4번째. 자리 2는 단위 검사로 상한번째를 쟀다. 자리 1은 코드 읽기(시도마다 대상이 달라 폐기마다 대상 수가 는다)이고 기존 단일 `scout` 검사는 서는 것만 문다. 자리 4 이상은 안 쟀다 - Role 열거형에 Scout 풀 멤버가 셋뿐이다]. 자리 키만이던 처음 판의 7번째보다 앞이고, 3번째보다 한 건 늦다. 풀 전역 장애 검사 이름이 `..._at_the_cap_...`에서 `..._as_soon_as_a_second_target_fails`로 바뀐 이유다.

⚠ **둘째 대상의 첫 실패 하나로 서는 모양이 새로 생겼다(자리 수 ≥ 상한일 때)** -> 상한 3 · 자리 3에서 대상 하나가 세 자리 전멸한 직후 다음 대상의 한 자리가 죽으면(나머지 둘은 멀쩡해도) 폐기 4건이 연속이라 선다. 자리 카운터는 안 서는 모양이다. 이것이 과한지는 실서빙 빈도를 재 봐야 안다 [미실측].

1. 본문은 「풀을 실서빙으로 켜는 PR이 ①을 실측하고 (a)·(b)를 정한다」고 했는데 실측 없이 정했다 -> 값을 안 만졌고, run 카운터는 #195 전 동작을 되살린 것이라서다. ⏵ 2026-10-10 -> 단일 `scout`(시도마다 대상이 다르다)에서만 문자 그대로 같다. 풀은 「대상 둘 이상」 조건이 더해졌다(아래 ⏵).
2. 상한 값은 여전히 잠정치다 -> 실대상 run의 후보 단위 실패 빈도를 잰 적이 없다. 카운터가 둘이 된 뒤의 실효(어느 쪽이 먼저 닿는지)도 실서빙에서 안 쟀다. 위 수는 전부 Fake다.
3. 단계 단위 `per_stage`에서 run 전체가 견디는 총 폐기 수가 후보 단위와 다르다는 ADR 0009의 성질은 그대로다.
4. 위 「⏵ 2026-10-10」의 두 가지 -> (가) 전 자리 장애가 상한번째보다 한 건 늦게 선다. (나) 자리 수 ≥ 상한이면 둘째 대상의 한 자리 실패로 서는 모양이 생겼다. 둘 다 빈도 미실측이고, 실서빙 풀 run이 나오면 그 수로 상한과 「대상 둘 이상」 조건을 다시 본다.
5. 폴러(`tools/monitor.py`)의 라이브 `error_storm`은 run 카운터 모양을 미탐한다([D76](D76.md)의 ⏵). 정지 뒤 종료 전이 사유로는 잡힌다.
