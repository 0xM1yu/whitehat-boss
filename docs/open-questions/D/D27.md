## 내용

**2026-08-25 첫 실서빙 대조**([보고서](../../experiments/harness/2026-08-25-pipeline-zlib542-atom.md) §3 해석 ⑧). 서버 측 `Prefix cache hit rate` **30.5%**(기동 로그에 보존 — 세 번 유실 끝에 처음 남은 값이다). 같은 run의 장부는 **실서빙 542콜 cached `0 / 1,052,676` = 0.00%**, **전체 605콜 cached `17,078 / 1,171,453` = 1.46%**다. **차집합이 정확히 Fake 콜 63건**(auditor 55 + critic 8)이다. → **`cached_tokens` 열은 실서빙에서 0이고 Fake에서만 값이 있다.** 서버는 실제로 30.5%를 재사용하는데 장부가 못 적고, **아무것도 캐시하지 않는 Fake가 값을 낸다.** 그 열을 그대로 읽으면 **“Fake가 캐시를 잘 쓴다”**로 읽힌다. **R6과 갈라 두는 이유**: R6은 “값이 항상 0이라 지표를 못 낸다”이고, 이쪽은 **“0이 아닌 값이 하필 틀린 쪽에만 있다”**는 것이다 — R6보다 한 겹 나쁘다. R6이 “없는 값”이면 이건 **“오도하는 값”**이라, R6이 닫혀도 이 열의 Fake 쪽은 남는다. **근본은 같다**: 응답의 `prompt_tokens_details`가 `None`인데 `/metrics`는 값을 준다 — 이 run이 그 대조를 **실서빙에서 처음** 만들었다. **판단이 필요한 것**: **(a)** `/metrics`에서 읽어 채운다 — 콜 단위가 아니라 엔진 누적치라 콜별 장부에 어떻게 배분할지가 먼저다 **(b)** 실서빙에서 못 재는 값이면 `None`으로 두고 **Fake도 안 내게 한다** — 지금은 **“0”과 “안 쟀다”가 같은 모양**이고, 그 구분이 없으면 조건 비교에서 Fake가 이긴다. **2026-08-26 — 두 번째 대조값. 이번엔 단계별로 직접 갈렸다.** 8/25는 "실서빙 0 / 전체 1.46%"라는 차집합으로 보였는데, 오늘은 4단계(실서빙) `cached_tokens` **0** · 5단계(Fake) **17,568** · 7단계(Fake) **1,526**으로 장부가 단계마다 나뉜다. **아무것도 캐시하지 않는 Fake만 값을 내고 실제로 캐시하는 실서빙이 0을 적는다** — 역전 진단이 재현됐다. 서버 값도 30.5% → **30.0%**로 안정적이라 열이 뒤바뀐 것이지 서버가 흔들린 것이 아니다
