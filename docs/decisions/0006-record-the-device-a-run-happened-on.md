# 0006. run과 registry 수치에 **어느 장비에서 나왔는지**를 기록한다

- 상태: 제안
- 일자: 2026-08-15
- 관련: [portability.md](../portability.md), [evaluation.md](../evaluation.md) §2.3·§6, [model-serving.md](../model-serving.md) §3·§5, [decisions/0005](0005-tool-runner-override.md), [STATUS.md](../../STATUS.md) §10

## 배경

지금까지 실서빙 검증은 Seraph에서만 했고, ATOM 접근이 열렸다. **한쪽으로 이관하는 것이
아니라 둘 다 지원 대상이다** — ATOM이 주 장비이고, Seraph는 이식성 요구사항이다(프로젝트
종료 후 외부 사용자가 자기 클러스터에서 이 하네스를 돌릴 수 있어야 한다).

그런데 **실행 기록에 장비를 가릴 것이 하나도 없다.**

| 기록 필드 | 장비를 구분하는가 |
| --- | --- |
| `model_checksums` | 아니다. model·tokenizer·quantization 해시라 **설계상 장비 불변**이다 |
| `prompt_versions` | 아니다 |
| `tool_runner` | 부분적으로만. Seraph=singularity / ATOM=podman(2026-08-17 실측)이지만 `--tool-runner`로 뒤집힌다<br><br>⚠ **ATOM 쪽은 반증됐다(2026-08-21 확인, 08-28 재확인).** 그 장비에는 docker 29.2.1과 podman 4.9.3이 함께 있고([portability.md](../portability.md) §6), 실서빙 프로필의 선언값도 2026-08-28에 `docker`로 되돌아갔다([decisions/0005](0005-tool-runner-override.md) 마지막 절). **원 문장은 지우지 않는다** — 이 ADR이 "장비를 가릴 것이 하나도 없다"를 세운 근거가 이 표이므로, 그때 무엇을 보고 그렇게 적었는지가 남아야 한다. **그리고 판정("부분적으로만")은 오히려 더 약해졌다**: 2026-08-17 시점에는 `podman`이 ATOM을 유일하게 가리켰는데, 지금은 ATOM도 GPU 없는 팀원 노트북도 `docker`다(portability.md §3). 이 필드로 갈리는 것이 그만큼 줄었으므로 `RunRecord.device`를 따로 두자는 이 ADR의 논지는 그만큼 세진다 |
| `thresholds`·`budget`·`seed` | 아니다. 공정성 규칙상 오히려 같아야 한다 |
| endpoint | **기록되지 않는다** |

즉 같은 프로필로 돈 Seraph run과 ATOM run은 `run_manifest.json`만 놓고 보면 구분할 수
없다. 반년 뒤 run 30개를 놓고 "이 중 어느 것이 ATOM이었나"를 답할 방법이 없다.

registry 쪽도 같다. `bench --apply`는 어느 장비에서 치든 `config/models.yaml`의 같은
`benchmark:` 블록에 쓴다. Seraph(A2000 12GB, sm_86)의 tok/s와 ATOM(GB10, 통합메모리)의
tok/s가 같은 칸에 들어가는데, 그 사실이 남지 않으면 다음 사람이 그 값으로 다른 장비를
예측한다.

**이건 endpoint가 갈라지는지와 무관한 결함이다.** 현재 registry의 endpoint는 전부
`127.0.0.1`이고(서버와 클라이언트를 같은 노드에서 돌리므로 앞으로도 그럴 가능성이 높다),
그래서 설정은 한 벌로 충분하다. 그런데도 위 문제는 그대로 남는다 — 설정이 같아도 **기계가
다르다.**

## 결정

두 곳에 값을 하나씩 더한다.

- **`RunRecord.device: str | None`** — `doctor`/`run`/`bench`의 `--device`가 준 라벨.
- **`Benchmark.measured_on: str | None`** — `bench --apply`가 수치와 함께 쓴다.

`--device`는 **명시 라벨 전용이다. 설정을 바꾸지 않는다.** 값이 없으면 `None`이고, 그
뜻은 `repo_dirty=None`과 같다: **확인 못 함.**

**막지 않고 기록한다.** `--device` 없이도 `run`도 `--apply`도 정상 동작한다. 이 저장소는
지금까지 금지가 아니라 기록으로 문제를 풀어 왔다 — `--tool-runner`는 막지 않고
`RunRecord.tool_runner`에 남기고(0005), `repo_dirty`는 dirty 실행을 막지 않고 기록만 한다.
여기서만 금지로 가면 그 논법이 깨지고, 무엇보다 1차 DoD("registry benchmark 값 채움")가
구조적으로 막힌다.

대신 **드러나게** 만든다: `doctor`는 `--device`가 주어졌을 때 registry의 `measured_on`과
비교해 다르면 WARN을 내고, `bench --apply`는 `--device` 없이 쓰면 그 순간 WARN을 낸다.
`run`은 `device`가 비면 `incomplete_fields()`가 "비교표에서 제외한다"를 남긴다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| **오버레이(`--device`가 장비별 endpoint를 덮는다)부터 만든다** | **endpoint가 실제로 갈라지는지 미확인이다.** 지금 registry의 endpoint는 전부 `127.0.0.1`이고, 서버와 클라이언트를 같은 노드에서 돌리므로(Seraph는 규정상 그것이 유일하게 가능한 방식이다) 두 장비에서 같은 값이다. 게다가 갈라진다면 그 원인은 공용 계정의 **포트 충돌**일 가능성이 높은데, 그러면 키는 장비가 아니라 **사용자**다 — `--device atom`이라는 이름과 `RunRecord.device = "atom"`이라는 기록은 참이지만 실제로 갈라진 것을 가리키지 않는다. 이름을 잘못 붙인 기록은 없는 기록보다 나쁘다. 확인 후 별도 ADR로 다룬다 |
| 호스트명(`platform.node()`)으로 자동으로 채운다 | **한 필드에 두 사실이 들어간다.** `"atom"`(사람이 붙인 장비 라벨)과 `"REDACTED-cluster-master"`(하네스 프로세스가 돈 호스트명)는 서로 다른 사실인데 기록만 보면 구분할 수 없다. 게다가 자주 어긋난다 — 로그인 노드에서 하네스를 돌리면 GPU 작업이 한 톨도 일어나지 않은 기계 이름이 적힌다. `measured_on="atom"`과 호스트명 `"atom-gb10-01"`을 비교하면 **같은 장비인데 불일치 WARN**이 뜨고, 헛경고가 나기 시작하면 사람은 경고를 안 읽는다 |
| 장비가 다르면 `--apply`를 거부한다 | 1차 DoD(registry benchmark 채움)가 구조적으로 막힌다. ATOM에서도 `--device atom`을 쓸 것이므로 "장비가 지정되면 거부"는 영영 못 쓰는 명령을 만든다. 그리고 이 저장소의 논법(금지가 아니라 기록)과 어긋난다 |
| 장비별 프로필을 추가한다 | 0005가 같은 이유로 기각한 것이다 — 조건 축에 장비 축이 섞이고, 조건이 늘 때마다 프로필이 장비 수만큼 곱해진다 |
| 환경변수로 받는다 | 실행 커맨드라인에 남지 않아 재현 시 놓치기 쉽다(0005의 같은 판단). 이 프로젝트의 다른 오버라이드는 전부 플래그다 |
| 문서로만 규율한다 | 문서가 규율하는 것은 사람이고, 비교표를 만드는 것은 기록이다(0005의 같은 문장) |

## 결과

**얻는 것**

- Seraph run과 ATOM run이 `run_manifest.json` 한 필드로 갈린다. 외부 사용자가 낸 결과와
  팀의 결과가 비교표에서 섞이지 않는다.
- registry의 수치가 어느 하드웨어 기준인지 파일 안에서 자명해진다.
- `doctor`가 "이 registry는 다른 장비 기준이다"를 실행 전에 말한다.

**잃는 것 / 위험**

- 라벨은 **사람이 준다.** 안 주면 `None`이고, 그 run은 비교표에서 빠진다. 자동화로
  메우지 않기로 한 것이 이 결정의 핵심이므로 이 비용은 의도적이다.
- 라벨 문자열에 규칙이 없다. `"atom"`과 `"ATOM"`이 다른 값으로 잡힌다. 값 집합을 닫는
  것은 장비가 늘 때마다 코드를 고쳐야 해서 지금은 열어 둔다.
- **§2.3의 예외가 아니다.** `--device`는 설정을 바꾸지 않으므로 0005와 성격이 다르다.
  다만 "장비가 다른 run을 같은 비교 셀에 넣지 않는다"는 판단은 여전히 **사람이** 해야
  하고, 지금 그것을 강제하는 코드는 없다(0005가 남긴 것과 같은 한계).

**되돌리는 비용: 낮다.** CLI 플래그 하나와 `doctor`의 검사 하나를 지우면 된다.
`RunRecord.device`와 `Benchmark.measured_on`은 되돌리지 않는다 — 이미 쓰인 기록의 스키마를
되돌리는 것이 더 비싸고, 오버레이가 오든 안 오든 필요한 기록이다(0005가
`RunRecord.tool_runner`에 대해 내린 것과 같은 판단).

## 후속

- ATOM에서 (a) 하네스를 서버와 같은 노드에서 돌리는지 (b) 계정이 공용이라 포트가
  사용자별로 갈리는지를 확인한다. (b)가 참이면 필요한 것은 `--device` 오버레이가 아니라
  **포트 오프셋**이고, 그때 별도 ADR을 쓴다.
- 비교표를 만들 때 `device`가 다른 run을 같은 셀에 넣지 않는지 확인하는 검사를 `eval/`에
  넣을지 정한다. `tool_runner`에 대해 0005가 남긴 후속과 같은 항목이다.
- 라벨 값 집합을 닫을지(예: `portability.md` §6의 표에서 유도) 재검토한다. 장비가 셋이 되면.
