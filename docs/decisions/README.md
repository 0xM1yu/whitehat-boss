# 결정 기록 (ADR)

되돌리기 비싼 결정만 여기에 남긴다. 일상적인 구현 선택은 코드와 PR에 남기면 된다.

## 언제 ADR을 쓰는가

- 오케스트레이터 선택·교체
- 상태 저장소 선택
- 모델 계열 확정 및 양자화 기본값
- 평가 프로토콜 변경(조건 정의, 데이터셋 구성)
- 분산 인프라 도입
- 하드웨어 검증 결과에 따른 방향 전환

## 파일 이름

`NNNN-짧은-제목.md` (예: `0000-example-title.md`). 번호는 순번이며, 폐기해도 재사용하지 않는다.

## 템플릿

```markdown
# NNNN. 제목

- 상태: 제안 | 승인 | 폐기 | 대체됨(→ NNNN)
- 일자: YYYY-MM-DD
- 관련: docs/xxx.md, open-questions.md D#

## 배경
무엇이 문제였고 어떤 제약이 있었는가. 측정값이 있으면 출처와 함께.

## 결정
무엇을 하기로 했는가. 한 문단.

## 대안과 기각 사유
| 대안 | 기각 사유 |
| --- | --- |

## 결과
얻는 것, 잃는 것, 그리고 **되돌리는 비용**.

## 후속
이 결정으로 새로 생긴 할 일이나 재검토 조건.
```

여는 결정이므로, 되돌리기 쉬운 것과 별개로 **실행 기록(`RunRecord.tool_runner`)에 흔적이
남는다.**

0006은 0005와 같은 논법을 쓰지만 **예외를 열지 않는다.** `--device`는 설정을 한 글자도
바꾸지 않고 기록만 남기므로 §2.3 규칙 2에 걸리지 않는다. 대신 규칙 5("장비가 다른 run은
같은 비교 셀에 넣지 않는다")가 성립하려면 그 기록이 있어야 한다. 이 ADR이 **장비별 설정
오버레이를 지금 만들지 않기로 한 근거**도 함께 담고 있다 — endpoint가 실제로 갈라지는지
미확인이고, 갈라진다면 키가 장비가 아니라 사용자일 수 있다.

0007은 성격이 또 다르다 — **결정이 아니라 측정 기록이 본체다**(위 "언제 ADR을 쓰는가"의
"하드웨어 검증 결과에 따른 방향 전환"). [model-serving.md](../model-serving.md) §3이
