# 0003. RoutingPolicy를 `src/interfaces/`가 아니라 `src/orchestrator/`에 둔다

- 상태: 제안
- 일자: 2026-08-08
- 관련: [engineering-guide.md](../engineering-guide.md) §3, [roadmap.md](../roadmap.md) §3

## 배경

노드가 임계값을 직접 비교하면 두 가지가 깨진다. 첫째, "임계값은 `config/`에서 온다"
(engineering-guide.md §8.5)가 코드 리뷰로만 지켜진다. 둘째, 정책을 바꿔 보려면 노드를
전부 고쳐야 해서 A/B 비교가 사실상 불가능해진다.

그래서 판정을 `RoutingPolicy`로 분리했다. 남은 문제는 **어디에 두는가**다.
`src/interfaces/`에 두면 4개 인터페이스와 나란히 서게 되는데, 그 디렉터리는 roadmap.md
§3에서 "트랙 간 유일한 결합점이므로 변경 시 전원 공지 대상"으로 지정된 표면이다.

두 경계는 성격이 다르다. `src/interfaces/`의 4개는 **외부 시스템 경계**다 — 모델
게이트웨이, 검색 엔진, 도구 샌드박스, 저장소. 구현이 저장소 밖에 있고 교체가 곧 인프라
교체다. `RoutingPolicy`는 **내부 정책 경계**다. 구현이 이 저장소 안에 있고, 바뀌는 이유가
실험 조건이지 인프라가 아니다.

## 결정

`RoutingPolicy` Protocol과 v1 구현체 `FixedThresholdPolicy`를
`src/orchestrator/policy.py`에 둔다. `src/interfaces/`는 PR 1에서 합의받은 4개 그대로
유지한다. 모든 판정은 `policy_decision` trace 이벤트로 남긴다 — 어떤 정책이 어떤 신호를
보고 어디로 보냈는지가 남아야 나중에 A/B 비교의 데이터가 된다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| `src/interfaces/`에 5번째로 추가 | 전원 공지 대상 표면이 넓어진다. 내부 정책을 바꿀 때마다 8개 트랙에 공지해야 하는데, 정책은 실험하며 자주 바뀔 값이다 |
| 별도 최상위 패키지(`src/policy/`) | 정책은 오케스트레이터 밖에서 쓰이지 않는다. 쓰는 곳이 하나인데 패키지를 나누면 import 경로만 길어진다 |
| 노드에 임계값 비교를 그대로 둠 | §8.5가 리뷰로만 지켜지고, 정책 비교의 데이터 소스가 생기지 않는다 |

## 결과

- 얻는 것: 전원 공지 표면이 4개로 유지됨, 정책 결정이 전부 trace에 남아 A/B 비교의
  기준선이 생김, 노드에서 임계값 리터럴이 사라짐
- 잃는 것: 정책이 오케스트레이터 안에 있으므로 다른 컴포넌트가 쓰려면 옮겨야 한다.
  지금은 쓸 곳이 없다
- **되돌리는 비용: 낮다.** 파일을 옮기고 import 경로를 바꾸면 된다. 다만 `src/interfaces/`로
  옮기는 순간 전원 공지 대상이 되므로, 옮기는 결정 자체는 그때 다시 논의한다

## 후속

- 재검토 조건: 오케스트레이터 밖(예: 별도 실험 러너, 대시보드)에서 같은 정책을 평가해야
  할 때
- v1 구현체는 `FixedThresholdPolicy` 하나다. 두 번째 구현체가 생기면 `policy_decision`
  이벤트의 `policy` 필드로 결과를 갈라 볼 수 있다
