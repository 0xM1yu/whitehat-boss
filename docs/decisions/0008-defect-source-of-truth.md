# 0008. 결함의 소스 오브 트루스 — 문서가 본체, GitHub Issue는 참조 미러

- 상태: **승인** (2026-09-08 팀 사인오프). 미결 넷의 결론은 아래 「사인오프」 절에 있다
- 일자: 2026-09-01
- 관련: [open-questions.md](../open-questions.md) §서두·:7, [CLAUDE.md](../../CLAUDE.md) §3, 이슈 #91–#103 「이관 메모」, 2026-09-01 병렬 전수조사(아티팩트 `e6cee515`), [tests/test_docs_format.py](../../tests/test_docs_format.py) (`test_decision_references_point_at_a_real_row`)·[tests/test_open_questions_layout.py](../../tests/test_open_questions_layout.py) (`test_every_d_has_a_body_file`), PR #86(워크플로 매뉴얼)·#104(코드 D참조 이슈화)·#105(본문 분리)

## 배경

결함의 "원천(source of truth)"이 어디인지 저장소가 **세 갈래로** 말한다. 셋을 동시에 만족시킬 수 없다.

| 자리 | 주장 |
| --- | --- |
| `open-questions.md:7` | "이 문서가 진실의 소스이고, GitHub Issue는 그 추적용이다" |
| `CLAUDE.md §3` | "이슈가 결함의 원천이고 상태의 원천이다" (그러면서 같은 절이 "인덱스는 지우지 않는다") |
| 이슈 #91–#103 이관메모 | "docs/open-questions.md 폐기에 따라 이 이슈가 원천이 된다. 표의 D 행은 이관 완료 후 제거한다" |

이건 취향이 아니라 **CI가 걸린 문제**다. 문서·설정·코드 전반의 D 참조가 그 표를 가리키고, `test_decision_references_point_at_a_real_row`가 그 참조를 전수 검사한다. **표를 지우면 그 테스트가 깨진다** — 55행을 실제로 지우고 돌려 확인했다. (`test_every_d_has_a_body_file`은 표의 행을 **순회**하므로 표가 사라지면 검사 대상이 0이 되어 **공허하게 통과한다** — 표를 지키는 것은 이 테스트가 아니다.)

그리고 이미 **드리프트가 실재한다**: 2026-09-01 전수조사에서 39건(= `[Dn]` 제목을 단 열린 D-시리즈 이슈 전수) 중 **13건은 이슈 본문이 더 최신임을 건별로 확인**했다. 나머지 26건 중 **개별 대조를 한 것은 표본 5건(#82·#83·#60·#64·#80)뿐이고, 그 다섯에서는 D 본문이 더 최신이었다.** 26은 39에서 13을 뺀 수이지 "D 본문이 더 최신"으로 전수 확인된 수가 아니다. 어느 쪽을 읽느냐에 따라 같은 결함의 상태가 다르게 보였고, 전수조사의 "사실이 틀린 12건"이 전부 이 분기에서 나왔다.

**근본 원인은 "소스"라는 말이 두 가지를 뭉갠 것이다** — 결함의 **내용(분석·증거·선택지)** 과 결함의 **상태(열림/부분/닫힘·추적)**. 둘의 소스를 따로 정하면 세 문장의 모순이 사라진다.

## 결정

**문서가 본체이고, GitHub Issue는 그것을 참조하는 미러다.** 아스펙트마다 단일 작성자(single writer)를 못 박는다.

| 아스펙트 | 소스(단일 작성자) | 나머지 |
| --- | --- | --- |
| **내용**(분석·증거·선택지·해소 근거) | `docs/open-questions/D/D<n>.md` 본문 (PR로 리뷰) | 이슈 본문은 D 본문을 **링크**만 한다 |
| **상태**(열림/부분/닫힘 등) | `D<n>.md`의 상태 필드 → 인덱스 표(`open-questions.md` §2)에 반영 | 이슈 open/closed는 여기서 **파생**된다 |
| **추적·논의** | GitHub Issue | — |

운영 규칙 셋:

1. **상태는 `D<n>.md`에서만 바꾼다.** 이슈에서 상태를 직접 편집(수동 close 포함)하지 않는다.
2. **이슈는 PR 본문의 `Closes #n`으로만 닫힌다** — 본문이 `닫힘`으로 바뀌는 그 PR이 자동으로 닫는다. 일부만 다루면 `Refs #n`. (문서 → 이슈 **단방향** 동기화라 두 곳이 갈릴 수가 없다.)
3. **인덱스 표는 유지한다.** CI가 그 위에 서 있고, "한 파일에서 훑는 참고면"이 이 문서의 값어치다.

## 근거

- **오프라인 단일 참고면이 값어치의 핵심이다**(PR #104 리뷰에서 제기). 작업 중 같은 오류를 반복하지 않으려면 훑어볼 곳이 필요한데, 상태가 이슈에만 있으면 상태 하나 확인하려고 매번 GitHub 리모트를 뒤져야 한다 — 그게 더 큰 병목이다.
- **드리프트를 구조로 막는다.** 상태를 양쪽에서 편집하면(현 상태) 반드시 갈린다. 단방향 `Closes`만 허용하면 물리적으로 안 갈린다.
- **CI가 이미 문서-권위를 인코딩한다.** 위 두 테스트가 인덱스·본문 무결을 강제하므로, 표를 유지하는 이 모델은 **테스트 변경이 0이다.** 반대로 표를 지우는 길은 CI를 깨고 대체물을 새로 만들어야 한다.

## 고려한 대안 — 이슈-원천 모델

상태의 소스를 GitHub Issue로 두고, 본문/인덱스의 상태는 이슈에서 파생(또는 제거)하는 안. `CLAUDE.md §3`과 #91–103 이관메모가 기운 방향이다.

- 장점: 이슈 트래커의 기본 기능(라벨·담당·알림)을 그대로 쓴다.
- 단점: (1) 상태를 보려면 리모트가 필요 — 오프라인 참고면이 깨진다. (2) 인덱스 표를 지우면 CI가 깨지고 D 참조가 전부 dangling. 표를 남기면 "이슈가 상태 원천"과 "표에 상태가 보임"이 다시 이원화된다. (3) 본문(문서)이 내용 소스인 것은 어차피 유지되므로, 상태만 갈라놓으면 한 결함이 두 시스템에 걸친다.

→ **본 ADR은 문서-권위를 추천**하지만, 팀이 이슈-원천으로 기운 흔적이 있어 이 대안을 나란히 남긴다. 이건 팀이 골라야 하는 지점이다.

## 결과 (사인오프 후 후속)

이 ADR이 승인되면 다음이 따라온다(각각 별도 PR):

1. **`CLAUDE.md §3` 개정** — "이슈가 상태의 원천" → "문서(`D<n>.md` 상태 필드)가 상태의 원천, 이슈는 추적 미러". 같은 절의 "인덱스는 안 지운다"와도 정합된다.
2. **이슈 #91–#103 「이관 메모」의 "표 제거 예정" 철회** — 코멘트 또는 편집으로 정정.
3. **일회성 정합** — 이슈가 더 최신인 13건을 본문으로 흡수하고, 전수조사가 나열한 "사실이 틀린 12건"을 본문/이슈에서 정정한다.
4. (선택) `open-questions.md` §서두의 워크플로(PR #86)를 이 3규칙으로 확정 반영.

이슈-원천이 채택되면 위 1·3의 방향이 반대가 되고, 인덱스·CI 처리 방안을 별도로 설계해야 한다.

## 미결 — 팀 확인 필요 (특히 @danielcho02)

> **위 「사인오프」 절이 이 넷에 답했다(2026-09-08).** 아래는 그때 물었던 원 질문이다.

- **방향**: 문서-권위(추천) vs 이슈-원천 — 어느 쪽인가?
- **상태의 물리적 위치**: 상태 필드를 본문+인덱스 양쪽에 두고 인덱스를 손으로 맞출지, 아니면 본문만 두고 인덱스를 생성물로 만들지(그러면 표를 사람이 안 건드림).
- **`D<n>.md`가 없는 이슈의 상태 원천**: 규칙 1이 "상태는 `D<n>.md`에서만 바꾼다"인데 본문 파일이 없는 열린 이슈가 있다. 2026-09-01 작성 시점에 셋이었고(#108 · #111 · #114), **그중 둘은 이 ADR과 같은 머지 배치에서 해소된다** — #108은 PR #109가 등재하고(본문 파일 + 인덱스 행이 생긴다), #111은 PR #112가 `Closes`로 닫는다. **남는 것은 #114**(`D-series` 라벨이지만 제목에 번호가 없다)다. 규칙 1·2 아래에서 이런 이슈는 상태를 바꿀 자리도, `Closes`가 닫을 근거 문서도 없다. **#108이 이 문제의 표본이었다** — 제목에 번호가 붙은 채로 등재(PR #109)보다 이슈가 먼저 났다. 이 ADR이 지키려는 워크플로(등재 → 이슈화)가 한 번 역전됐던 기록이다. (a) 등재를 강제해 번호를 주거나 (b) "본문 파일이 없는 이슈는 이슈가 상태 원천"이라는 예외를 명시하거나 — 어느 쪽인지 정해야 한다. **설계 판단이 안 걸린 결함에 D 등재를 강제하면 과하다**는 점도 함께 본다(#111이 그 사례다 — 상태 어휘를 안 바꿔 과거 run 판정이 안 뒤집힌다).
- **규약 강제 수단**: "이슈 상태 직접 편집 금지"를 관례로만 둘지, 아니면 CI/봇으로 강제할지(예: 이슈 close는 `Closes #` 경유만 허용).
